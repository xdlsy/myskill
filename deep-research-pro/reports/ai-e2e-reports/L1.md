# L1 — 流程改造(每一环都变)

## 执行摘要

- **实现是最容易的一环,瓶颈正向上下游转移。** Faros AI 对 10,000+ 开发者的 telemetry 显示:AI 让开发者完成的 task 增加 21%、合并的 PR 增加 98%,但 **PR review 时间增加 91%**,而组织级 DORA 交付指标"基本持平"——典型的 "AI Productivity Paradox"。([Faros AI](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025))

- **"审查时间 +91%"常被误归于 DORA Report 2025,但其原始出处是 Faros AI 2025 年 7 月的 telemetry 分析;DORA Report 2025(9 月发布、~5,000 开发者问卷)是独立佐证。** 两项研究结论一致但样本与方法不同,引用时需区分。更值得注意的是:Faros 2026(22,000 开发者)显示 review 时间已飙升至 **+441%**,bug/developer +54%,incident/PR +242.7%——"Acceleration Whiplash"。([Faros AI](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025))

- **Spec-Driven Development (SDD) 正在把"写代码"重构为"写规格"。** 工程师的核心产出从 code 转为 spec,代表工具有 GitHub Spec Kit、AWS Kiro、Tessl、BMAD-METHOD、OpenSpec。Kiro 用 EARS notation 把 prompt 转成 requirements → design → implementation 三阶段,并明确把 spec 作为"single source of truth"。([Martin Fowler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html), [GitHub Blog](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/), [kiro.dev](https://kiro.dev/))

- **架构判断仍是人类领地。** 共识是:AI 擅长生成备选方案与解释 trade-off,但"taste、权衡、问责"仍属人类;务实做法是把 AI model 视为架构中的"unreliable service"。([HackerNoon](https://hackernoon.com/system-design-in-the-age-of-ai-what-still-requires-human-judgment), [InfoQ](https://www.infoq.com/minibooks/architecture-age-ai-opportunity/))

- **测试策略从"写用例"升级为"定验证策略"。** Property-based testing (PBT) 正成为 AI 生成代码的关键验证层(fast-check、Anthropic PBT 研究、arXiv "Property-Generated Solver"),golden/snapshot/approval test 仍用于回归,但 **AI 生成代码让传统 test pyramid 受到挑战**。([Anthropic Research](https://www.anthropic.com/research/property-based-testing), [arXiv 2506.18315](https://arxiv.org/html/2506.18315v1))

- **发布更保守,feature flag 成为 AI 代码的强制项。** 因不能同等信任 AI 代码,渐进式交付(canary、percentage rollout、ring deployment)从"最佳实践"变为"默认设置";Cloudflare 把其 Flagship 产品定位为"built for the age of AI"。([LaunchDarkly](https://launchdarkly.com/guides/progressive-delivery/how-feature-management-enables-progressive-delivery/), [Cloudflare](https://blog.cloudflare.com/flagship/), [GrowthBook](https://www.growthbook.io/blog/feature-flags-ai-development))

- **"96% 技术领导认为可观测性必需"需要纠偏。** 原始来源是 LogicMonitor《2026 Observability & AI Outlook》(100 位 VP+ IT 决策者,Q2 2025):准确表述是 **"96% 的 IT leader 预期 observability 支出持平或增长"**(其中 62% 预期增加),强调的是预算韧性而非"必需性"。该调研另有"59% 对平台洞察不满意"等更尖锐结论。([LogicMonitor](https://www.logicmonitor.com/resources/2026-observability-ai-trends-outlook))

- **维护/重构是最弱一环,需按 James Shore 框架刻意分配预算。** Shore 的原始论述(2026 博客):*"You need AI that reduces your maintenance costs, and in proportion to the speed boost you get from new code. Without it, you're screwed."* 若 AI 让写代码提速 2× 而维护成本同时翻倍,约 **5 个月内**净收益归零并转负——"Hotel California"锁定效应。([James Shore](https://www.jamesshore.com/v2/blog/2026/you-need-ai-that-reduces-your-maintenance-costs))

## 核心发现

### 1. 需求 / Spec —— 新的核心瓶颈

#### 1.1 工程师的角色从"写代码"转为"写规格"

Spec-Driven Development (SDD) 的核心定义是"documentation first":先把需求、约束、验收标准写成结构化 spec,spec 成为 single source of truth,再让 AI agent 在 spec 边界内生成代码。Martin Fowler 站点的对比文章将其概括为:spec-first 的本质是"the spec becomes the source of truth for the project"。([Martin Fowler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html))

这一转变把瓶颈从实现(打字速度)前移到了 spec:工程师的产出从"代码行数"变为"可测试的规格行数",spec 的精确性、可测试性、完备性直接决定 AI 输出质量。GitHub 在官方公告中明确将 Spec Kit 定位为"building high-quality software with any AI coding agent"的 toolkit,强调的是流程而非模型。([GitHub Blog](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/))

#### 1.2 主要的 spec 方法与工具

| 工具 | 厂商 | 核心机制 | 关键特性 |
|------|------|----------|----------|
| **GitHub Spec Kit** | GitHub(开源) | CLI + templates,把开发分成 spec → plan → implement 多阶段,可适配任意 AI agent | vendor-neutral、`specs/` 目录产物、review gates([github/spec-kit](https://github.com/github/spec-kit)) |
| **Kiro** | AWS/Amazon | 使用 **EARS notation**(Easy Approach to Requirements Syntax)结构化需求;prompt → requirements → design → implementation 三阶段;Claude 驱动,集成 Amazon Bedrock | "vibe coding → spec-driven"、acceptance criteria 自动生成、launched mid-2025([kiro.dev](https://kiro.dev/), [AWS re:Invent 2025 DEV314](https://www.youtube.com/watch?v=4qcWgPb-8Fk)) |
| **Tessl** | Tessl | 把 spec 作为"living artifact",持续更新 | spec-as-source([Augment Code 对比](https://www.augmentcode.com/tools/best-spec-driven-development-tools)) |
| **BMAD-METHOD** | 开源社区 | 多角色 agent 协作(PM/Architect/Dev 等)的 SDD 流程 | ([Augment Code](https://www.augmentcode.com/tools/best-spec-driven-development-tools)) |
| **OpenSpec / Augment Cosmos / Cursor** | 各厂商 | 不同侧重的 SDD 实现 | Cosmos 强调全流程,Cursor 以编辑器为中心([Augment Code](https://www.augmentcode.com/tools/best-spec-driven-development-tools)) |

Kiro 的差异化在于:它把 spec 阶段产品化为 IDE 内的一等公民,用 EARS notation 保证需求"精确、可测试",并在 re:Invent 2025 的 DEV314 session 中明确把目标定位为"move beyond AI coding to agentic engineering"。AWS 自己的案例显示生命科学客户用 Kiro 在三周内构建了 drug discovery agent。([kiro.dev](https://kiro.dev/), [AWS Industries Blog](https://aws.amazon.com/blogs/industries/from-spec-to-production-a-three-week-drug-discovery-agent-using-kiro/))

> **落地启示:** 选择 SDD 工具时,关键不是模型能力,而是 (a) spec 的结构化程度(EARS、Gherkin、自定义);(b) review gates 的强制力;(c) vendor lock-in 风险。GitHub Spec Kit 的 vendor-neutral 是企业首选起点。

### 2. 设计 —— 人定架构与取舍,AI 给备选方案

跨多个来源的共识是:**AI 不取代架构判断,而是放大问责(amplifies accountability)。** HackerNoon 的"System Design in the Age of AI"提出务实框架:把 AI model 视为架构中的"unreliable service",围绕其不可靠性设计 fallback、validation、human-in-the-loop gate。([HackerNoon](https://hackernoon.com/system-design-in-the-age-of-ai-what-still-requires-human-judgment))

InfoQ 的《Architecture in the Age of AI》minibook 进一步指出,在招聘和实践信号上,评估"human judgment、system design、hands-on AI collaboration"变得更有价值而非更少——也就是说架构师岗位不是被消灭,而是被重新定义。([InfoQ](https://www.infoq.com/minibooks/architecture-age-ai-opportunity/))

具体分工建议(综合多源):
- **人类保留:** 架构方向、技术选型权衡(latency vs cost vs consistency)、安全边界、合规决策、跨团队契约。
- **AI 辅助:** 生成备选方案、解释 trade-off、产出 ADR 草稿、扫描已知反模式、对设计做"红队"提问。
- **关键原则:** 任何架构决策的最终 accountability 不能下放给 AI——AI 可以建议,但签字的是人。([Medium / Predict](https://medium.com/predict/what-happens-when-ai-starts-reviewing-your-data-architecture-designs-0ac80fb0b393))

### 3. 实现 —— AI 主写,是最容易的一环

这是文献中最少争议的一环。Faros 数据显示 AI 采用者 PR 合并量 +98%(2025)/ +16.2%(2026,基数变大后放缓),task 完成 +21%(2025)/ +33.7%(2026)。([Faros AI](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025))

但"容易"不等于"无害":
- **PR 体积膨胀:** Faros 2025 显示 AI 让 PR size +154%,2026 仍达 +51.3%——直接违背 DORA 推崇的"small batch"原则,加重 review 负担。
- **多任务并发陷阱:** 2026 数据显示 AI 用户日均接触 +67.4% 的 PR context、+17.7% 的 task context;"work restarts"+13.8%,26% more in-progress tasks 出现 7 天以上停滞——"easy to begin, hard to finish"。([Faros AI](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025))

> **落地启示:** 实现环节的 KPI 不应再是"代码行数"或"PR 数",而要引入"completion ratio"、"stall rate"、"rework rate"(DORA 2024 新增指标)来对冲虚假繁荣。

### 4. 测试 —— AI 生成测试 + 人定验证策略

#### 4.1 Property-Based Testing 成为 AI 代码验证的关键层

arXiv 2025 论文《Use Property-Based Testing to Bridge LLM Code Generation and Validation》提出 "Property-Generated Solver",用 PBT 作为生成与验证之间的 bridge,引导 LLM 产出更正确、更可泛化的代码。([arXiv 2506.18315](https://arxiv.org/html/2506.18315v1))ACM 的实证研究也表明,unit test + PBT 组合能揭示传统 testing 遗漏的缺陷。([ACM](https://dl.acm.org/doi/10.1145/3696630.3728702))

**Anthropic 自己的研究**是一个强信号:他们构建了用 PBT 在大型代码库中高效定位 bug 的 agent,通过推断代码的 general properties 来发现 example-based test 抓不到的问题。([Anthropic Research](https://www.anthropic.com/research/property-based-testing))

实操上,fast-check(JS/TS)、Haskell QuickCheck、Python Hypothesis 等库可让 agent 自动生成数百个随机输入验证不变式,被多个来源定位为"scalable verification layer for AI-generated code"。([Understanding Data](https://understandingdata.com/posts/property-based-testing/), [Medium / VectorWorksAcademy](https://medium.com/@VectorWorksAcademy/property-based-testing-in-the-age-of-ai-coding-a-paradigm-shift-97b83051f8b8))

#### 4.2 Golden / Snapshot / Approval Test 与 Test Pyramid 的张力

传统 test pyramid(单元多、集成少、E2E 极少)在 AI 代码下面临挑战:Harness、Autonoma 等指出,LLM 生成的 test 即使 coverage 100% 也可能"形式达标、语义缺失",需要 approval test(golden master)锁定行为基线,再以 PBT 探索不变式。([Harness](https://www.harness.io/blog/unit-testing-in-ci-cd-how-to-accelerate-builds-without-sacrificing-quality), [Autonoma](https://getautonoma.com/blog), [Angie Jones](https://angiejones.tech/verifying-entire-api-responses/))

**人的新职责:** 不再写"用例",而是定义"验证策略"——选择哪些性质值得用 PBT、哪些行为需要 golden 锁定、哪些 agent 输出要走 contract test。

### 5. 评审 —— AI 预审 + 人在 gate 把关,已成新瓶颈

#### 5.1 头条统计的对抗式核验(重要纠偏)

| 常见说法 | 实际原始来源 | 真实数字 | 差异 |
|----------|-------------|----------|------|
| "DORA 报告说 review 时间 +91%" | **Faros AI** 2025 年 7 月 telemetry(10,000+ 开发者) | +91% median PR review time | 来源误归:Faro ≠ DORA |
| "AI 让 bug 率 +9%" | 同上 Faros 2025 | +9% bugs/developer | 同上 |
| "组织级交付持平" | 同上 Faros 2025 | flat DORA metrics | 同上 |
| "DORA 2025 也证实了" | **DORA Report 2025** 2025 年 9 月(近 5,000 开发者问卷) | 95% 开发者用 AI,80%+ 自报生产力提升,AI 是"amplifier" | 不同方法(问卷 vs telemetry),但同向 |

两项研究是**互补而非重复**:DORA 是 self-reported survey,Faros 是 objective telemetry。Faros 自己也强调"developer sentiment is pretty aligned with objective telemetry"。([Faros AI](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025), [DORA Report 2025](https://dora.dev/dora-report-2025/))

**更严峻的更新:** Faros 2026(22,000 开发者)显示瓶颈在恶化而非缓解——median PR review time **+441%**、bugs/developer **+54%**、incidents/PR **+242.7%**、**31% 更多的 PR 在零 review 下合并**。这被命名为 "Acceleration Whiplash"。([Faros AI](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025))

#### 5.2 行业实证:Salesforce 与 Morgan Stanley

- **Salesforce Engineering** 在《Scaling Code Reviews: Adapting to a Surge in AI-Generated Code》中承认 review latency 逐季上升,且最大 PR 的 review 时间甚至开始"plateau 或下降"——意味着大 PR 被放弃仔细审查。配套文章显示他们通过 AI-enabled tooling 在 code output +30% 的同时维持了 quality/deployment safety。([Salesforce Engineering](https://engineering.salesforce.com/scaling-code-reviews-adapting-to-a-surge-in-ai-generated-code/), [Salesforce Engineering](https://engineering.salesforce.com/how-ai-enabled-tooling-boosted-code-output-30-while-keeping-quality-and-deployment-safety-intact/))

- **Morgan Stanley** 采用 **risk-based PR routing**:低风险变更走快速通道,高风险变更才进入深度人工审查,用以对抗"PR 拥堵"。该案例由 Moderne 在《AI Code Review Is the New Bottleneck in Agentic Coding》中披露。([Moderne](https://www.moderne.ai/blog/ai-didnt-break-coding-it-broke-code-review))

#### 5.3 新分工

- **AI 预审(第一道闸):** 自动 lint、安全扫描、test 覆盖检查、PR summary 生成、风险分级。
- **人在 gate 把关(第二道闸):** 架构正确性、业务语义、跨系统影响、不可量化风险。Anthropic 已推出 Claude Code 的 Code Review feature(Research Preview,Team/Enterprise),把 AI 预审产品化。([Reddit r/ClaudeAI](https://www.reddit.com/r/ClaudeAI/comments/1rp9dps/introducing_code_review_a_new_feature_for_claude/))

> **落地启示:** review 瓶颈不能用"加快 review"解决,只能用"减少需要 review 的 PR 数 + 风险分级 + small batch 强制"解决。把 PR size 作为一流工程指标。

### 6. 发布 —— 渐进式交付、feature flag、灰度,因不能同等信任 AI 代码

核心论点:AI 生成的代码"看似通过测试"但可能在边界情形、安全、性能上隐含问题,因此发布策略要比人写代码更保守。

- **Feature flag 成为强制项:** GrowthBook 在《Feature Flags in AI-led Development》中明确指出,gradual rollout 让团队"在每个 gate 监控性能",在概率性 AI 场景下尽早发现问题。([GrowthBook](https://www.growthbook.io/blog/feature-flags-ai-development))

- **解耦 deploy 与 release:** LaunchDarkly 把 progressive delivery 的核心定位为"separate code deployments from feature releases",提供自动 rollback、AI 运行时配置控制、集成 observability。([LaunchDarkly](https://launchdarkly.com/guides/progressive-delivery/how-feature-management-enables-progressive-delivery/), [LaunchDarkly Blog](https://launchdarkly.com/blog/beyond-feature-flags-launchdarkly-vs-tools/))

- **"为 AI 时代而生"的厂商叙事:** Cloudflare Flagship 直接自我定位为"feature flags built for the age of AI",强调可在不改代码的前提下逐步暴露新代码路径、toggle flag、调整 rollout。([Cloudflare](https://blog.cloudflare.com/flagship/))

- **典型模式:** canary release、percentage rollout、ring deployment(dogfood → 内部 → 1% → 10% → 100%)。([Flagshark](https://flagshark.com/blog/progressive-delivery-feature-flags-practical-guide/), [Unleash](https://www.getunleash.io/blog/progressive-delivery-with-feature-flags))

### 7. 运维 —— 可观测性变为强制项

#### 7.1 头条统计的对抗式核验(重要纠偏)

| 常见说法 | 实际原始来源 | 真实数字 | 差异 |
|----------|-------------|----------|------|
| "96% 技术领导认为可观测性必需" | **LogicMonitor《2026 Observability & AI Outlook》** | **"96% 的 IT leader 预期 observability 支出持平或增长"**(其中 62% 预期增加) | 语义偏差:原数据讲的是"预算韧性",不是"必需性" |

**调研方法:** 100 位 VP+ IT 决策者(均有 observability 预算权),2025 年 Q2(mid-2025)执行,67% 来自 1,000+ 员工的企业,75% 拥有最终决策权,89% 集中在北美。([LogicMonitor](https://www.logicmonitor.com/resources/2026-observability-ai-trends-outlook))

**更有信息量的同源数据:**
- **84%** 在推进或考虑 tool consolidation;**67%** 可能在 1–2 年内更换 observability 平台;**59%** 对当前平台"产出 actionable insights 的能力"不满意;只有 **4%** 的组织达到 AI 在 IT 运维的"full operational maturity"。([LogicMonitor](https://www.logicmonitor.com/resources/2026-observability-ai-trends-outlook))

#### 7.2 为什么 AI 代码让 observability 从"nice to have"变为"non-negotiable"

Faros 2026 数据给出了硬证据:**incident/PR +242.7%**——每一次代码变更触发生产事故的概率比 AI 普及前翻了三倍多。这意味着 MTTR、change failure rate、trace 覆盖率、alert 质量不再是"运维 KPI",而是"能否上 AI 代码"的前置条件。([Faros AI](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025))

DORA Report 2025 的 7 项"AI 放大器能力"中,**"quality internal platforms"** 与 **"strong version control practices"** 直接对应 observability + 快速 rollback 的能力——报告强调"AI ROI fundamentally depends on platform maturity"。([Faros AI](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025), [DORA Report 2025](https://dora.dev/dora-report-2025/))

### 8. 维护 / 重构 —— 最弱的一环,需刻意分配预算

#### 8.1 James Shore 框架的原始论述(已核验)

来源:**James Shore 2026 博客《You Need AI That Reduces Your Maintenance Costs》**。原文核心引述:

> *"You need AI that reduces your maintenance costs, and in proportion to the speed boost you get from new code. Without it, you're screwed. You're trading a temporary speed boost for permanent indenture."*
>
> *"You write code twice as quick now? Better hope you've halved your maintenance costs. Three times as productive? One third the maintenance costs."*
>
> *"About five months after you start using Rock Lobster [虚构的 agentic 框架], your productivity is back down to where you started, and a few months after that, it's worse than it would have been had you never touched Rock Lobster in the first place."*

来源:([James Shore](https://www.jamesshore.com/v2/blog/2026/you-need-ai-that-reduces-your-maintenance-costs))

#### 8.2 Shore 的量化模型(Wisdom of the Crowd)

Shore 给出了可复现的电子表格模型,核心假设:每写 1 个月的代码,后续每年要花 **10 天维护(第一年)**、**5 天/年(此后每年)** 维护。结论:
- 默认参数下,约 **2.5 年**后团队超过一半时间花在维护上;
- 维护成本减半 → 多 3 年才到 50%;
- 维护成本翻倍 → 不到 1 年就跌破 50%。

#### 8.3 "Hotel California"锁定效应(Shore 原创)

> *"When you stop using the agent, all the productivity benefit goes away... but the added maintenance costs don't! As long as that code's still around, you're stuck with lower productivity than if you had never touched the agent at all."*

这是对"先冲速度再说"策略的致命反驳:AI 生成的代码即使在你停用 AI 后仍持续产生维护成本。Shore 还提示这不是反 AI 立场——"AI that makes maintenance itself more productive"也是有效的杠杆。([James Shore](https://www.jamesshore.com/v2/blog/2026/you-need-ai-that-reduces-your-maintenance-costs))

#### 8.4 业界佐证

- **LeadDev:** "Data suggests that if current trends continue, defect remediation and refactoring may soon dominate developer workloads."([LeadDev](https://leaddev.com/technical-direction/how-ai-generated-code-accelerates-technical-debt))
- **arXiv 2601.07786:** GenAI 诱导的 self-admitted technical debt 中,design 类债务减少但 requirement 类债务增加——意味着债务形态在变。([arXiv](https://arxiv.org/html/2601.07786v1))
- **Tembo:** 明确定义"AI technical debt"为 AI 生成代码中的 shortcut、duplication、architectural issue 累积的维护负担。([Tembo](https://www.tembo.io/blog/ai-technical-debt))

> **落地启示(Shore 框架的操作化):** 维护降本预算应与 new code 提速成比例。若 AI 让新代码提速 2×,必须把等量资源投到:refactoring sprint、AI 辅助的 dependency upgrade、dead code 删除、文档同步、test 加固。否则 5 个月内净收益归零。

### 9. 现实案例 —— 头部组织如何重设计环节

## 风险与陷阱

1. **"买 Copilot = 落地 AI"的谬误。** Faros 数据证明:个体提速 21–33% 但组织级交付持平/恶化。没有流程改造,工具采购只是把瓶颈搬家。([Faros AI](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025))

2. **Review 瓶颈被低估。** "+91%"已被误读为"DORA 数据",实际是 Faros;且 2026 已恶化到 +441%。若团队没把 review capacity 作为一等约束规划,交付系统会先在 review 阶段崩盘,而非实现阶段。([Faros AI](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025))

3. **"代码量 = 生产力"的旧 KPI 继续误导。** AI 让 PR 数翻倍但 rework rate、stall rate、incident/PR 同步上升。继续用 PR 数 / 代码行数激励工程师,会系统性鼓励"easy to begin, hard to finish"。([Faros AI](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025))

4. **维护债务的"Hotel California"锁定。** 按 Shore 模型,AI 代码提速 2× 而维护成本不变,5 个月内净收益归零;停用 AI 后维护负担仍存。先冲速度再考虑维护的顺序是致命的。([James Shore](https://www.jamesshore.com/v2/blog/2026/you-need-ai-that-reduces-your-maintenance-costs))

5. **"96% 认为可观测性必需"的传播失真。** 原数据是"96% 预期 observability 支出持平或增长"。引用时若不纠偏,会高估组织对 observability 的真实成熟度(实际只有 4% 达到 full operational maturity)。([LogicMonitor](https://www.logicmonitor.com/resources/2026-observability-ai-trends-outlook))

6. **Spec 草率化。** SDD 若退化成"让 AI 写一份 spec 然后让 AI 实现",等于把人剔除出 loop,失去 spec 的核心价值(精确、可测试、可追溯)。spec 必须由人主导编写或至少人审批。

7. **Test pyramid 假阳性。** AI 生成的 test 即使 coverage 100%,也可能无法捕获语义错误;只信 coverage 数字会让缺陷逃逸到生产。必须叠加 PBT 与 golden test。([Harness](https://www.harness.io/blog/unit-testing-in-ci-cd-how-to-accelerate-builds-without-sacrificing-quality), [Anthropic PBT](https://www.anthropic.com/research/property-based-testing))

8. **架构 accountability 下放。** 让 AI 做"看起来合理"的架构决策而无人类签字,会放大组织既有 dysfunction——DORA 2025 把 AI 定位为"amplifier"而非"fixer"。([Faros AI](https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025))

9. **"先部署再治理"。** Straiker 调研显示 96% IT leader 计划扩大 AI agent 部署,但 75% 把治理与安全列为首要挑战——治理滞后会触发合规与安全事故,金融业尤其敏感。([Straiker](https://www.straiker.ai/blog/the-agent-security-gap-why-75-of-leaders-wont-let-security-concerns-slow-their-ai-deployment))

## 给企业的落地建议

### 一、按环节重构 KPI(而非按工具采购)

| 环节 | 旧 KPI(陷阱) | 新 KPI(建议) |
|------|--------------|--------------|
| 需求/Spec | 需求数量 | spec 精确度、acceptance criteria 覆盖率、spec 变更率 |
| 实现 | 代码行数 / PR 数 | completion ratio、stall rate、rework rate |
| 测试 | coverage % | PBT property 数、golden test 覆盖的行为、逃逸缺陷率 |
| 评审 | review 速度 | PR size 分布、risk-based routing 命中率、零 review PR 占比 |
| 发布 | deploy 频率 | change failure rate、flag-protected 比例、rollback 率 |
| 运维 | uptime | MTTR、incident/PR、alert precision |
| 维护 | (通常不度量) | 维护成本占比、dead code 比、dependency 新鲜度 |

### 二、把"流程改造"作为独立项目立项

不要把 AI 落地放在"工具采购"预算线下,而要单独立项:
- 设立 **AI 工程平台 team**(参考 Shopify、JPMorgan 的平台化路径);
- 用 **Value Stream Management** 工具(Faros、LinearB、Jellyfish)端到端度量,而非只看 IDE 内指标;
- 用 DORA 7 项 capabilities 做差距审计。

### 三、强制 small batch + risk-based review

- 把 PR size 作为工程文化红线(Faros 数据:PR size +51% 直接推高 review 时间 +441%);
- 引入 risk-based PR routing(Morgan Stanley 模式):低风险自动合并、中风险 AI 预审、高风险人审;
- 31% 的 PR 在零 review 下合并是不可接受的红线——需在 CI 中强制最小 review 数。

### 四、按 Shore 框架分配维护预算

- 量化 AI 让 new code 提速的倍数 N;
- 强制把等量资源(N-1 倍的新代码工时)投入:refactoring、dependency upgrade、dead code 清理、test 加固、文档同步;
- 把"维护成本占比"作为季度工程回顾的一等指标。

### 五、SDD 工具选型的三条原则

1. **vendor-neutral 优先:** 优先 GitHub Spec Kit 等开源、可移植方案;锁定 Kiro 等深度集成某云的方案前评估退出成本。
2. **spec 由人主导:** spec 的编写与审批必须留在人类;AI 可辅助起草,但不能独自定稿。
3. **EARS 或等价结构化 notation:** 拒绝纯自然语言 spec;需求必须可测试、可追溯。

### 六、observability 与 feature flag 作为"上 AI 代码的前置条件"

- 在允许 AI 生成代码进入生产前,强制:(a) 完整 trace 覆盖、(b) feature flag 包裹、(c) 自动 rollback 能力、(d) incident runbook;
- 用 LogicMonitor 的 "tool consolidation → unified data → AI on top" 路径降低 observability TCO;
- 把 incident/PR 作为比 change failure rate 更敏感的早期预警指标(Faros: +242.7%)。

### 七、文化改造(最难、也最关键)

- 参考 Shopify:把"reflexive AI usage"写入 baseline expectation,把 AI 熟练度纳入 review;
- 参考 JPMorgan:集中化平台 + 治理先行,而非"先开放再收口";
- 参考 Anthropic:系统化 dogfooding + transcript 分析,用数据驱动流程演进。
