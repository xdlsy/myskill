# L6 — 度量与落地路径

> **本层定位**：在 7 层架构(L0–L6)中,L6 是"计分牌 + 路线图"——回答两个问题:**怎么客观度量端到端 AI 开发的产出?**与**怎么从买工具一步步走到可信的自主开发?**
>
> 核心论点:**端到端落地 ≠ 买 Copilot**。度量同样如此——开发者"感觉变快了"是 L6 中最不可信的信号。本层把度量体系的搭建与分阶段自主度的扩张绑在一起:每个阶段的"是否能进入下一阶段"必须由客观指标判定,而不是由开发者满意度或厂商 ROI 模型判定。

---

## 执行摘要

- **主观感受系统性失真**:METR 的 RCT 发现,经验丰富的开源开发者**预期 AI 让他们快 24%、事后仍自认快 20%,但客观上慢了 19%**(CI +2% 到 +39%)。屏幕录像显示用 AI 时 idle time 反而更多——"省力"被误读为"更快"。这是 L6 全部的出发点。(来源:[METR 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/))

- **同一个团队 8 个月后部分翻转**:METR 在 2026 年 2 月对原开发者复测得到 **18% 加速**(但 CI -38% 到 +9%,且因大量开发者拒绝参加"不能用 AI"的分组而产生严重 selection bias)。结论不是"AI 没用",而是**单一时点、单一人群的数字会随风转向,必须用连续、客观、多维的指标体系取代单点实验**。(来源:[METR 2026 update](https://metr.org/blog/2026-02-24-uplift-update/))

- **DORA 2024 的反直觉**:AI 采纳每提升 25%,**个人生产力 / flow / 满意度上升**,但**软件交付吞吐量下降 1.5%、稳定性下降 7.2%**——典型的"局部最优、全局变差"。2025 DORA 中吞吐量回正,但稳定性仍下降,印证"J-curve"。(来源:[DORA 2024](https://dora.dev/research/2024/dora-report/), [RedMonk analysis](https://redmonk.com/rstephens/2024/11/26/dora2024/))

- **必须同时跑两套指标**:(1) 流量/速度类(cycle time、churn、acceptance rate);(2) 结果/质量类(defect escape rate、change failure rate、MTTR、维护成本占比)。**任何只看一边都会被游戏化**——典型如 GitHub Copilot 的 ~30% acceptance rate 不能单独用作"成功"指标。

- **分阶段自主度是有"硬门"的**:Northflank 与 Gartner 数据显示 **88% 的企业 AI agent pilot 永远上不了生产**,Gartner 预测 2027 年前 40%+ agentic AI 项目被砍。原因不是模型不行,而是**没在第一阶段就建立 SSO / SIEM / secret scanning / PR gate / sandbox / license / IR 这 7 项治理控制**。(来源:[Northflank 2026](https://northflank.com/blog/enterprise-ai-coding-agent-deployment))

- **真实案例几乎都是"分阶段、且可回滚"**:JPMorgan 用内部助手得到 10–20% 效率提升([Reuters 2025](https://www.reuters.com/technology/artificial-intelligence/jpmorgan-engineers-efficiency-jumps-much-20-using-coding-assistant-2025-03-13/));Klarna 是反面教材——把客服 AI 数据(700–853 个 FTE)被错读为"研发效率",后又重新招人。(来源:[Fast Company](https://www.fastcompany.com/91468582/klarna-tried-to-replace-its-workforce-with-ai), [Customer Experience Dive](https://www.customerexperiencedive.com/news/klarna-reinvests-human-talent-customer-service-AI-chatbot/747586/))

- **既有多维框架仍是底座**:DORA(交付视角)、SPACE(五个维度)、DevEx(三条信号:反馈回路 / 认知负荷 / 心流)、DX Core 4(把前三者整合成 Speed / Effectiveness / Quality / Impact 四块)。AI 时代的关键不是另起炉灶,而是**给既有框架加一列"AI 来源代码占比 / agent 自主度等级"**。

- **L6 的最小可用形态**:Cycle Time 四段(Coding/Pickup/Review/Deploy)+ Code Churn(2-week 窗口)+ Defect Escape Rate + AI Acceptance Rate + PR Review Time + DORA 四指标,加上每阶段自主度的"进入/退出"门槛——这套组合已经足以避免 90% 的度量陷阱。

## 核心发现

### 发现 1:METR 证明了"主观感受是错的",但它本身也在演化

**原始研究(2025-07-10)**:
- 16 名经验丰富的开源开发者(平均在目标仓库 5 年、1500 次提交),来自平均 22k+ stars、1M+ 行代码的成熟项目(很多是编译器、库这类"纯软件")。
- 246 个真实 issue,随机分配到 "AI allowed" / "AI disallowed"。AI allowed 时主要用 **Cursor Pro + Claude 3.5/3.7 Sonnet**(当时的前沿模型)。
- 开发者按 $150/hr 报酬参与,自己上报完成时间,屏幕全程录像。
- **结果:用 AI 时完成 issue 慢 19%(confidence interval +2% to +39%)**。开发者事前预期会快 24%,事后仍相信自己快了 20%。69% 的人结束后继续用 AI。
- 作者列出 20 个可能解释,最终确认 5 个有证据(其中包括:开发者把时间花在清理 AI 生成的代码上;这些任务对资深开发者而言 AI 的边际收益很小;大型项目隐式规则多、AI 不擅长)。
- 录像显示用 AI 时 idle time 反而更多——作者推测这是"AI 让编码的认知负荷下降,容易多任务或放空,所以主观上感觉快"。

**对抗式核验**:这是一个**真随机对照试验**,样本虽小但统计上能拒绝零假设(作者用 clustered standard errors 处理同一开发者的多任务相关性)。它对**该人群**与**该任务类型**是可信的。

来源:[METR 2025-07-10](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)、[Sean Goedecke 的方法学评论](https://www.seangoedecke.com/impact-of-ai-study/)、[The Register 报道](https://www.theregister.com/software/2025/07/11/ai-coding-tools-make-developers-slower-study-finds/1143832)

**2026-02-24 的反转**:
- METR 用 late-2025 工具(Cursor + Claude Code 等)重做实验,共 **57 名开发者、143 个仓库、800+ 任务**。
- 原 16 名开发者中的 10 名复测得到 **18% 加速**(CI -38% to +9%);新招募的 47 名开发者得到 **4% 加速**(CI -15% to +9%)。
- **作者明确声明:这些数据不可信**——大量开发者拒绝参加"不能用 AI"的分组(降价到 $50/hr 加剧了这一偏差),30–50% 的开发者承认会主动避开提交那些"不给用 AI 就太痛苦"的任务。这意味着**真实的加速效应大概率更高,但这个实验无法测量**。
- 一个有趣的旁证:**约 4% 的 GitHub commits 已经由 Claude Code author**(METR 观察)。

来源:[METR 2026-02-24 update](https://metr.org/blog/2026-02-24-uplift-update/)

**可推广的度量教训**:
1. **主观自评与客观计时系统性偏离**:在这个 RCT 里差了 ~40 个百分点(自评 +20% vs 实测 -19%)。任何只靠问卷的 AI ROI 研究都要打折。
2. **能力曲线不是单调的**:同一群人 8 个月后从 -19% 翻到 +18%。**单时点度量无法回答"AI 是否值得"——必须连续度量**。
3. **selection bias 是度量的最大杀手**:入选开发者越依赖 AI,实验越难做。企业内做 A/B 也会遇到一样的问题——"不让我用 AI 我就不参加"。
4. **任务异质性被平均值掩盖**:METR 自己承认 5 类因素影响结果,因此要按任务类型分层度量,而不是看一个公司级均值。

### 发现 2:不度量客观指标就会被厂商数字洗脑

| 厂商常引用的数字 | 真实出处 | 陷阱 |
|---|---|---|
| "用 Copilot 快 55.8%" | Peng et al. 2023, 控制实验,任务=写一个 HTTP server ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/the-impact-of-ai-on-developer-productivity-evidence-from-github-copilot/), [arXiv 2302.06590](https://arxiv.org/abs/2302.06590)) | 单一 toy task,实验室环境,被试为学生/初级开发者 |
| "76% 开发者在用 AI" | 2024 DORA 报告([DORA](https://dora.dev/research/2024/dora-report/)) | 自报使用,不等于有效使用 |
| "AI 让生产力提升 55%" | GitHub Octoverse 2024 转引 Peng 论文([GitHub Blog](https://github.blog/news-insights/octoverse/octoverse-2024/)) | 同源循环引用 |
| "9.5–10.0 code health score" | 部分博客转述,无一手数据 | 来源不明,需警惕 |
| JPMorgan "效率提升 10–20%" | Reuters 2025-03,内部助手,数万名工程师([Reuters](https://www.reuters.com/technology/artificial-intelligence/jpmorgan-engineers-efficiency-jumps-much-20-using-coding-assistant-2025-03-13/)) | 公司自报、未公开方法学 |

**结论**:在企业内部,**唯一可信的数字是你自己的工程系统里产生的**——PR 周期、churn、change failure rate、defect escape、MTTR。厂商白皮书只能用作"假说",不能用作"证据"。

### 发现 3:DORA 2024 的"个体—组织悖论"是 AI 度量最重要的发现之一

按 DORA 2024 数据,**AI 采纳每提升 25%** 对应:
- **正面**:文档质量 +7.5%、代码质量 +3.4%、flow +2.6%、个人生产力 +2.1%
- **负面**:软件交付吞吐量 -1.5%、交付稳定性 -7.2%
- "有价值工作时间"反而 -2.6%——DORA 称之为 **Vacuum Hypothesis**(省下的时间被低价值任务吸走了)

来源:[DORA AI report](https://dora.dev/ai/)、[OpsLevel 总结](https://www.opslevel.com/resources/how-generative-ai-is-changing-software-development-key-insights-from-the-dora-report)、[RedMonk 分析](https://redmonk.com/rstephens/2024/11/26/dora2024/)

**这是 L6 必须直面的现象**:开发者个人层面的收益与团队/系统层面的损失并存。如果只度量开发者满意度(SPACE 的 S 维度),你会得出"AI 很成功";如果只度量交付稳定性(DORA 的稳定性),你会得出"AI 在拖后腿"。**结论依赖于你度量了哪一维**。

DORA 2025 已显示吞吐量回正,但稳定性仍承压——印证这是"J-curve"而非"AI 不行"。

### 发现 4:88% 的 agent pilot 上不了生产——失败不是模型,是治理

Northflank 引用 Gartner 与 McKinsey 数据:**88% 的企业 AI agent pilot 永远到不了生产**;Gartner 预测到 2027 年底 **40%+ 的 agentic AI 项目会被砍**;McKinsey 看到 2/3 企业试过 agent 但**不到 10% 做出了可衡量的价值**。

来源:[Northflank 2026](https://northflank.com/blog/enterprise-ai-coding-agent-deployment)

被砍的原因排序(Forrester 12-month negative-ROI 分析):**不清楚的成功标准(41%)、工具/数据访问不足(33%)、eval 覆盖漂移(26%)**。**没有一个被归因为"模型不够强"**。这反过来证明 L6(度量 + 落地)才是决定 L0–L5 投资能否兑现的关键层。

## 客观指标体系

> 设计原则:**"每一个指标都对应一种游戏化方式"**——所以指标要成组使用,且任何单一指标都不应直接挂钩 KPI / 奖金。

### 1. Cycle Time(端到端周期时间)

**怎么度量**(采用 LinearB 的四段分解,业界事实标准):

| 阶段 | 定义 | 健康基准 |
|---|---|---|
| **Coding Time** | 第一次 commit 到 PR 开启 | < 2–3 天 |
| **Pickup Time** | PR 开启到第一次评审活动 | 越短越好 |
| **Review Time** | 第一次评审活动到 PR 合并 | 取决于变更大小 |
| **Deploy Time** | PR 合并到生产部署 | 取决于部署频率 |

来源:[LinearB: How is cycle time calculated](https://linearb.helpdocs.io/article/0vif1ihmgc-how-is-cycle-time-calculated)、[LinearB Cycle Time Blog](https://linearb.io/blog/cycle-time)

**AI 场景下的陷阱**:
- AI 让 Coding Time 看起来缩短(commit 更快产出),但 Review Time 与 Pickup Time 经常**反而上升**——评审者要读更多行数、判断 AI 生成代码的正确性。
- LinearB 自己的数据:50% 的 PR 在生命周期里有 ≥50.4% 的时间处于 idle。AI 不解决 pickup——组织流程才解决。
- 当 AI agent 能直接开 PR 时,**Coding Time 趋近于 0**,会让 cycle time 看起来"飞快"——必须**单独标注 agent-authored PR**,不能与人写 PR 混算。

### 2. Code Churn(代码改动量 / 短期回写率)

**怎么度量**:最常见的是 GitClear 的定义——**作者提交后 14 天内被 revert 或修改的代码行占比**。

来源:[GitClear: Coding on Copilot](https://www.gitclear.com/coding_on_copilot_data_shows_ais_downward_pressure_on_code_quality)、[Visual Studio Magazine](https://visualstudiomagazine.com/articles/2024/01/25/copilot-research.aspx)

**关键发现**:GitClear 分析 2020–2023 年约 **153M 行代码变更**,发现 **2024 年 code churn 较 2021 年 pre-AI 基线预计翻倍**;同时"新增代码"和"复制粘贴代码"占比上升、"更新/删除/移动"下降——AI 生成的代码更像"短期外包"。

**陷阱——为什么 churn 上升未必是坏事**:
- **健康 churn**:重构、技术债清理、AI 加速了"好的重写";
- **不健康 churn**:bug 修复、回滚、AI 生成的代码没经过评审就合并又被改;
- 区分方法:**把 churn 按 commit 类型拆开**(refactor / bugfix / feature / revert),不要看一个总值。
- 还要叠看**Code Age**(新代码存活时长)与 **Moved Code**——这三者一起才反映可维护性。

### 3. Defect Escape Rate(缺陷逃逸率)

**公式**:**DER = (生产环境发现的缺陷数 / 所有阶段发现的缺陷总数) × 100%**

来源:[Opsera DER Guide](https://opsera.ai/knowledge-base/change-and-quality-metrics/what-is-defect-escape-rate-der-and-why-it-matters-a-comprehensive-guide/)、[Stackify](https://stackify.com/measure-defect-escape-rate/)、[QASphere](https://qasphere.com/blog/qa-metrics-guide/)

**AI 场景下的特殊价值**:
- 这是**最直接衡量"AI 写的代码到底有没有制造更多线上事故"**的指标。
- 与 DORA 的 **Change Failure Rate** 互补:CFR 看每次部署是否失败,DER 看漏到生产的缺陷比例。
- 陷阱:DER 高可能意味着"测试覆盖差"(漏报)而不是"代码质量差";DER 低可能意味着"测试太多导致开发慢"。**永远要和"测试覆盖率 / 测试执行时间"一起看**。

### 4. AI Acceptance Rate(AI 代码接受率)

**业界基准**:GitHub Copilot 长期在 **~30% 建议接受率**(其中 line-level acceptance 约 20%),ZoomInfo 的 arXiv 论文给的是 **33% 建议接受、20% 行级接受**,开发者满意度 72%。被接受的代码**约 88% 会进入最终提交**。

来源:[arXiv ZoomInfo Study](https://arxiv.org/html/2501.13282v1)、[Quantum Run Stats](https://www.quantumrun.com/consulting/github-copilot-statistics/)、[SecondTalent](https://www.secondtalent.com/resources/github-copilot-statistics/)

**陷阱**:
- **高 acceptance 不等于高效率**——开发者可能机械地按 Tab 接受,然后回头大改。
- 这个指标会被 IDE 厂商"刷":把模型调得更激进、建议更多,acceptance 比例就上去,但产出价值未必。
- 必须看**"被接受且未被 14 天内修改"的留存率**,而不是单看 acceptance。
- agent 时代这个指标需要扩展为 **"agent PR 的合并率 / 合并后 revert 率 / 合并后修改率"**。

### 5. 审查时间(PR Review Time)

**为什么单独列**:这是 cycle time 的子项,但在 AI 时代它**最容易被低估**。
- DORA 2024 暗示了 AI 让 review 负担增加(churn 上升、PR 体积上升)。
- LinearB 早期数据:PR 平均要等 **4+ 天**才会被 pickup;**50%+ 的 PR 寿命里有 50%+ 时间是 idle**。
- AI agent 让 PR 体积爆炸(10x–100x,见 [Northflank](https://northflank.com/blog/enterprise-ai-coding-agent-deployment)),人审瓶颈会指数级放大。

来源:[LinearB Review Time Study](https://linearb.io/blog/why-estimated-review-time-improves-pull-requests-and-reduces-cycle-time)、[LinearB Pickup Time](https://linearb.io/blog/pull-request-pickup-time)

### 6. 维护成本占比(Maintenance Cost Ratio)

**怎么度量**:`用于修复缺陷 + 重构 + 维持现有系统运行`的工程时间 / 总工程时间。这一项在 DORA 之外的工程经济学体系(如 SQALE、技术债度量)中长期存在。

**AI 场景下的变化**:
- 如果 AI 把"新增功能"做快了,但维护成本占比上升,说明**净效益可能为负**——你只是把成本推到了未来。
- GitClear 的 churn 翻倍预测,本质就是维护成本上升的先兆。
- **建议每个季度把这个比例和"AI 生成代码占比"做散点图**——如果两者同向上升,就是危险信号。

### 与既有框架的关系

#### DORA(4 个交付指标)
- 部署频率 (Deployment Frequency)
- 变更前置时间 (Lead Time for Changes)
- 变更失败率 (Change Failure Rate)
- 平均恢复时间 (Mean Time to Restore / MTTR)

**与 AI 度量结合**:
- DORA 2024 已经给出**关键经验数据**:AI 采纳 +25% → 吞吐 -1.5%、稳定性 -7.2%——所以 DORA 是**最早能反映 AI 副作用的现成框架**,企业无需自己重新发明。
- Larridin 等分析师提出当 30–70% 代码由 AI 生成时,DORA 的隐含假设(部署频率 ↔ 人力上限)会失效——需要**对 DORA 指标按"人写 vs agent 写"分桶**。
- DORA 2025 已经把 throughput 翻回正值,但 stability 仍承压,印证 J-curve——所以**单年数据绝不能下结论**。

来源:[DORA AI](https://dora.dev/ai/)、[DORA 2024 Report](https://dora.dev/research/2024/dora-report/)、[Larridin: Why DORA metrics break in the AI era](https://larridin.com/developer-productivity-hub/why-dora-metrics-break-ai-era)

#### SPACE(5 个维度)

来自 Forsgren 等 2021 年的 ACM Queue 论文。五个维度:
- **S**atisfaction and well-being
- **P**erformance(outcome)
- **A**ctivity(output count)
- **C**ommunication and collaboration
- **E**fficiency and flow

来源:[ACM Queue: The SPACE of Developer Productivity](https://queue.acm.org/detail.cfm?id=3454124)、[GitHub Enterprise Blog](https://github.blog/enterprise-software/devops/measuring-enterprise-developer-productivity/)

**与 AI 度量结合**:SPACE 的价值在于**强制多维**——避免只用 A(activity,例如 commit 数 / PR 数)这种最容易被 AI 刷高的维度。AI 时代应在每个维度下加 AI 子项,例如:
- A: AI 生成代码行数 / agent PR 数
- E: AI 工具打断 flow 的次数(被建议干扰)
- C: agent 与人 review 的往返次数

#### DevEx(3 条信号)

来自 Abi Noda、Margaret-Anne Storey、Nicole Forsgren 2023 年 ACM Queue 论文:
- **Feedback loops**:多快能验证一次改动(CI、code review、deploy)
- **Cognitive load**:任务的心理负担
- **Flow state**:能否持续专注

来源:[ACM Queue: DevEx](https://queue.acm.org/detail.cfm?id=3595878)、[InfoQ: DevEx metrics framework](https://www.infoq.com/articles/devex-metrics-framework/)、[DX DevEx Guide](https://getdx.com/blog/developer-experience/)

**与 AI 度量结合**:DevEx 是**主观 + 客观结合**的典范——定量(反馈时间)加定性(问卷)。METR 的发现正好证明:**只用定性 / 主观自评会被 AI 误导**,DevEx 把定量反馈回路纳入恰好弥补。

#### DX Core 4(2025 年整合框架)

DX(Abi Noda 创立的公司)在 2025 年 1 月推出 Core 4,把 DORA + SPACE + DevEx 整合成四个高阶维度:
- **Speed**(速度)
- **Effectiveness**(有效性)

## 分阶段自主度落地路径

> 设计原则:**自主度不是"买更贵的工具就升一级"——它是"eval 通过率 + 治理控制成熟度 + 历史事故率"三个变量的函数。**

### 阶段总览

| 阶段 | 模式 | 人在环里的位置 | 进入条件 | 退出条件 | 典型时长 |
|---|---|---|---|---|---|
| **0. Copilot** | 行内补全 | 人写、AI 补 | 已有 IDE 接入 | acceptance rate 稳定 4 周以上 | 1–3 个月 |
| **1. Assistant** | 带人审的 agent | AI 起 PR、人审 | 阶段 0 + PR gate 全部就位 | agent PR merge rate ≥ 人写 PR 的 80% | 3–6 个月 |
| **2. Gated Autonomous** | 带 gate 的自主 agent | 自动跑、人在关键点审批 | 阶段 1 + eval 覆盖 ≥ 70% | DER / MTTR 不劣化 2 个季度 | 6–12 个月 |
| **3. Expanded Autonomous** | 扩大自主 | 仅异常才找人 | 阶段 2 + 多个领域 eval 持续达标 | (持续运营,不退出) | 持续 |

### 阶段 0: Copilot(补全)

- **模式**:行内补全 + chat(IDE 内 / Slack 内)。AI 不开 PR。
- **进入条件**:SSO 接入、数据驻留满足合规、开发者完成 1 小时 onboarding。
- **度量重点**:Cycle Time 全四段、Acceptance Rate(作为健康指标,**不作 KPI**)、SPACE 的 S 与 E 维度。
- **退出条件(进入阶段 1 的"门")**:
  - Acceptance rate 连续 4 周稳定(不强制上限,只看稳定性);
  - Cycle Time 没有显著恶化(用 DORA throughput 检验);
  - DER 与 change failure rate 不上升;
  - 开发者经过培训能识别 AI 错误输出(可加一个简单测试);
- **风险**:**误把"开发者用得多"当成"产出更好"**——METR 已经证明这两件事可以反着走。
- **典型时长**:1–3 个月。重点不是"用得多",是"建立 baseline"。

### 阶段 1: Assistant(带人审的 agent)

- **模式**:AI agent(Cursor agent mode / Claude Code / Codex / Jules 等)能独立完成一个 issue 并开启 PR,**但必须人审才能合并**。
- **进入条件**(Northflank 七项控制的最小子集):
  - **SSO**:每个 agent session 映射到具名人类身份;
  - **SIEM-connected audit logging**:每次 file access、shell command、PR 创建、API 调用都进 SIEM;
  - **Secret scanning on agent PRs**(强制必检,merge 前阻断);
  - **PR policy gates**:agent PR 走与人 PR 完全一样的 owner review / coverage / lint / SAST,**没有任何 pilot 豁免**;
  - **Sandbox isolation**:agent 执行环境微 VM 隔离;
  - **License governance**:agent 生成的代码扫开源 license;
  - **Incident response runbooks**:agent 导致事故时谁被 page、如何 revoke。
- **度量重点**:
  - agent PR 的 merge rate、合并后 revert 率、合并后 14 天内的修改率;
  - 人审 review time 的变化(关键!**很多人在这一步发现 review time 反而上升**);
  - cycle time 拆开看 Coding vs Review(Coding ↓ 而 Review ↑ 是典型 AI 现象);
  - DER、change failure rate 不劣化。
- **退出条件(进入阶段 2 的"门")**:
  - agent PR merge rate ≥ 人写 PR 的 80%;
  - 合并后 14 天修改率不显著高于人写 PR;
  - DORA throughput 不下降;
  - 已有针对该领域的 eval 集(可参考 RigorBench 等公开基准的思路)。
- **典型时长**:3–6 个月。

来源:[Northflank Enterprise AI Coding Agent Deployment](https://northflank.com/blog/enterprise-ai-coding-agent-deployment)、[GAIE: Graduated Human Oversight arXiv](https://arxiv.org/html/2606.22484v2)

### 阶段 2: Gated Autonomous(带 gate 的自主 agent)

- **模式**:agent 自动跑、自动测试、自动 deploy 到 staging,**关键点(生产 deploy、删除数据、对外发送、改 config)需要人审批**。
- **进入条件**:
  - Eval 覆盖率 ≥ 70%(关键路径有自动测试);
  - 阶段 1 的所有治理控制 + IR runbook 全部演练过至少一次;
  - 有"agent 行为基线"——能检测异常(例如 agent 突然开始删大量文件);
- **度量重点**:
  - **DER** 是这一阶段最重要的指标——自主度上升,**测试与 eval 必须把守漏到生产的缺陷**;
  - **MTTR**——agent 自己 fix bug 的能力(注意区分"agent 引发 vs agent 修复");
  - 每千次 agent action 的人介入次数(human escalation rate);
  - 信任分数 τ(SOSA / HAIG 论文提出,见下文"实践/框架")。
- **退出条件**:
  - DER 与 MTTR 连续 2 个季度不劣化;
  - Human escalation rate 单调下降;
  - 多个领域的 eval 通过率持续达标;
  - 法务、安全、合规都签字(这是治理 gate,不是技术 gate)。
- **典型时长**:6–12 个月。

### 阶段 3: Expanded Autonomous(扩大自主)

- **模式**:agent 在已批准的领域内自主全流程,**只在异常 / 超阈值时找人**。
- **进入条件**:阶段 2 全部门通过 + 有专责 owner(56% 成功 scale agent 的企业有 dedicated owner,[Northflank](https://northflank.com/blog/enterprise-ai-coding-agent-deployment) 引用)。
- **度量重点**:稳定运营、持续 eval 漂移监控、agent 行为异常检测、定期回滚演练。
- **退出**:不退出——这是稳态。每升一级自主度都先在子领域里重走 0→2 的循环。

### 治理控制清单(Northflank 七项)

| # | 控制 | 必要性 |
|---|---|---|
| 1 | SSO(SAML / OIDC + SCIM) | 必须 |
| 2 | Audit logging → SIEM | 必须 |
| 3 | Secret scanning on agent PRs | 必须 |
| 4 | PR policy gates(无 pilot 豁免) | 必须 |
| 5 | Sandbox isolation(microVM) | 必须 |
| 6 | License governance | 必须 |
| 7 | Incident response runbooks | 必须 |

> Northflank 引用 Forrester:agent 部署 12 个月内出现负 ROI 的根因排序是**不清楚的成功标准(41%)、工具/数据访问不足(33%)、eval 覆盖漂移(26%)**——没有任何一项是"模型不够强"。这反过来证明 L6 才是投资能否兑现的关键。

## 风险与陷阱

### 陷阱 1:把厂商数字当结论

55.8% 来自一个写 HTTP server 的实验室任务;GitHub 主动营销这个数字 5+ 年。在企业内做决策前,**要求厂商提供在你工作负载下的 POC 数据**,并要求自己 run 一段盲测。

### 陷阱 2:把开发者满意度当 KPI

METR 已经证明满意度可以和真实产出**反向**。满意度**用来发现 adoption 阻力**,不用来证明 ROI。

### 陷阱 3:用 acceptance rate 作 KPI

厂商最容易刷这个数(模型激进一点、建议多一点,acceptance 比例就上)。改用"**被接受且 14 天未被修改**"的留存率。

### 陷阱 4:只看吞吐不看稳定性

DORA 2024 的核心反直觉就是吞吐与稳定性会**反向**(AI 让 throughput 短期下降、stability 显著下降)。**必须同屏看 DORA 四指标**,且至少观察 2 个季度。

### 陷阱 5:把 cycle time 平均值当真相

AI agent 写 PR 速度极快,会把 Coding Time 拉到 0,但 Review Time 与 Pickup Time 经常**上升**。**必须看四段分解**而不是均值,且**按 agent PR vs 人 PR 分桶**。

### 陷阱 6:不区分"AI 加速 vs AI 替代"

Klarna 的教训:客服 AI 顶替 700+ 客服岗位是"替代",**与研发 AI 提效是两件事**。在很多外部报道里这两件事被混为一谈,导致企业错估研发 AI 的实际产出。Klarna 后来重新招人([Customer Experience Dive](https://www.customerexperiencedive.com/news/klarna-reinvests-human-talent-customer-service-AI-chatbot/747586/))。

### 陷阱 7:单时点度量

METR 8 个月内从 -19% 翻到 +18%。**任何只用一个时点的 ROI 计算都是错的**。要有连续 dashboard 而不是季度 PPT。

### 陷阱 8:agent pilot 没有 exit criteria

Gartner / McKinsey 数据:88% pilot 永远上不了生产,40%+ 项目被砍。**每个 pilot 启动时就要写好 exit criteria 与时间盒**,否则会无限期拖延或被静默砍掉。

### 陷阱 9:治理控制后置

Northflank 的关键建议:**治理控制不是 GA 阶段才补的事**——必须从阶段 0 就建好。SSO / audit log / secret scan / PR gate / sandbox 这些**后置会让 80% 的 pilot 在审计时被砍**。

### 陷阱 10:把 eval 当一次性

agent 的能力随着模型升级会变(从 Claude 3.5 → 3.7 → 4 短短一年)。**eval 必须随模型版本演进**——Forrester 把 "drift in evaluation coverage"(26%)列为 agent 失败前三根因。

## 给企业的落地建议

1. **先建度量,再买工具**:在引入任何 AI 编码工具之前,先把 DORA 四指标、Cycle Time 四段、DER、churn 这套 dashboard 跑起来,做 4 周基线。**没有 baseline 的 ROI 都是谎话**。

2. **拒绝单点实验,接受连续面板**:把 METR 式的 RCT 思想内化——单点实验数字会翻转,只有连续面板才能看出趋势。每个季度与上一季度比,而不是与"AI 出现之前"比。

3. **永远双轨度量**:开发者主观(SPACE 的 S、DevEx 的问卷) + 系统客观(DORA、churn、DER)。**两套数都要看,任一套单独都不能下结论**。

4. **从阶段 0 开始就把治理控制建好**:SSO / SIEM / secret scan / PR gate / sandbox / license / IR 这七项在阶段 0 完成就够,不要拖到 GA。Northflank 数据显示**56% 成功 scale 的企业都有 dedicated owner**——任命一个"AI 工程 owner"。

5. **每阶段写"进入/退出"门**:把它写进 policy——例如阶段 1 到阶段 2 的过渡必须 DER 连续 2 季度不劣化 + eval 覆盖 ≥ 70%。**让指标,而不是 enthusiasm,驱动自主度扩张**。

6. **标注每一行代码的来源**:agent / 人 / 协作。没有这个标签,你所有的指标都会被混合,**无法回答"AI 让我们更好还是更差"**。

7. **警惕厂商白皮书**:GitHub 55.8%、McKinsey 46%、JPMorgan 20%——这些都是**自报、单场景、未公开方法学**的数字。当 hypothesis 听,不当 evidence 用。

8. **小步快上,允许回滚**:每升一级自主度都先在 1 个低风险 repo / 1 个团队试,**设时间盒(4–6 周)**,不达标就回退到上一阶段。Klarna 的教训就是"一刀切全面 AI 化"必然回退。

9. **把"AI 治理"提升到与"安全合规"同等级别**:Audit log、IR runbook、年度演练——把 agent 当成一个能 commit 代码的"远程外包团队"来管。

10. **把 METR 的 5 个解释变成 5 个度量维度**:开发者过度乐观 / 把时间花在清理 AI 代码 / 任务太熟悉没空间 / 大型项目隐式规则多 / AI 工具学习曲线。**每个解释都对应一个可监控的工程信号**(清理时间、任务类型分布、PR 大小、context switch 次数、Cursor 等工具使用时长)。
