# L2 — 验证与质量护栏

> **核心论点**:"端到端落地 ≠ 买 Copilot"。AI 让"写代码"变得廉价,但让"信任代码"变得昂贵。本层(L2)是整个 7 层体系的"心脏"——它决定 AI 产出的代码能否安全地自动合入、自动发布、自动运维。本报告聚焦多层验证栈、供应链威胁、AI 互审、eval 平台、CI/CD gate 实践与厂商盘点。

---

## 执行摘要

- **两条关键数字对抗式核验结果**:(1)"AI 代码约 40% 含漏洞"——**基本属实**,源自 NYU 的 Pearce et al. 论文 *Asleep at the Keyboard?*(IEEE S&P 2022),89 个场景、1,692 个程序中约 40% 存在可被攻击者利用的 bug 或设计缺陷,但这是 **2021 年的 Copilot**,**针对 MITRE Top-25 CWE**,不应被当作所有现代模型的当前水平。(2)"约 20% AI 代码引用不存在的包"——**部分属实但常被误读**,源自 UTSA/Virginia Tech/Oklahoma 的 Wijewickrama et al. 论文(arXiv:2406.10279),真实数字是 **商业模型 5.2%、开源模型 21.7%、总体 19.7%**(440,445/2.23M),"20%"主要归因于开源模型;GPT-4 Turbo 仅 **3.59%**,CodeLlama 7B 高达 **26.12%**。

- **单一防线必败**:SAST 工具业界平均误报率 **40–60%**,某学术评测中 7 款 SAST 仅检出 **12.7%** 的真实漏洞;Semgrep 在 DryRun 基准中检出率约 **46%**,SonarQube 约 **19%**。任何"装一个 SAST 就够了"的想法都不成立——必须分层。

- **slopsquatting 已从理论威胁转为现实威胁**:2024–2025 年 Socket、Snyk、Trend Micro、Unit 42 等多家记录了攻击者按 AI 高频幻觉的包名在 npm/PyPI 预注册恶意包的真实模式(`starlette-reverse-proxy` 即典型);`vulcan.io`/Lanyado 2023 年已发布 PoC。开源模型幻觉率高 + 幻觉可重复(58% 在 10 次重试中复现)使该攻击成本极低。

- **AI 审 AI 有用但不是银弹**:Anthropic 2026-03-09 发布的 **Claude Code Review** 是多 agent 并行评审系统,Anthropic 内部数据显示大 PR(>1000 行)在 84% 情况下能找到 bug(平均 7.5 个),误标率<1%,但单次评审约 $15–25、平均耗时 20 分钟,且 **Cloud Security Alliance 已披露其 GitHub Action 存在 prompt-injection 漏洞**——第三方 AI 验证仍可被绕过,不能作为唯一防线。

- **eval 平台是度量基线**:公开基准(SWE-bench、HumanEval、EvalPlus)与真实业务表现存在巨大鸿沟——有团队在 SWE-bench Verified 上 89 分但内部 eval 仅 38 分。企业必须建立**自有业务 eval 集**,工具栈推荐 OpenAI Evals / Inspect AI(AISI)/ EvalPlus / Braintrust + LLM-as-judge。

- **CI/CD 分层 gate 是落地形态**:推荐 **5 层栈**(lint/typecheck → SAST+secrets → SCA → 测试覆盖 → agentic/行为测试),按风险路径分级强制;先用 observe 模式,再 enforce;快门(lint/type)<3 分钟必须先跑。

- **高保证领域需形式化方法**:航空航天、医疗、汽车、金融核心系统应叠加 TLA+(系统级协议)/Coq/Lean(代码级证明),并出现"AI 同时生成代码与形式化规约"的新范式。

## 核心发现(Findings,带证据与 URL)

### 发现 1:40% 漏洞率被广泛误引,真实出处是 2021 年 Copilot + MITRE Top-25

**证据**:NYU Center for Cybersecurity 官方新闻稿原文:"The researchers drew their conclusion after creating **89 potential scenarios and having CoPilot output 1,692 programs**. When these programs were reviewed, **about 40 percent included bugs or design flaws that could be exploited by an attacker**." 来源:Hammond Pearce, Baleegh Ahmad, Benjamin Tan, Brendan Dolan-Gavitt, Ramesh Karri, *Asleep at the Keyboard? Assessing the Security of GitHub Copilot's Code Contributions*,IEEE Symposium on Security and Privacy (S&P) 2022。

**对抗式核验要点**:
- 该数字是 **2021 年 6 月发布的 GitHub Copilot**(基于 Codex 初代),**不是**当前的 GPT-4o/Claude Sonnet 4.5/Gemini 2.5 类模型。许多引用者把它说成"AI 代码"的当前水平,这是**误导**。
- 论文方法是对每个场景映射 **MITRE Top-25 CWE**,因此"40%"特指这 25 类已知弱点,不等于"任意 bug"。
- 同期 Stanford 的 Perry et al.(CCS 2023)*Do Users Write More Insecure Code with AI Assistants?* 是另一篇常被混淆的研究——它发现**使用 AI 助手的开发者**写出的代码更不安全,而非 AI 本身的产出率。

**来源**:
- https://cyber.nyu.edu/2021/10/15/ccs-researchers-find-github-copilot-generates-vulnerable-code-40-of-the-time/
- https://arxiv.org/abs/2108.09293(Pearce et al., *Asleep at the Keyboard?*)
- https://ee.stanford.edu/dan-boneh-and-team-find-relying-ai-more-likely-make-your-code-buggier(Stanford 不同研究的对照)
- https://techcrunch.com/2022/12/28/code-generating-ai-can-introduce-security-vulnerabilities-study-finds/

### 发现 2:"20% 幻觉包"是总体均值,商业模型实际仅 5.2%

**证据**:Wijewickrama et al., *We Have a Package for You! A Comprehensive Analysis of Package Hallucinations by Code Generating LLMs*(arXiv:2406.10279,UTSA + Oklahoma + Virginia Tech)。原始数字:
- **576,000 段代码、16 个 LLM、2.23M 个推荐包**
- **440,445(19.7%)为幻觉,205,474 个唯一幻觉包名**
- **商业模型 5.2% / 开源模型 21.7%**(开源约 4×)
- 最低 **GPT-4 Turbo 3.59%**,最高 **CodeLlama 7B(Python)26.12%**
- **58% 的幻觉在 10 次重试中复现**——这是攻击可行性的关键
- **81% 的幻觉包名仅由单一模型产生**——攻击需针对具体模型

**对抗式核验要点**:
- "20% AI 代码引用不存在的包"这一说法**方向正确但归因常错**——它把开源模型的 21.7% 当作所有 AI 的代表,而企业实际多使用商业 API(GPT-4o/Claude),其幻觉率在 **3.59–5.76%** 量级。
- 论文还指出 Lanyado(2023)早期博客估算 GPT-3.5/GPT-4 幻觉率为 24.2%/22.2%,**比严格方法高出 4–6 倍**——说明早期"流行说法"被夸大。

**来源**:
- https://arxiv.org/html/2406.10279v3
- https://www.usenix.org/publications/loginonline/we-have-package-you-comprehensive-analysis-package-hallucinations-code
- https://vulcan.io/blog/ai-hallucinations-package-risk(Lanyado/Vulcan 早期 PoC)

### 发现 3:slopsquatting 已从"理论"变为活跃攻击向量

**机制**:LLM 幻觉出看似合理但不存在的包名 → 攻击者监控/重放 AI 输出获得候选名 → 在 npm/PyPI 预注册同名恶意包 → 开发者或 autonomous agent 信任 AI 输出并 `pip install` → 恶意代码进入依赖链。

**已公开的真实/PoC 证据**:
- `vulcan.io`(Lanyado,2023)发表过 PoC,证明发布幻觉包后被实际下载并进入其他包依赖链(论文 Section 2.1 引用)。
- Trend AI Security 与 Endor Labs 记录了 `starlette-reverse-proxy` 这类典型幻觉依赖名,攻击者可照名注册。
- 2025-08 The Hacker News:`termncolor`、`colorinal` 等恶意 PyPI 包(被下载 884 次)利用 DLL 侧加载、持久化与 C2。
- SafeDep:针对 TanStack、Mistral AI 的协调攻击,**400+ npm 包版本 + ≥2 个 PyPI 包**被污染(注:此事件含多种攻击向量,slopsquatting 是其中之一)。
- Socket、Snyk、FOSSA、Aquilax、Cloudsmith 均已发布 slopsquatting 专题。
- Palo Alto Unit 42 将该思路扩展到域名——"Phantom Squatting",攻击者注册 AI 幻觉的域名。

**缓解措施(论文验证有效)**:
- **RAG**(检索增强生成,把 top-20k 合法包向量注入 prompt):DeepSeek 16.14%→12.24%、CodeLlama 26.28%→13.40%。
- **Self-refinement**(模型自检合法/非法):DeepSeek 降到 13.04%。
- **Fine-tuning**:DeepSeek 降到 2.66%、CodeLlama 到 10.27%(但 HumanEval 质量下降)。
- **Ensemble**:DeepSeek 2.40%、CodeLlama 9.32%。
- **工程层**:SCA 扫描 + 私有镜像/allowlist + 安装前校验包在注册表的"年龄/下载量/维护者"信号 + Socket 类 AI 包分析。

- https://www.trendaisecurity.com/en-us/resources-insights/research/slopsquatting-when-ai-agents-hallucinate-malicious-packages

### 发现 4:AI 审 AI——Claude Code Review 的实战数据漂亮,但有结构性与安全性局限

**产品现状**:
- **Anthropic Claude Code Review**(2026-03-09 发布,Teams/Enterprise):多 agent 并行,聚焦**逻辑错误**(刻意不做样式/风格以压低误报),可在云端按 PR 触发,平均 **20 分钟、$15–25/次**,管理员可设月度上限。Anthropic 内部:实质性 review 评论占比从 16%→**54%**,>1000 行 PR 在 **84%** 情况下找到 bug(平均 7.5 个),误标率 **<1%**。它**不会自动 approve PR**——人类仍是最后闸门。
- **GitHub Copilot Code Review**(2025-10-28 公开预览更新):已混合 LLM detection + agentic tool calling + 确定性工具(ESLint、CodeQL),文档承认在大型/复杂 PR 上覆盖有限。
- **Claude Code Security**:扫描全代码库的安全 bug,与 Code Review 互补。
- 其他:CodeRabbit、Qodo Merge、Greptile、Cursor、DryRun Security、Qodo(原 CodiumAI)。

**结构性局限**:
- **同一模型家族的"互审"有同源盲点**:论文显示 81% 的幻觉包仅由单一模型产生,即每个模型有自己的"系统性错误指纹",一个 AI 审自己(或近亲)会漏掉自己的系统性缺陷。
- **第三方 AI 验证可被绕过**:Cloud Security Alliance 已披露 Anthropic Claude Code Security Review GitHub Action 存在 **prompt-injection** 漏洞——攻击者在 PR 描述/被审代码中注入指令即可影响审查结论,把 AI reviewer 变成攻击者代言人。
- **AI reviewer 的"看起来很认真"会制造虚假安全感**:GitHub 社区与 Reddit 多个讨论指出,团队易过度依赖自动评审而跳过人工,放过架构级/业务逻辑级问题。
- **成本/延迟**:20 分钟/$20 对 hot path 不可接受,需选择性触发(高风险路径)。

### 发现 5:公开 eval 基准与真实业务表现存在巨大鸿沟——必须建内部 eval

**关键警示案例**:"The right agent for us scored **73% on SWE-Bench Verified** and **81% on our internal eval**. The 'wrong' agent was **89% on SWE-Bench** and **38% on our internal eval**."——SWE-bench 高分反而对应业务低分。arXiv:2506.12286(*The SWE-Bench Illusion*)进一步指出部分高分来自**记忆**而非推理,且存在数据污染。

**公开基准谱系**:
- **HumanEval**(OpenAI 2021,164 题)——功能正确性 pass@1,适合快速 sanity check。
- **EvalPlus**(NeurIPS 2023,被引 2300+ 次)——给 HumanEval 加海量自动测试用例,揭露"看起来对"实则错。
- **SWE-bench / SWE-bench Verified**(普林斯顿,真实 GitHub issue)——当前公认黄金标准,但记忆/污染问题已被研究。
- **LiveCodeBench / CodeClash**——抗污染的新一代基准。
- **Senior SWE-Bench**(Snorkel.ai)——长时程、真实工程任务。

**内部 eval 工具栈**:
| 工具 | 定位 | 出处 |
|---|---|---|
| OpenAI Evals | 通用 LLM eval 框架,带 registry | https://github.com/openai/evals |
| Inspect AI(UK AISI + Meridian) | 前沿模型安全/能力评估,可复现 | https://inspect.aisi.org.uk/ |
| EvalPlus | 代码生成功能正确性增强测试 | https://github.com/evalplus/evalplus |
| Braintrust | 端到端 eval + 可观测性 + CI 集成,支持 autoevals/LLM-as-judge/自定义代码 | https://www.braintrust.dev/ |
| Datadog LLM Observability / LangSmith / Helicone / Arize Phoenix | 生产 eval 与监控 | 多家 |

**落地建议**:用 EvalPlus 风格把内部业务题升级为"严格测试";用 Inspect AI 做安全/越权 eval;用 Braintrust/LangSmith 接 CI 做回归;LLM-as-judge 只作辅助,必须有人工 spot-check 校准。

### 发现 6:CI/CD 分层 gate 是把上述能力工程化的落地形态

**5 层栈参考(Autonoma 提出,可直接落到 GitHub Actions)**:

| Layer | 拦截目标 | 关键工具 | CI 耗时 | 强制级别 |
|---|---|---|---|---|
| 1. Lint/Format | 死代码、幻觉 import、风格漂移 | ESLint/Prettier/Biome | ~1 min | Required |
| 2. Type Check | 类型漂移、`any` fallback | TypeScript `--strict` | ~2 min | Required |
| 3. Security Scanning | 硬编码 secrets、SQL 注入、不安全默认值 | Semgrep + Gitleaks + npm audit | ~3 min | Required |
| 4. Test Coverage | 未测试的新代码、回归 | Jest/Vitest + `--changedSince` | ~5 min | Required |
| 5. Agentic/行为测试 | 端到端行为回归、auth 缺口 | Autonoma/CodeRabbit + 部署 preview | ~10 min | Recommended |

**关键编排原则**:
1. **快门先跑**:lint+typecheck <3 分钟内 fail-fast,避免浪费昂贵的 agent 跑已知坏 PR。
2. **分级强制**:全部 PR 强制 1–2 层;`src/auth/**`、`src/payments/**` 等高风险路径才强制第 5 层。
3. **observe → enforce**:第一周只跑不强卡、调规则;第二周开始 enforce。
4. **AI reviewer 插在 2–3 层之间**:做 diff 级逻辑审查,作为静态扫描的补充而非替代。

**头部企业/平台公开实践**(注意:Google、Netflix 等未公开详尽内部 AI gate 细节,以下为公开材料):
- **Microsoft**:CI/CD Pipeline Guide 强调 build-deploy 各阶段 gate;CodeQL/GuardDog/SmartSuppression 等用于 GitHub Advanced Security。
- **GitHub 自身**:Advanced Security 提供 CodeQL(SAST)、 Dependabot(SCA)、Secret Scanning 三件套,可作 required check;Copilot code review 作为"评审助手"叠加。
- **ARMO**:提出 **three-tier decision framework**(per-layer gate 决策)。
- **Snyk/Checkmarx/Cycode/Sonar**:均把 SAST+SCA+secrets+IaC 打包成 ASPM 平台,Cycode 明确主张"扫描必须是 CI/CD 每次运行的强制自动步骤"。
- **Opcito**:5 层 CI/CD——SAST、SCA、DAST + LLM adversarial 测试套件。
- **OX Security**:主张 ASPM 整合,批评"孤立扫描代码/依赖而无 build/runtime 上下文"的点工具。

## 多层验证栈详述(按层)

### 层 A:静态分析与 Lint
- **目的**:在 ~1 分钟内拦截幻觉 import、死代码、类型漂移、风格漂移。
- **为什么对 AI 代码特别重要**:AI 常生成"两份同函数都留在文件里"、unused import,以及被 `any` 掩盖的类型错误;`--strict` + `--max-warnings 0` + changed-files 限定是性价比最高的两步。
- **工具**:ESLint、Prettier、Biome、Ruff(Python)、golangci-lint。

### 层 B:SAST(静态应用安全测试)
- **现状与真相**:业界平均误报率 **40–60%**(Autonoma);DryRun 基准中 **Semgrep 检出率 ~46%、SonarQube ~19%**;学术研究:7 款 SAST 工具仅检出 **12.7%** 真实漏洞(Reddit r/cybersecurity 引用研究)。
- **AI 时代的演进**:**AI SAST / ASPM**(Wiz、Augment Code、Aikido、Arnica、Checkmarx One、Snyk Code、GitHub CodeQL)用 LLM 做 taint 分析、跨文件/跨服务的多跳注入路径、业务逻辑缺陷——单文件扫描漏掉的,AI SAST 可补。
- **关键局限**:仍无法替代运行时验证(Invicti 主张 AI 代码必须叠加 DAST/IAST/runtime)。
- **建议**:用 Semgrep(CI 快、规则可写)+ CodeQL(语义深)+ 一个 AI SAST(如 Snyk Code/Checkmarx One)做交叉覆盖,把规则调到"AI 常产模式"——SQL 字符串拼接、缺失授权、IDOR、`eval()`、文件路径来自请求参数。

### 层 C:SCA / 供应链扫描
- **目的**:防 slopsquatting、依赖混淆、typosquatting、已知 CVE。
- **工具**:Dependabot、Snyk Open Source、Socket(AI 增强包分析)、FOSSA、JFrog Xray、Sonatype Nexus、Chainguard、ARNICA。
- **针对 AI 代码的强化**:
  - 安装前校验"包年龄/下载量/维护者"——幻觉包通常刚注册、零下载、新账号。
  - 用私有镜像/allowlist,新包需人工或 AI 二次确认。
  - 对 AI 输出做"幻觉包检测":交叉比对注册表、检查名字与合法包的 Levenshtein 距离(论文显示仅 13.4% 的幻觉包距离 ≤2,即大多数不是简单拼写错误)。
  - Socket 专门做 AI 包风险评分,适合 slopsquatting 场景。

### 层 D:Secrets 扫描
- **目的**:AI 会从开发者 `.env` 上下文里"复述"出 API key/JWT/数据库 URL 并硬编码进生成代码。
- **工具**:Gitleaks(开源,扫 diff 而非仅当前状态,能抓"加完又删"的 secret)、TruffleHog、GitHub Secret Scanning、GitGuardian、Snyk Code(含 secret 规则)。
- **要点**:secret 扫描必须扫**整个 diff**,而非文件最终状态。

### 层 E:测试覆盖与生成
- **痛点**:AI 生成新功能时,人工测试套件根本没覆盖。传统 CI 跑"人写的旧测试"对 vibe-coded PR 几乎无信号。
- **做法**:
  - `jest --changedSince` + `--collectCoverageFrom` 限定到变更文件;阈值从 70% 起步渐进上调。
  - 让 agent 从 diff 生成测试并跑(CodiumAI Qodo、CodiumAI Cover、Diffblue、Mabl、Autonoma)。
  - 突变测试(Stryker)反向验证测试质量。

### 层 F:eval(业务基准)
- 详见"发现 5"。要点:公开基准只做选型参考,**业务回归 eval** 才是上线 gate。建立 golden set + LLM-as-judge + 人工 spot-check 三角。

### 层 G:形式化方法(高保证领域)
- **何时用**:航空航天(DO-178C)、汽车(ISO 26262 ASIL-D)、医疗(IEC 62304 Class C)、金融核心账务、密码学实现。
- **工具栈**:
  - **TLA+**(系统级协议、并发、分布式):AWS、Microsoft、Oracle 长期使用;适合验证锁、一致性、选举协议。
  - **Coq / Lean**(代码级构造性证明):CompCert(C 编译器)、seL4(微内核)等经典案例。
  - **F*(Project Everest)、Dafny、CBMC、TLA+** 的工业链路。
- **新范式**:AI 同时生成代码 + 形式化规约/证明义务——"if AI writes the code, perhaps AI can also write the TLA+ specification"(LinkedIn 讨论,CodeMetal 研究)。FizzBee 让 TLA+ 类验证更可及。
- **现实**:对绝大多数业务代码过度;对"出事就是人命/巨额资金"的代码不可或缺。

## 风险与陷阱

1. **把单一工具当银弹**:装一个 SAST 或 Copilot Review 就认为"AI 代码安全了"。真实数据:SAST 检出率 12.7%–46%,Copilot Review 不 approve、不查所有 CWE——必须分层。

2. **AI 互审的同源盲点**:同一厂商的 coder + reviewer 共享训练偏置,会系统性漏掉同族错误(发现 1 的 81% 单模型幻觉即佐证)。**应使用跨厂商、跨模型族的多 agent 交叉评审**。

3. **第三方 AI reviewer 被绕过**:prompt injection 已被 CSA 实证——AI reviewer 是攻击面的一部分,绝不能是唯一防线。把它的输出当**信号**,不是**裁决**。

4. **用公开 benchmark 当业务上线标准**:SWE-bench 与业务表现脱钩,甚至负相关(发现 5)。没有内部 golden eval 集,等于盲飞。

5. **gate 过重拖死 velocity**:把 5 层全 required、不分路径,会逼团队绕过 gate。用 path scoping + observe→enforce 分阶段、快门先跑。

6. **secret 扫描只看最终文件**:AI 加了又删的 key 会被漏掉。必须扫整个 diff 历史。

7. **SAST 误报噪声把团队训练成"全忽略"**:Autonoma 警告——把 Semgrep 调太宽 → 噪声 → 团队养成无视报警习惯 → 真漏洞被淹没。从窄规则集起步。

8. **对 agentic 测试过度信任**:agent 跑出的 E2E"通过"不等于行为正确——Planner agent 自己也可能漏掉关键流程,需用突变/异常注入校准。

9. **形式化方法用错地方**:对一般业务代码上 Coq 是自杀式 ROI;反过来,核心账务/医疗设备没用形式化方法,则是把公司押在 40% 漏洞率上。

10. **忽视 slopsquatting 的新经济学**:攻击者零成本批量预注册,防御者必须验证每一个 AI 推荐——不对称。allowlist + 私有镜像是结构性缓解。

11. **数据时效性陷阱**:Pearce 2022 的 40% 是 2021 Copilot;Wijewickrama 2024 的 5.2%/21.7% 是 2024-01 的模型快照。新一代模型未重新评估,任何"现在的 AI 代码 X% 有问题"都需重新测。

## 给企业的落地建议

1. **从 5 层最小栈起步,3 周内见效**:
   - 第 1 周:lint + typecheck(`--strict` + changed-files)设为 required。
   - 第 2 周:Semgrep(OWASP Top-10 + 语言规则)+ Gitleaks,**observe 模式**,调规则到低误报。
   - 第 3 周:security + 测试覆盖(70%, changed-files)转 enforce;接入 SCA(Dependabot/Snyk/Socket)。
   - 第 4 周起:高风险路径(auth/payment/PII)叠加 AI reviewer 与 agentic E2E。

2. **建内部 eval 集(头等优先级)**:
   - 选 50–200 个真实业务任务,用 EvalPlus 风格写严格测试。
   - 每个模型/prompt/agent 版本上线前必须跑内部 eval,而非看 SWE-bench。
   - 用 Braintrust/LangSmith 把 eval 接 CI,回归即阻断。

3. **AI 审 AI 用"多模型 + 多厂商"**:
   - 内层:Cursor/Devin 内建 review(同厂商 coder)。
   - 外层:Claude Code Review 或 Copilot Code Review(跨厂商)。
   - 最后一层:人工 spot-review 高风险路径——AI 只做过滤不做裁决。
   - 务必读 CSA 的 prompt-injection advisory,对 AI reviewer 的输入做 sanitize。

4. **供应链专项加固**:
   - 私有 npm/PyPI 镜像 + allowlist;新包需"年龄/下载量/维护者"信号 + 人工或 AI 二次审。
   - 用 Socket 做 AI 包风险评分,默认拦截下载量极低的新包。
   - 禁止 agent 在无 human-in-the-loop 下直接 `pip install` AI 推荐的未知包。

5. **SCA/SAST/secrets/IaC 全部进 CI 为 required check**;用 ASPM(OX/Cycode/Snyk)统一治理,避免工具孤岛。

6. **建立"AI 代码信任度"内部看板**:跟踪每层的真实拦截率、误报率、平均修复时间、漏过到生产的 incident 数——没有度量就没有改进。

7. **高保证管线单独立项**:金融核心、医疗设备、自动驾驶等,在 5 层栈之上强制 TLA+(协议)+ Coq/Lean(关键算法) + 模糊测试(AFL/libFuzzer) + 形式化验证 CI gate。

8. **不要把"已通过所有 gate"等同于"可无人合并"**:L2 是必要非充分条件——必须与 L3(测试与 eval 闭环)、L4(评审与审批)、L5(发布与回滚)联动,才构成端到端可信。

9. **预算与成本模型**:Claude Code Review ~$20/PR、Snyk/Checkmarx 按代码量、agentic 测试每 PR ~$5–15——按 PR 风险分级触发,避免每 PR 都跑全套(agent 成本会失控)。

10. **持续追踪基准演化**:SWE-bench、HumanEval 每年迭代;模型每季度更新;每年至少重测一次 40%/5.2%/21.7% 这类基线数字,避免用过时证据驱动当下决策。
