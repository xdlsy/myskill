## 引言

当一行提示词背后站着一个会读代码、会改文件、会自己跑测试的 agent，文档的角色就被改写了：它不再只是给同事翻阅的备忘录，而是给 agent 在每一次任务开始时加载的"上下文契约"——契约写得清楚，agent 才知道边界在哪、风格在哪、谁说了算。这是 2024–2026 年间业界逐渐形成的稳定共识：2025-08-19，OpenAI 正式公开提交了 `AGENTS.md`（*Agent Markdown*，agent 入口约定文件）规范，之后被 Cursor、Aider、GitHub Copilot 等三十余款工具兼容、被超过六万个开源项目采用，并已交由 Linux Foundation 旗下的 Agentic AI Foundation 接管演进。文档的形态、加载方式、维护节奏，都在围绕这个契约重新组织。

本指南要解决的，正是契约从无到有、从有到稳的全链路问题。我们把 AI 辅助研发涉及的文档工作拆成六个连贯场景：从最上游的"项目入口该写什么"，到存量代码该怎样被 agent 看懂，再到增量开发如何用规范驱动一次次提交，紧接着是文档如何像代码一样接受 PR 门禁与 CI 校验，以及如何抵御上下文腐烂——长文档失效、规则互相打架、agent 越读越糊涂。最后一章回到方法论选型，回答"轻量项目要不要上 Spec-Kit"、"brownfield 适不适合 BMAD"这类必然遇到的取舍题。六个场景之外，第 1 章是全书导航，第 8 章是落地建议，附录 A/B/C 分别给出术语表、模板速查和工具清单。

读这本指南有三种姿势可选。如果你只想用半小时拿走结论，建议读完这段引言后直接跳到第 1 章导航，再扫每章开头的【一页结论】方框，最后看第 8 章的实施路线图，整套流程通常 30 分钟内可以走完。如果你打算系统建立认知，按章节顺序通读最稳妥，每章都从动机讲到反模式，前后呼应。如果你是被排期追着跑的"工具人"，最快路径是直接翻附录 B 抄模板，遇到不确定的字段再回正文对应章节查上下文；附录里的每一份模板都标了它在哪一章被讨论。

需要事先声明的是，本指南综合了三十五份以上的一手与二手来源，覆盖官方规范、知名实践者总结、社区反模式归档与公司内部经验。每一项方法论建议都会标注其适用规模档——轻型（个人或小团队脚本项目）、中型（多人协作的产品代码库）、重型（多团队跨服务的大型系统）——重型流程套到轻型项目上往往得不偿失，反之亦然。我们倾向把判断留给读者：模型能力还在快速演进，今天的最佳实践明年可能被压缩成一个内置 hook，所以读这份指南时，请把它当作一张当前时刻的地图，而不是永久的法典。

### 1.2 术语速查表（按字母序）

本指南涉及的术语横跨 AI 编码代理、架构文档、规约驱动开发与 CI 工具链四个领域，初读容易卡壳。下面这张速查表按字母序列出 ~40 条最常出现的术语，每条只给"短名 + 全称 + 一句话定义 + 附录跳转"，需要详细解释、争议点或权威源时请跳到附录 A 的同名条目。

- **`4+1 view`**（*Four Plus One Architectural View Model*）：Kruchten 1995 年提出的架构 4+1 视图模型，从逻辑、开发、过程、物理 4 个视图加 1 个场景视图描述系统。详见 [附录 A](#术语-four-plus-one)。
- **`@-import`**（*at-import*）：Claude Code 与 Cursor 在 markdown 文件里用 `@path` 语法递归引入其他文件，最多 5 跳，超出会静默截断。详见 [附录 A](#术语-at-import)。
- **`ADR`**（*Architecture Decision Record*）：架构决策记录，每个 ADR 是一份小文档，记录"在某个时间因为某些理由做了某个决定"，常用于追溯架构演化。详见 [附录 A](#术语-adr)。
- **`AGENTS.md`**（*Agent Markdown*）：AI 编码代理通用入口规范，2025-08 由 OpenAI 公开，目标是让任意编码代理读同一个文件理解项目约定。详见 [附录 A](#术语-agentsmd)。
- **`applyTo`**（*applyTo field*）：GitHub Copilot 自定义指令文件 frontmatter 的路径作用域字段，限定该规则只对匹配 glob 的文件生效。详见 [附录 A](#术语-applyto-field)。
- **`arc42`**（*arc42 architecture template*）：开源的 12 节架构文档模板，覆盖目标、约束、上下文、构建块、运行时、决策等，常用于中重型项目。详见 [附录 A](#术语-arc42)。
- **`auto memory`**（*auto memory*）：Claude Code 自动记忆机制，会话中观察到的稳定事实自动持久化到 MEMORY.md，下次会话自动加载。详见 [附录 A](#术语-auto-memory)。
- **`BMAD-METHOD`**（*Breakthrough Method for Agile AI-Driven Development*）：一套面向 AI 驱动敏捷开发的重型方法论，把 PM/Architect/Dev 等角色全部代理化。详见 [附录 A](#术语-bmad)。
- **`Bounded Context`**（*Bounded Context*）：DDD 中的限界上下文，把大领域切成多个有清晰边界的子领域，每个子域内部术语自洽。详见 [附录 A](#术语-bounded-context)。
- **`C4 model`**（*Context, Container, Component, Code*）：Simon Brown 提出的 4 层架构图模型，从 Context 到 Code 逐级放大，是目前最流行的架构可视化方法。详见 [附录 A](#术语-c4-model)。
- **`Claude Code`**（*Claude Code CLI*）：Anthropic 官方编码代理 CLI，支持 CLAUDE.md / hooks / skills / @-import 等机制，是本指南最常引用的代理实现。详见 [附录 A](#术语-claude-code)。
- **`CLAUDE.md`**（*Claude Markdown*）：Claude Code 的项目入口约定文件，放在仓库根目录，启动时自动加载，等价于 Claude Code 版的 AGENTS.md。详见 [附录 A](#术语-claudemd)。
- **`CODEOWNERS`**（*Code Owners file*）：GitHub 的所有者文件，按路径声明谁负责审阅哪些代码，常被 AI 工具复用做"按目录加载不同规则"。详见 [附录 A](#术语-codeowners)。
- **`compaction`**（*context compaction*）：Claude Code 上下文压缩机制，长会话超过窗口阈值时自动摘要旧消息，是控制 context rot 的内置手段。详见 [附录 A](#术语-compaction)。
- **`Constitution`**（*Spec-Kit Constitution*）：Spec-Kit 流程里的项目宪章文件，写明项目不可违背的原则，所有 spec 与 plan 必须与宪章一致。详见 [附录 A](#术语-constitution)。
- **`context rot`**（*context rot*）：上下文腐烂，长会话或长文档累积无关信息后，模型注意力被稀释、答案质量下降的现象。详见 [附录 A](#术语-context-rot)。
- **`CONVENTIONS.md`**（*Conventions Markdown*）：Aider 编码代理的项目约定文件，等价于 Aider 生态的 AGENTS.md，启动时自动加载。详见 [附录 A](#术语-conventionsmd)。
- **`dorny/paths-filter`**（*paths-filter GitHub Action*）：流行的 GitHub Action 路径过滤器，根据 PR 改动路径输出布尔变量，用于条件触发后续步骤。详见 [附录 A](#术语-paths-filter)。
- **`Gherkin AC`**（*Gherkin Acceptance Criteria*）：用 Given/When/Then 三段式写的验收标准，源自 Cucumber/BDD，AI 容易解析也方便人类阅读。详见 [附录 A](#术语-gherkin-ac)。
- **`globs`**（*globs field*）：Cursor 规则文件 frontmatter 的路径作用域字段，作用类似 Copilot 的 `applyTo`，按 glob 限定规则生效范围。详见 [附录 A](#术语-globs-field)。
- **`Glossary`**（*Glossary*）：术语表，DDD 中即"通用语言"的物化形式，把项目核心名词的定义集中维护，避免代码与文档同名异义。详见 [附录 A](#术语-glossary)。
- **`hooks`**（*Claude Code hooks*）：Claude Code 工具调用钩子，可在 PreToolUse / PostToolUse / InstructionsLoaded 等事件点插入脚本，实现自动化与守卫。详见 [附录 A](#术语-hooks)。
- **`INDEPENDENTLY TESTABLE`**（*Independently Testable user story*）：Spec-Kit 对用户故事的硬约束，每个故事必须能单独验证，不能依赖其他故事完成才能测。详见 [附录 A](#术语-independently-testable)。
- **`InstructionsLoaded`**（*InstructionsLoaded hook event*）：Claude Code 在加载完所有规则与 memory 之后触发的 hook 事件，常用于注入运行时上下文。详见 [附录 A](#术语-instructionsloaded)。
- **`JIT 检索`**（*Just-In-Time retrieval*）：按需加载策略，只在真正需要时把文档片段注入上下文，避免一次性塞满窗口，是对抗 context rot 的核心手段。详见 [附录 A](#术语-jit-retrieval)。
- **`lychee`**（*lychee link checker*）：Rust 写的死链检测器，速度极快，常用于 CI 中扫描文档里失效的内外部链接。详见 [附录 A](#术语-lychee)。
- **`MADR`**（*Markdown Architecture Decision Records*）：基于 markdown 的 ADR 模板，比 Nygard 原版多出"Considered Options"等字段，是目前最流行的 ADR 实现。详见 [附录 A](#术语-madr)。
- **`markdownlint-cli2`**（*markdownlint-cli2*）：Node 实现的 markdown 规则校验工具，CI 中用来强制标题层级、行长、列表风格等格式约束。详见 [附录 A](#术语-markdownlint)。
- **`MEMORY.md`**（*Memory Markdown*）：Claude Code 记忆持久化文件，auto memory 把跨会话稳定事实写入此文件，下次启动作为上下文加载。详见 [附录 A](#术语-memorymd)。
- **`Nygard 模板`**（*Nygard ADR Template*）：Michael Nygard 2011 年提出的 ADR 原始模板，五段式：Title / Status / Context / Decision / Consequences。详见 [附录 A](#术语-nygard)。
- **`OpenSpec`**（*OpenSpec*）：Tessl 公司推出的 spec 工作流工具，强调规约先行、可机读，是 Spec-Kit 的同代竞争者。详见 [附录 A](#术语-openspec)。
- **`paths`**（*paths field*）：Claude Code 规则文件 frontmatter 的路径作用域字段，作用类似 Copilot `applyTo` 与 Cursor `globs`。详见 [附录 A](#术语-paths-field)。
- **`path frontmatter`**（*path frontmatter*）：在 markdown 文件顶部用 YAML frontmatter 声明该文件作用路径，是三大代理（Copilot/Cursor/Claude）通用的作用域机制。详见 [附录 A](#术语-path-frontmatter)。
- **`PreToolUse`**（*PreToolUse hook*）：Claude Code 在执行工具调用前触发的 hook 事件，常用于权限校验、命令拦截、注入额外指令。详见 [附录 A](#术语-pretooluse)。
- **`prompt cache`**（*Anthropic prompt cache*）：Anthropic API 的提示缓存机制，把稳定前缀缓存 5 分钟内复用，显著降低长上下文成本与延迟。详见 [附录 A](#术语-prompt-cache)。
- **`SDD`**（*Spec-Driven Development*）：规约驱动开发，先写可执行规约再写实现，AI 时代由 Spec-Kit、OpenSpec 等工具复兴。详见 [附录 A](#术语-sdd)。
- **`skills`**（*Claude Code skills*）：Claude Code 的技能机制，把可复用的工作流封装成一个目录加 SKILL.md，按需加载到上下文。详见 [附录 A](#术语-skills)。
- **`Spec-Kit`**（*GitHub Spec-Kit*）：GitHub 官方推出的 SDD 工具集，提供 specify / plan / tasks 三个 slash command 与配套模板。详见 [附录 A](#术语-spec-kit)。
- **`Spec/Plan/Tasks 三件套`**（*Spec/Plan/Tasks trio*）：增量开发的三份标准文档：spec.md 描述做什么、plan.md 描述怎么做、tasks.md 拆成可独立执行的任务。详见 [附录 A](#术语-spec-plan-tasks)。
- **`Structurizr DSL`**（*Structurizr DSL*）：Simon Brown 发布的领域专用语言，把 C4 模型写成代码，再渲染成多种图形格式，支持版本化与 diff。详见 [附录 A](#术语-structurizr-dsl)。
- **`Vale`**（*Vale linter*）：开源自然语言 lint 工具，按可配置的样式规则检查 markdown 与文档，CI 中守住"AI 友好文档风格"。详见 [附录 A](#术语-vale)。
- **`Y-statement`**（*Y-statement ADR*）：一行式 ADR 写法，模板为"In context of X, facing Y, we chose Z, accepting W, to achieve V"，适合轻型项目。详见 [附录 A](#术语-y-statement)。

## 第 2 章 场景一：搭建 AI 友好的项目入口

### 【核心概念盒】

- [`AGENTS.md`](#术语-agentsmd)（*Agent Markdown*，AI 编码代理通用入口规范，2025-08-19 由 OpenAI 首次公开）
- [`CLAUDE.md`](#术语-claudemd)（*Claude Markdown*，Anthropic Claude Code 专属项目入口文件，支持 `@-import` 与路径作用域）
- [`MEMORY.md`](#术语-memorymd)（*Memory Markdown*，Claude Code 自动记忆索引，硬截断 200 行 / 25 KB）
- [`CONVENTIONS.md`](#术语-conventionsmd)（*Conventions Markdown*，Aider 生态惯用的项目约定文件）
- [`@-import`](#术语-at-import)（Claude Code / Cursor 在 markdown 中用 `@path` 递归引入其他文件的语法）
- [`path frontmatter`](#术语-path-frontmatter)（YAML 头部声明作用路径，让规则只对匹配文件生效）
- [`paths:`](#术语-paths-field)（Claude Code 路径作用域字段，YAML 数组，读到匹配文件时加载）
- [`globs:`](#术语-globs-field)（Cursor 路径作用域字段，支持标量或数组，与 `alwaysApply` 互斥）
- [`applyTo:`](#术语-applyto-field)（GitHub Copilot 路径作用域字段，逗号分隔字符串，IDE Chat 不读）

### 【一页结论】

1. 入口文件用 `AGENTS.md` 命名最跨工具兼容；Claude 用户单独加一份 `CLAUDE.md`
2. `CLAUDE.md` 软建议 ≤ 200 行；`MEMORY.md` 硬截断 200 行 / 25 KB
3. 三种统一方案：短重定向 / @-import 路由（推荐）/ 物理冗余
4. monorepo 嵌套：`AGENTS.md` 覆盖语义、`CLAUDE.md` 合并语义；子文件不要复制父级
5. Copilot `applyTo` 只在 cloud-agent + code-review 生效，IDE Chat 不读
6. 优先级加载顺序：Claude local > project > user；Cursor Team > Project > User
7. 高频 H2 七件套：Overview / Build & Test / Style / Testing / Commit / Do Not / Structure

### 2.1 AGENTS.md 是怎么变成事实标准的

[`AGENTS.md`](#术语-agentsmd)（*Agent Markdown*，AI 编码代理通用入口规范）并非一夜成名。它的前身是单数形式的 `AGENT.md`，在 2025 年 5 月 OpenAI Codex 研究预览发布前后就已出现在部分仓库中。2025 年 8 月 19 日，OpenAI 将规范推送到独立仓库并首次公开提交；仅两天后，兼容工具列表从 5 个迅速扩展到 Aider、Gemini、Kilo Code、OpenCode、Phoenix、Zed 等，形成第一波行业共振。到 2025 年 8 月底，兼容工具已突破 23 个，涵盖 Claude Code、Cursor、Copilot、OpenAI Codex、Sourcegraph Amp、Google Jules、Factory 等主流代理。

治理层面，[`AGENTS.md`](#术语-agentsmd) 经历了从 OpenAI 个人仓库到 **Linux Foundation 旗下 Agentic AI Foundation** 接管的过渡。规范本身没有版本号、release 或 RFC 流程，仅以 markdown spec 加 FAQ 形式存在。FAQ 中甚至给出了一条迁移指引：`mv AGENT.md AGENTS.md && ln -s AGENTS.md AGENT.md`，暗示早期社区在单复数命名上曾有过短暂分歧。如今，`AGENTS.md` 已成为事实上的跨工具通用入口，其“最近者覆盖”的嵌套语义也被多数工具默认接受。

### 2.2 真实项目的入口文件长什么样

为了回答“我的入口文件该写多长”，我们抽样了 20 余个开源项目，按长度分为四档：

- **重型（200+ 行）**：仅框架/SDK 类项目，如 openai/codex（213 行）、vercel/ai（306 行）、langchain-ai/langchain（291 行）。这类项目子包多、技术栈杂，需要大量 H2 区段覆盖不同模块。
- **标准型（50–150 行）**：公认的“舒适区”，如 withastro/astro（89 行）、modelcontextprotocol/servers（103 行）。内容足够完整，又不至于拖慢上下文。
- **极简型（≤30 行）**：只列步骤式工作流，如 mendableai/firecrawl（18 行）。适合规则单一、团队规模小的项目。
- **路由型（≤5 行）**：把入口当重定向，内容下沉到 `.claude/`、`.clinerules/`、`.ai/` 等目录。如 microsoft/vscode（5 行，指向 copilot-instructions.md）、cline/cline（3 行纯 `@-import`）。

从非路由型样本中，我们提炼出高频 **H2 七件套**：Project Overview / Project Structure、Build & Test Commands、Coding Style、Testing Guidelines、Commit & PR Guidelines、Do Not / Gotchas、Repository Structure。这七项基本覆盖了 AI 代理首次接触仓库时最需要的上下文。对一般 5–30 人团队来说，标准型长度（50–150 行）是最稳妥的起点：既不会遗漏关键约定，也不会因文件过长导致代理遵循度下降。

### 2.3 monorepo 与多工具兼容

monorepo 场景下，不同工具的嵌套语义差异显著。[`AGENTS.md`](#术语-agentsmd) 采用**覆盖语义**——“离被编辑文件最近的 AGENTS.md 获胜”；而 [`CLAUDE.md`](#术语-claudemd) 采用**合并语义**——“所有发现的文件按优先级追加”。有趣的是，两套语义最终收敛到同一个实战建议：**子文件不要复制父级内容**，只写本子树独有的约定。例如，根目录的 `AGENTS.md` 描述全局构建与测试规范，子包 `packages/api/AGENTS.md` 只补充 API 层特有的错误处理模式，其余留给父级覆盖。

当团队需要同时服务 Claude、Cursor、Copilot、Aider 等多个工具时，业界已分化出三种统一方案：

| 方案 | 做法 | 适用场景 |
|---|---|---|
| **(A) 短重定向** | 在 `CLAUDE.md` 里写一行 "see AGENTS.md" | 工具自觉跳转，不保证加载第二份 |
| **(B) @-import 路由（推荐）** | `CLAUDE.md` 仅写 `@AGENTS.md` 一行 | Claude / Cursor 均支持，跨平台最稳 |
| **(C) 物理冗余 / CI 同步** | `CLAUDE.md` 与 `AGENTS.md` 字节级一致 | 不依赖 import 能力，需配 CI 校验 |

对一般 5–30 人团队来说，方案 B 是性价比最高的选择：Claude Code 支持 [`@-import`](#术语-at-import) 最多 5 跳递归，Cursor 也能识别 `@filename` 语法，一行即可实现跨工具共享。若团队重度使用 Copilot，则需搭配方案 A 或 C，因为 Copilot 不识别 `@-import`。

工具兼容层面需特别注意：Copilot 的 [`applyTo:`](#术语-applyto-field) 字段在 GitHub.com 仅对 cloud-agent 与 code-review 生效，IDE 端 Copilot Chat 完全不读路径作用域规则。这意味着靠 `applyTo` 拆分的前端/后端规则，在 VS Code 里聊天时会被完全忽略——详见 [report.md](./report.md) §1.4。

### 2.4 长度上限与路径作用域

这是用户最容易踩坑的一节。我们先对比三类工具对入口文件长度的态度：

| 工具 | 长度建议 | 超长后果 |
|---|---|---|
| Claude Code `CLAUDE.md` | ≤200 行（软建议） | 不截断，但 context 越胖、遵循度越差 |
| Claude Code `MEMORY.md` | ≤200 行 / 25 KB（取小） | **硬截断**：超出部分启动时不加载 |
| Cursor | ≤500 行 / 单 `.mdc` | 软建议，无截断 |
| GitHub Copilot | ≤2 页（仅约束自动生成器） | 对手写指令无硬性限制 |

对一般 5–30 人团队来说，**把主入口控制在 150 行以内、单文件不超过 500 行**是安全区。若规则确实庞大，优先用 [`@-import`](#术语-at-import) 拆分到子目录，而不是在一个文件里堆叠 H2。

接下来对比三家工具的路径作用域字段。先说我们对比的是 Claude Code [`paths:`](#术语-paths-field)、Cursor [`globs:`](#术语-globs-field)、Copilot [`applyTo:`](#术语-applyto-field) 三类机制，它们共同目标都是“让规则只对特定目录生效”，但实现细节差异极大：

| 维度 | Claude Code `paths:` | Cursor `globs:` | Copilot `applyTo:` |
|---|---|---|---|
| 字段类型 | YAML 数组 | YAML 标量或数组 | **逗号分隔字符串** |
| 旁路开关 | 无 | `alwaysApply: true` 跳过 globs | `excludeAgent` 指定不生效的代理 |
| 智能描述 | 无 | `description:` 触发 "Apply Intelligently" | 无 |
| 触发时机 | 读到匹配文件时加载 | 同 / 也支持 alwaysApply | "Copilot 正在处理的文件匹配时" |

对一般 5–30 人团队来说，最隐蔽的陷阱是 **Claude Code 的 `paths:` 只在 agent 读到匹配文件时才加载**。如果用户聊天时还没触发 Read 工具，该规则不会进入上下文——这意味着全局风格指南不应放在带 `paths:` 的子规则里，而应留在根 `CLAUDE.md`。Cursor 的 `globs:` 与 `alwaysApply: true` 互斥，二者只能二选一；若想让规则全局生效，直接写 `alwaysApply: true` 即可，不必画蛇添足加 `globs:`。Copilot 的 [`applyTo:`](#术语-applyto-field) 在 IDE Chat 里完全失效，因此不要指望靠它给 IDE 内的编码助手做路径隔离。

最后看优先级合并差异。Claude Code 的加载顺序是 **local > project > user > policy**（项目规则后加载、优先级更高）；Cursor 是 **Team Rules → Project Rules → User Rules**（earlier sources take precedence）；Copilot 则是 **Personal > Repository > Organization**。这意味着同一条冲突规则，在 Claude 里以项目级为准，在 Cursor 里以团队级为准，迁移时需逐条核对覆盖关系。

以下表格作为单页速查，写入仓库 `docs/` 即可作为团队字典使用。

| 维度 | AGENTS.md（通用） | Claude Code | Cursor | Copilot | Aider |
|---|---|---|---|---|---|
| 入口文件 | `AGENTS.md` | `CLAUDE.md` + `.claude/CLAUDE.md` | `.cursor/rules/*.mdc` + AGENTS.md | `.github/copilot-instructions.md` | 任意 markdown，惯用 `CONVENTIONS.md` |

## 第 3 章 场景二：让 AI 看懂存量代码

### 【核心概念盒】

- [`Code Map`](#术语-code-map)（matklad 范式的"目录/模块导览"）：受 rust-analyzer 作者启发的三段式文档，回答"X 在哪里"与"这个东西是干啥的"，不直接放链接以防腐烂。
- [`ADR`](#术语-adr)（Architecture Decision Record，架构决策记录）：记录"在某个时间因为某些理由做了某个决定"的小文档，防止新人或 agent 重复推翻已决策事项。
- [`MADR`](#术语-madr)（基于 Markdown 的 ADR 规范）：在 Nygard 原版基础上增加 YAML frontmatter、显式选项对比与 Pros/Cons，是目前最流行的 ADR 实现，特别适合 AI agent 程序化检索。
- [`C4 model`](#术语-c4-model) / [`arc42`](#术语-arc42)（架构图与架构手册标准）：C4 是 Simon Brown 提出的 Context-Container-Component-Code 四级架构图模型；arc42 是覆盖 12 章节的完整架构手册模板，常用于合规与审计。
- [`Glossary`](#术语-glossary)（领域术语表）：把项目核心名词的定义集中维护，是 DDD 中"通用语言"（Ubiquitous Language）的落地文件，防止代码与文档同名异义。
- [`Bounded Context`](#术语-bounded-context)（DDD 限界上下文）：把大领域切成多个有清晰边界的子领域，每个子域内部术语自洽，子域之间通过显式上下文映射交互。

### 【一页结论】

1. 存量代码文档第一公民是"Code Map + Invariants"（matklad 范式）——"在哪里改"比"怎么改"重要 5 倍。
2. 架构图首选 C4 + Structurizr DSL；企业可补 arc42 第 5/6/7 章把 C4 图嵌入完整手册。
3. ADR 模板首选 MADR——YAML frontmatter 可被 agent 程序化检索，Status 严格枚举且不可改只能追加。
4. 术语表"Don't confuse with"字段是反漂移核心，每次新人或 agent 误用都应把它加进来。
5. Runbook 用 Tom Limoncelli 7 段式骨架，Pager Playbook 是 on-call 生命线。
6. Onboarding 文档前 200 行决定一切，30 分钟动手骨架让 agent 和新人都能快速进入状态。

### 3.1 找代码比改代码慢 5 倍：Code Map 为什么是第一公民

存量代码文档的核心矛盾是"高信息密度 vs. 低维护成本"。matklad（rust-analyzer 作者）有一句被反复引用的观察："Patches take ~2× longer without project familiarity, but locating where to change code takes ~10×." 换句话说，当你不熟悉项目时，找到该改哪里所花的时间，是实际修改代码的 5 倍。这个比例决定了存量文档的优先级排序：第一公民不是 UML 类图，也不是详尽的 API 文档，而是一份能让人在 30 秒内定位到正确目录的 Code Map，加上一组显式声明的架构不变量（Invariants）。Code Map 的任务是回答"X 在哪里"，不变量的任务是回答"你不能打破什么"。

matklad 提出的 ARCHITECTURE.md 范式采用三段式结构。第一段是 Bird's-eye view，用两三句话说明项目解决什么问题、面向什么用户。第二段是 Code map 本身，按目录或 crate 逐个给出 2–5 句描述，每个条目回答两个关键问题："这个东西是干啥的"和"如果你想改相关功能，应该先看哪里"。第三段是 Cross-cutting concerns，列出不属于任何单一模块的横切关注点——例如性能策略、错误处理约定、可观测性埋点、测试风格等。这三段共同构成一份"不依赖链接、不追逐细节"的活文档。

matklad 对这份文档有一条看似反直觉的约束："Do name important files, modules, and types. Do not directly link them (links go stale). Explicitly call-out architectural invariants." 在维护成本高的环境下，不放链接反而是最优选择。链接会腐烂：文件重命名、目录重构、模块合并都会让 markdown 链接失效，而失效的链接比没有链接更危险，因为它制造"已找到"的幻觉。取而代之的是显式命名——告诉读者关键模块叫什么、大概在哪个目录下，让他们用 grep 或 agent 的文件搜索工具去定位。这种"命名 + 搜索"的策略在链接频繁失效的存量代码库中，维护成本远低于"命名 + 链接"。

rust-analyzer 的 architecture.md 是这一范式的模范范本。它对约 18 个 crate 各给出两三句描述，并明确标注每个 crate 是"API boundary"还是"internal"；Cross-cutting Concerns 覆盖了 Stability、Cancellation、Testing、Error Handling、Observability 等维度。如果你的项目还没有这样一份文档，建议直接以 rust-analyzer 的架构文档为蓝本开始写。

### 3.2 架构图：C4、arc42、4+1 视图怎么选

架构图的选择取决于"谁在看"和"agent 能不能读"。四个主流标准在抽象层级、产物形态、适用场景和可解析性上差异显著。下面给出对照表，再逐条解读。

| 标准 | 抽象层级 | 产物形态 | 适合谁 | agent 可解析性 |
|---|---|---|---|---|
| **C4 model** | Context → Container → Component → Code 四级 | 4 张层级嵌套图 + dynamic/deployment | 中小型系统、微服务 | **高**（DSL/JSON 可程序化读取） |
| **arc42** | 12 章模板 | 完整"架构手册" | 大型企业、合规/审计 | 中（自由文本为主） |
| **4+1 view** | 5 个视图（Logical / Process / Development / Physical / Scenarios） | 5 套 UML 图 | 重度 UML 团队 | 低（图为主，文本为辅） |
| **自由 Mermaid** | 无规范 | repo 里散落的 .md + mermaid 块 | 小项目、原型 | 中（Mermaid 文本可读取，但语义自由） |

解读如下。**首选 C4 + Structurizr DSL**：DSL 是纯文本，天然支持版本化、diff 和程序化读取，已有 Structurizr MCP server 可以让 agent 直接查询架构关系。**大型企业补 arc42 章节**：如果团队已有 arc42 文化或需要审计追踪，不必推翻重来，只需把 C4 图嵌入 arc42 模板的第 5、6、7 章（构建块视图、运行时视图、部署视图），避免重复写文字描述。**不建议 4+1**：5 个视图同步维护成本极高，且 UML 图不利于 LLM 直接阅读；仅在已有重度 UML 工具链和建模文化的团队中保留。**小项目用自由 Mermaid**：快速画一张系统上下文图或容器图即可，但必须在 README 里明确声明"这就是本项目唯一的架构图"，防止后来者不断追加风格不一致的新图。

### 3.3 ADR：把"为什么"写下来

代码注释回答"做了什么"，Code Map 回答"在哪里"，ADR 回答"为什么选 A 不选 B"。ADR 的价值在存量代码场景中尤其突出：当一个 agent 或新成员看到一段"看起来可以优化"的代码时，ADR 能阻止他重复踩坑。目前有三种主流模板，选择取决于团队规模和决策复杂度。

三种模板的对照如下。Nygard 模板是 Michael Nygard 2011 年提出的原始五段式：Title、Status、Context、Decision、Consequences，散文风，半页到 1 页即可，适合个人或小团队快速记录。MADR 在此基础上增加了 YAML frontmatter、Decision Drivers、Considered Options、Decision Outcome、Confirmation、Pros/Cons 等字段，显式列出"考虑过哪些选项、为什么排除它们"，长度 1–2 页，是中大团队的首选。Y-statement 把决策六要素压缩成一句话："In the context of X, facing Y, we decided for Z, and against W, to achieve V, accepting D"，适合高管汇报或咨询场景，但不能替代完整 ADR。

**AI agent 主导维护时，推荐 MADR + frontmatter**。YAML 字段可被 agent 程序化检索，例如"列出所有 Status 为 superseded 的 ADR"或"找出所有涉及数据库选型的决策"。实战要点包括：文件名编号化（`0001-…`），Status 严格枚举（proposed / accepted / deprecated / superseded by 0042），ADR 不可改、只能追加新 ADR 取代旧决策，每条 ADR 长度控制在 2 页以内。一个典型的生命周期是：`proposed` → `accepted` → 两年后因技术栈迁移变为 `deprecated` → 最终被 `superseded by 0042`。

### 3.4 术语表与领域语言

Martin Fowler 提出的 **Ubiquitous Language（通用语言）** 是领域驱动设计的核心原则之一：团队（包括开发、产品、业务）必须使用同一套精确术语交流，代码中的类名、函数名、数据库表名应与日常对话中的术语保持一致。Glossary 就是这套通用语言的物化形式。

单条术语建议包含 6 个字段：English（英文原文）、中文（统一译名）、Bounded Context（所属限界上下文）、Definition（精确定义）、Code mapping（代码映射，如关键类名或状态机文件）、Don't confuse with（易混淆概念辨析）、Last reviewed（最后审阅日期）。其中 **"Don't confuse with"是反漂移的核心机制**。以电商领域为例：`Order`（客户已付款的购买请求）容易与 `PurchaseOrder`（采购方向）和 `Invoice`（账务方向）混淆。每次新人或 agent 把三者混用，都应该把混淆点补进这一字段。久而久之，Glossary 变成了一部"防踩坑词典"。

组织方式上，小项目（单 bounded context）直接按字母序排列即可；中大型项目应先按子域分组（如 `# Billing`、`# Inventory`、`# Auth`），子域内再按字母序。Glossary 也应作为 docs-as-code 管理：PR 修改需要 review，CI 可用 `grep` 或 Vale 禁用已废弃的旧术语，每季度安排一次集中 review。

### 3.5 Runbook 与 Onboarding 文档

Runbook 是 on-call 工程师的救生圈。Tom Limoncelli 提出的 7 段式骨架被 PagerDuty 和 Google SRE 广泛采用：1) Service Overview（服务概述）；2) Service Build Information（构建信息）；3) Instructions for Deploying（部署步骤）；4) Instructions for Common Tasks（常见操作）；5) **Pager Playbook**（每个监控告警的逐步处理流程，这是最关键的一段）；6) Disaster Recovery Plans（灾难恢复）；7) Service Level Agreement（SLA 承诺）。

Onboarding 文档的目标是让 agent 或新人在 30 分钟内完成第一次有效提交。前 200 行决定一切——如果前 200 行还没讲清楚"怎么跑起来"，读者就会流失。优秀样本包括：OpenAI Codex 的 `AGENTS.md`（213 行，包含最近一次必跑命令、"不要碰的文件"清单、目标行数上限）、Grafana 的 `developer-guide.md`（432 行，troubleshooting 占比最高，因为新人最容易卡的地方就是环境配置）、Kubernetes 的 `contributors/devel`（按 SIG 拆分，每个 SIG 给出自己的 code hierarchy + design conventions）。

最小骨架可以用 8 个 H2 组织：1. What this project does（3 句以内）；2. Quickstart（照抄能跑）；3. Repo layout（matklad Code Map 风格）；4. How to make a change；5. Where to look first；6. Common tasks；7. Troubleshooting；8. Where to go next。

当入口文件（AGENTS.md / CLAUDE.md / README.md）已经就位，下一步就是为存量代码补充结构化文档。下面给出一份可直接套用的 `docs/` 目录树，覆盖 Code Map、架构图、ADR、术语表、Runbook 和 Onboarding 六大板块。

## 第 4 章 场景三：用 AI 做增量开发

### 【核心概念盒】

- [`SDD`](#术语-sdd)（*Spec-Driven Development*，规约驱动开发）：先写可验证规约再写实现，AI 时代由 Spec-Kit、OpenSpec 等工具复兴
- [`Spec-Kit`](#术语-spec-kit)：GitHub 出品的 SDD 流水线，提供 specify / plan / tasks / implement 四个 slash command 与配套模板
- [`BMAD-METHOD`](#术语-bmad)：角色驱动的 Agile 框架，把 PM / Architect / Dev 等角色全部代理化，覆盖 Agile 全生命周期
- [`Spec/Plan/Tasks 三件套`](#术语-spec-plan-tasks)：spec.md 描述"做什么"、plan.md 描述"怎么做"、tasks.md 拆成"一步步做哪些"
- [`Constitution`](#术语-constitution)：Spec-Kit 中不可变的项目宪章，写明技术栈、安全底线、性能基线等不可违背原则
- [`INDEPENDENTLY TESTABLE`](#术语-independently-testable)：Spec-Kit 对用户故事的硬约束，每个故事必须能单独验证，不能依赖其他故事完成才能测
- [`Gherkin AC`](#术语-gherkin-ac)：Given / When / Then 三段式验收标准，源自 Cucumber / BDD，AI 容易解析也方便人类阅读

### 【一页结论】

1. 增量开发的心智模型：spec → plan → tasks，对应"做什么 / 怎么做 / 一步步做哪些"
2. spec 硬约束：每个 user story 必须 INDEPENDENTLY TESTABLE，拆到能单独发版才算合格
3. plan 的入口在 Constitution Check——必须先过门禁才进 Phase 0，违反宪章的复杂度必须显式追踪
4. tasks 并行规则 `[P]`：不同文件 + 无依赖 + 同一 phase 内，三条必须全满足
5. 任务粒度：Epic 1–4 周 / Story 0.5–3 天 / Task 15 min–2 h，AC 数量 3–7 条是 story 大小的体温计
6. TDD × AI 铁律：spec → test → code，test 必须先 FAIL 再 PASS，tasks.md 里 test 编号 < 实现编号
7. 决策树：diff 一句话能描述就跳过 plan；多文件或不熟悉就上 plan；新功能或重构上完整三件套

### 4.1 心智模型：spec → plan → tasks 解决什么问题

AI agent 有一个通病：过度热心。你只说"加个头像上传"，它已经连路由、存储、裁剪、CDN 刷新全写好了——却没问你要不要支持 GIF、允许多大、存本地还是 S3。这种"上来就改代码、不问需求"的模式，在小型改动上可能侥幸过关，一旦涉及跨模块或新数据模型，返工率会急剧上升。

spec → plan → tasks 三件套正是为了把 agent 的"热心"约束在正确的轨道上。spec 回答"做什么"：用户故事、验收标准、成功指标。plan 回答"怎么做"：技术选型、架构变更点、风险与回滚策略。tasks 回答"一步步做哪些"：每个任务对应一次可提交的改动，带编号、带依赖、带并行标记 `[P]`。三者不是瀑布三阶段，而是一张决策滤网——diff 一句话能说清的任务直接跳过，跨文件或陌生代码才上升到 plan，全新功能或重构才拉满三件套。

以"用户头像上传"为例。spec 层面会拆成两条用户故事：US1"用户能上传并预览头像"（P1，MVP），US2"系统自动压缩并生成多尺寸缩略图"（P2）。每条故事配 3–5 条 Given/When/Then 验收标准，并写明"单张不超过 5 MB、仅接受 JPG/PNG/WebP"。plan 层面决定技术路线：用 Hono 接收 multipart、Sharp 做服务端压缩、R2 做对象存储、Presigned URL 做前端直传——同时标注风险"Sharp 在 Worker 环境需要 wasm 版，需验证冷启动耗时"。tasks 层面则拆成 T001 写 contract test（先 FAIL）、T002 加路由与中间件、T003 加 storage 适配器、T004 写压缩 pipeline，每条任务 15 min–2 h，可并行的打 `[P]`，依赖关系显式写出。agent 拿到这份清单后，每一步都有边界、有验证、有回退点，不会再"自作主张"地多写或少写。

### 4.2 GitHub Spec-Kit 四件套

Spec-Kit 是 GitHub 官方推出的 SDD 工具集，核心产物是四份模板文件：Constitution、spec-template、plan-template、tasks-template。Constitution 是最高约束——它写明项目不可违背的原则（如"所有 P1 story 必须有 contract + integration test"、"单 Worker 内存 < 128 MB"），任何 spec 与 plan 都必须与其一致。plan-template.md 里专门设了"Constitution Check"门禁：未通过检查不得进入 Phase 0 研究，设计完成后还要复验一次。

spec-template.md 的章节顺序很有讲究。它从"User Scenarios & Testing"（强制）开始，要求每个用户故事标注优先级 P1/P2/P3，并回答"Why this priority"与"Independent Test"两个子问题——后者正是 INDEPENDENTLY TESTABLE 约束的落地形式。接着是 Requirements（强制，FR-001 起编）、Success Criteria（强制，SC-001 起编，要求 measurable + technology-agnostic）、最后才是 Assumptions。这种顺序强迫写 spec 的人先想"谁用、怎么用、怎么测"，再落功能点，避免一上来就堆技术细节。

plan-template.md 的亮点在"Technical Context"与"Complexity Tracking"两段。Technical Context 列出 9 个 advisory 字段（Language/Version、Primary Dependencies、Storage、Testing、Target Platform、Project Type、Performance Goals、Constraints、Scale/Scope），缺省值一律是字面量 `NEEDS CLARIFICATION`——如果 plan 里还有字段没澄清，说明 plan 本身就不合格。Complexity Tracking 则是一张异常登记表：只有当实现方案违反了 Constitution 的某条原则时才填，写明 Violation / Why Needed / Simpler Alternative Rejected Because。这张表的存在，让"为了赶进度而妥协"这件事从隐性变成显性，方便后续审计与回滚。

tasks-template.md 的格式是 `[ID] [P?] [Story] Description`，其中 `[P]` 表示可并行，条件有三：不同文件、无依赖、同一 phase 内。依赖结构是 Setup → Foundational（阻塞所有 stories）→ User Stories（只依赖 Foundational，可并行）。在一个 story 内部，顺序固定为 tests → models → services → endpoints → integration——test 必须写在最前面，且必须先 FAIL 再 PASS。

INDEPENDENTLY TESTABLE 这条硬约束值得单独强调。Spec-Kit 原文说："if you implement just ONE of them, you should still have a viable MVP." 换句话说，如果只实现 US1 就能单独验证并交付价值，说明拆分对了；如果 US1 的测试必须等 US2 的接口就绪，说明要么拆得太细、要么依赖关系没澄清，需要回炉重写。

### 4.3 BMAD-METHOD：角色驱动的 Agile 框架

BMAD-METHOD（Breakthrough Method for Agile AI-Driven Development）与 Spec-Kit 不同，它的核心不是流水线，而是角色。BMAD 把 PM、Architect、Scrum Master、Dev 等角色全部代理化，每个 persona 有明确的职责边界与输入输出格式。真实仓库已有 33 个下游项目 + 16 个 package，其中最受关注的是 `BMAD-AT-CLAUDE`（229 stars），专门把 BMAD 移植到 Claude Code 生态。

BMAD 的 Epic + Story 模板采用严格的 Gherkin AC 格式：

```
## Epic {{N}}: {{epic_title_N}}
### Story {{N}}.{{M}}: {{story_title}}
As a {{user_type}}, I want {{capability}}, So that {{value_benefit}}.
**Acceptance Criteria:**
- Given {{precondition}}
- When {{action}}
- Then {{expected_outcome}}
```

AC 数量经验是 3–7 条；超过 7 条说明 story 太大，必须拆分。这个阈值不是拍脑袋定的，而是来自大量实践：3 条以下容易遗漏边界，7 条以上人类 review 时注意力会涣散，agent 也容易漏掉某条。

BMAD 的真正创新在单 Story 实现模板里的"task → AC 反追踪"。每个子任务后面标注 `(AC: #)`，明确说明这条任务覆盖哪几条验收标准：

```
- [ ] Task 1 (AC: 1, 3)
- [ ] Task 2 (AC: 2)
```

这种反追踪让"实现是否覆盖需求"从主观判断变成可机械检查的事实。BMAD 还要求在 Dev Notes 的 References 里给出 `path#anchor` 引用源，例如 `[Source: docs/architecture.md#auth-flow]`，确保 agent 在实现时能快速定位到相关上下文。

与 Spec-Kit 相比，BMAD 重在"角色协作 + 全生命周期"：从 Epic 规划、Story 拆分、任务实现到验收归档，每个阶段都有明确的输入输出和负责 persona。Spec-Kit 重在"流水线 + 严格门禁"：Constitution Check、INDEPENDENTLY TESTABLE、Complexity Tracking 都是不可跳过的硬性检查点。两者并不互斥——BMAD 的 `(AC: #)` 可以混进 Spec-Kit 的 tasks.md，Spec-Kit 的 `[P]` 并行标记也可以用在 BMAD 的任务清单里。

### 4.4 决策树：什么情况下要写 plan？

Anthropic 在最佳实践文档里有一句原话："**If you could describe the diff in one sentence, skip the plan.**" 这句话是增量开发文档化的北极星。它的含义不是"不要写文档"，而是"不要让文档的 overhead 超过它带来的价值"。

我们把这个原则落地成一张五类场景决策矩阵：

| 任务类型 | 一句话能描述 diff？ | 跨文件？ | 不熟悉？ | 决策 | 文档产物 |
|---|---|---|---|---|---|
| 改 typo / 注释 | 是 | 否 | 否 | **跳过 plan** | 无 |
| 修小 bug（已定位） | 是 | 1–2 文件 | 否 | **轻 plan**：口头列 2–3 步 | inline TODO |
| 加新接口/端点 | 否 | 3+ 文件 | 否 | **Plan Mode + plan.md** | spec.md + plan.md |
| 跨模块重构 | 否 | 5+ 文件 | 是 | **完整三件套** | 全套 |
| 新功能（含数据模型） | 否 | 是 | 是 | **完整三件套 + research** | 全套 |

口诀可以记成三句："diff 一句话 → 直接做；多文件或不熟悉 → plan；新功能或重构 → 全套"。

举个例子。你发现登录按钮的颜色写错了，把 `#ff0000` 改成 `#dc2626`，一句话能说清、单文件、代码熟悉——直接改，不需要任何 plan。但如果你要给用户系统加"邮箱验证"功能，涉及 model、service、route、email provider 四个模块，且你对团队用的 email 网关不熟悉——这时候必须上完整三件套：先写 spec 明确"验证链接 24 小时有效、失败 3 次后锁定"，再写 plan 决定"用 Resend 还是 SES、token 存 Redis 还是 DB"，最后拆 tasks 让 T010 写 test（先 FAIL）、T012 加 model、T014 加 service、T016 加 endpoint。没有这套约束，agent 很可能跳过 token 过期逻辑、漏掉重试限制，或者把 email 发送做成同步阻塞调用——这些错误在 code review 时很难一眼看出，但在 spec 的 AC 里写清楚后，agent 想漏都漏不掉。

### 4.5 任务粒度与并行规则

增量开发的三层粒度是 Epic、Story、Task。Epic 对应一个完整用户旅程，含 3–8 个 story，工期 1–4 周，由 PM 或 Architect 产出。Story 是"独立可测可发"的最小切片，含 3–7 条 AC，工期 0.5–3 天，由 PM 与 Tech Lead 共同产出。Task 是单文件改动加验证，单一动作，15 min–2 h，由 Tech Lead 或 agent 直接产出。

这个粒度的设计意图是"让人类审 story，让 agent 做 task"。人类擅长判断"这个功能对用户有没有价值、AC 是否完整"，所以 story 的拆分与验收标准必须由人把关。agent 擅长"按清单执行、跑测试、修报错"，所以 task 的编排与执行可以交给 agent。Epic 则是路线图级别的聚合，用于向 stakeholder 汇报进度。

`[P]` 并行标记有三条铁律，必须全部满足才能打 `[P]`：

1. **不同文件**：两个 `[P]` 任务不能修改同一个文件，否则 git 冲突概率极高
2. **无依赖**：不能读取其他未完成 task 的产物（例如 task B 需要 task A 生成的接口类型）
3. **同一 phase 内**：不能跨 Foundational → Story 边界并行，因为 Foundational 阻塞所有 stories

一个正例：T012 `[P]` `[US1]` 在 `src/models/user.ts` 里写 User model，T013 `[P]` `[US1]` 在 `src/models/order.ts` 里写 Order model——不同文件、无依赖、都在 Phase 2 Foundational，可以并行。一个反例：T014 在 `src/services/order.ts` 里实现 OrderService，它依赖 T012 和 T013 的 model——虽然与 T012/T013 是不同文件，但有依赖，所以不能打 `[P]`，必须串行。另一个反例：同文件内两处 edit，即使逻辑无关，也不能并行，因为 git 的 line-based diff 会把它们当成冲突。

### 4.6 TDD × AI Agent

TDD（Test-Driven Development）在 AI agent 时代不是可选项，而是必选项。原因很直接：agent 没有人类的"直觉正确"，它只有"测试通过"这一个 reward signal。你给了 spec，agent 把 spec 翻译成 test，test 把"做什么"编码成可执行契约，agent 再拿契约当指南针去写代码。没有 test，agent 就会产出 plausible-but-wrong 的代码——看起来对，跑起来错，review 时还发现不了。

顺序铁律是 spec → test → code，不可颠倒。Spec-Kit tasks-template.md 的原文是："Write these tests FIRST, ensure they FAIL before implementation." Anthropic 的措辞更强烈："Include tests, screenshots, or expected outputs so Claude can check itself. **This is the single highest-leverage thing you can do.**" 这里的 leverage 指的是 reward signal 的清晰度：test PASS 是明确的正反馈，test FAIL 是明确的负反馈，agent 在这两种信号之间迭代，效率远高于"你看着代码说好像不对"。

为什么 test 必须先 FAIL 再 PASS？因为 agent 有时会写"占位测试"——test 本身就有 bug，或者 mock 了全部依赖，导致无论实现对不对 test 都 PASS。这种自欺欺人在人类团队里也很常见，但在 agent 场景下更隐蔽，因为 agent 不会"觉得不对劲"。强制要求"先看到 RED 再看到 GREEN"，就是为了堵住这个漏洞。

三个检查点构成 TDD × AI 的完整闭环：

1. **spec 完成后人类 review**：禁止 agent 一口气从 idea 到代码。agent 可以在 explore 阶段帮你草拟 spec，但 spec 定稿必须经过人类确认——因为"做什么"是价值判断，不是技术问题。
2. **test 必须先 FAIL 再 PASS**：tasks.md 里 test 任务的编号必须小于实现任务的编号（如 T010-test < T012-impl），确保执行顺序不可颠倒。
3. **tasks.md 里 test 编号 < 实现编号**：这不是形式主义，而是把"test 先行"从口头约定变成机械约束。agent 读 tasks.md 时，看到 T010 是 test、T012 是 impl，自然会先跑 T010 看到 FAIL，再写 T012 让测试变绿。

一个反例可以说明这套规则的必要性。某团队让 agent 直接实现"用户注册"功能，没有写 spec，也没有先写 test。agent 用了 20 分钟写完代码，看起来一切正常——但注册成功后没有设置 session cookie，用户刷新页面就掉登录。这个 bug 在 code review 时很难发现，因为 reviewer 的注意力被"代码风格对不对、变量命名好不好"占满了。如果先写 spec，AC 里会有一条"Given 注册成功 When 刷新页面 Then 用户仍保持登录状态"；如果先写 test，T010 会断言 cookie 存在，agent 在实现时就不会漏掉这一步。test 不是"额外的负担"，而是"把隐性需求变成显性约束"的翻译器。

### 【实战速查】Spec-Kit / BMAD 模板抄写指引

完整模板见附录 B.1（Spec-Kit 四件套）与 B.2（BMAD Epic + Story 模板）。本节只给精简骨架，供快速起手：

**spec.md 骨架（5 行核心）**：

```markdown
## User Scenarios & Testing *(mandatory)*
### User Story 1 — <切片> (Priority: P1)
**Independent Test**: <怎么单独验证>
1. **Given** <前置>, **When** <动作>, **Then** <结果>
```

**plan.md 骨架（5 行核心）**：

```markdown

<1 句话需求 + 1 句话技术路线>

- [ ] 代码质量 / 测试标准 / 性能 三项门禁

| Violation | Why Needed | Simpler Alternative Rejected Because |
```

**tasks.md 骨架（5 行核心）**：

```markdown
## Phase 2: Foundational  ⚠️ blocks all stories

- [ ] T005 [P] <可并行任务>
## Phase 3: User Story 1 — <标题>  🎯 MVP

```

**BMAD 单 Story 骨架（3 行核心）**：


> 把"做什么、怎么做、一步步做哪些"写下来还远远不够——这些文档**写完之后会腐烂**。第 5 章和第 6 章合在一起回答两个相关问题：怎么让文档与代码同步演化、以及怎么让规则不被时间侵蚀。

## 第 5 章 场景四：把文档维护成代码

### 【核心概念盒】

本章涉及 5 个关键术语：

- [`Vale`](#术语-vale)：散文风格检查工具，覆盖术语一致性、拼写、句法与可读性。
- [`markdownlint-cli2`](#术语-markdownlint)：Markdown 结构层 lint，负责标题层级、列表样式、代码围栏语言标签等。
- [`lychee`](#术语-lychee)：链接失效检查工具，Rust 编写，异步并发，自带缓存。
- [`CODEOWNERS`](#术语-codeowners)：GitHub 文件归属机制，可强制要求特定路径的变更必须经过指定 reviewer 批准。
- [`dorny/paths-filter`](#术语-paths-filter)：PR 路径过滤守卫，用于检测"某路径改了而另一路径没改"并阻断合并。

### 【一页结论】

1. **文档静态检查 = Vale + markdownlint-cli2 双轨**：Vale 管 prose 风格，markdownlint-cli2 管 Markdown 结构，二者互补不重叠。
2. **链接检查首选 lychee**：Rust 实现，异步并发，大仓库速度比 Node.js 替代品快 5–30 倍，且自带缓存。
3. **双层链接检查**：增量 PR 守门（只扫改动文件，阻塞合并）+ 全量定期巡检（每日 cron，失败开 issue，不阻塞代码流）。
4. **PR 门禁：dorny/paths-filter** 防止"代码改了而 docs 没改"；允许 `skip-docs` 或 `chore` label 跳过。
5. **文档审批：CODEOWNERS + Branch Protection** 给 `docs/` 指定 reviewer，启用 "Require review from Code Owners"。
6. **自动 vs 手写**：API 签名、类型、接口 schema 自动生成；架构图、决策原因（why）、部署 runbook 必须手写。
7. **文档覆盖率**：业界无统一指标，可自建 "src 行变 / docs 行变" 比，健康值 **0.05–0.30**（每改 100 行代码改 5–30 行文档）。
8. **Claude Code hooks**：8 个最值得配置的事件（SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、Stop、PreCompact 等），让 agent 自动遵守 docs-as-code 规则。

### 5.1 docs-as-code 是什么、不是什么

docs-as-code 不是"把文档放在代码旁边"，而是把文档当作一等工程资产来维护。它的四要素缺一不可：

1. **同仓**：文档与源码在同一 Git 仓库，共享分支、tag、history。反例：Confluence、Wiki——版本与代码脱节，无法 `git bisect` 回溯。
2. **PR 门禁**：任何文档变更走 Pull Request，不能直推 main。代码 review 的纪律同样适用于文档。
3. **CI 校验**：合并前自动跑 lint、链接检查、风格检查，失败即阻断。
4. **CODEOWNERS**：给 `docs/`、`adr/`、`runbook/` 等路径指定固定 reviewer，防止"谁都可以改、没人负责审"。

**例子：同 PR vs 单独 PR**
- 功能开发时，文档与代码放在**同一个 PR**。reviewer 同时审逻辑与文档，确保二者一致。
- 单独开一个 "docs update" PR 看似干净，实则割裂上下文： reviewer 看不到代码改了什么，容易漏审。
- 例外：大规模文档重构（如统一术语替换）可单独 PR，但需标注影响的代码范围。

### 5.2 静态检查工具组合：Vale + markdownlint + lychee

#### Vale（Go，社区规则包丰富）

Vale 是 prose linter，检查拼写、大小写、术语替换、禁用词、可读性、句法序列。配置核心在 `.vale.ini`：

```ini
StylesPath = .github/styles
MinAlertLevel = suggestion
Packages = Google, write-good, proselint

[*.{md,mdx}]
BasedOnStyles = Vale, Google, write-good
```

社区有 Google、Microsoft、RedHat 等现成规则包，开箱即用。write-good 与 proselint 不必单独安装——Vale 通过 `Packages = write-good, proselint` 一行接管。

#### markdownlint-cli2（Node.js，结构层）

markdownlint-cli2 管 Markdown 结构：标题层级是否跳跃、列表样式是否统一、代码围栏是否带语言标签、行长是否超限。它与 Vale 互补——Vale 不管 `###` 后面是否空行，markdownlint 不管 "setup" 是否该写成 "set up"。

#### lychee（Rust，链接检查一锤定音）

| 项 | lychee | markdown-link-check |
|---|---|---|
| 实现 | Rust，单二进制 | Node.js |
| 速度 | 异步并发，**大仓快 5–30×** | 串行 |
| 缓存 | `--cache --max-cache-age 1d` | 无 |
| GitHub Action | 官方 `lycheeverse/lychee-action` | 第三方 |

**双层策略**：
- **增量（PR 守门）**：仅扫描 PR 改动文件，失败阻断合并。
- **全量（定期巡检）**：每日凌晨 cron 跑全仓，失败自动开 issue，不阻塞代码流。

完整配置文件（`.vale.ini`、`.markdownlint.json`、`docs-lint.yml`、`links.yml`）见 [附录 B.4](#b4-docs-as-code-工具配置)。

### 5.3 PR 门禁：让文档落后于代码不能合并

#### CODEOWNERS：给文档指定"责任人"

```
# .github/CODEOWNERS
docs/           @tech-writer-team @architects
adr/            @architects
runbook/        @sre-team
```

- 区分大小写，`/docs/` 包含全部子目录。
- 在 Branch Protection 中启用 **"Require review from Code Owners"**。
- Tech Writer 的 review 可设为 **non-blocking**：maintainer 可提前合并，但必须创建 post-merge follow-up issue。

#### dorny/paths-filter：防止"代码改了 docs 没改"

```yaml
- uses: dorny/paths-filter@v4
  id: filter
  with:
    filters: |
      src: 'src/**'
      docs: 'docs/**'
- if: steps.filter.outputs.src == 'true' && steps.filter.outputs.docs == 'false'
  run: echo "代码改了但文档没改"; exit 1
```

- 检测 `src/**` 改而 `docs/**` 未改时，CI 失败，阻塞合并。
- 允许 `skip-docs` 或 `chore` label 跳过，避免无意义阻塞。

#### 进阶：ADR 联动守卫

代码动核心目录（`src/auth/`、`src/db/`、`src/api/`）时，必须新增或更新 ADR。实现方式：在 paths-filter 中增加 `adr` 路径检测，要求 `src/core/**` 改则 `adr/**` 必须同时改。

简化 GitHub Actions 片段（5–10 行骨架）见上文，完整配置见 [附录 B.5](#b5-pr-门禁配置)。

### 5.4 自动生成 vs 手写：what/where 自动；why/when 手写

核心原则：**what 与 where 自动生成，why 与 when 必须手写。**

API 签名、类型定义、接口 schema 属于 "what"——它们随代码变动而变动，手工维护必然过期。OpenAPI/Swagger、TypeDoc、godoc、Sphinx autodoc 等工具可 100% 自动生成，且保证与代码一致。Stripe 的 API reference 就是完全从 OpenAPI 生成的典范。

但 "why" 无法自动生成：为什么这个字段是必需的？为什么弃用旧接口而不是直接删除？为什么采用 JWT 而非 Session？这些决策原因必须人工写成 docstring、ADR 或架构文档。agent 读到 "why"，才能避免推翻已经深思熟虑的决策。

同理，"when" 也靠手写：部署 runbook 里的异常路径、回滚步骤、告警响应流程——这些涉及业务上下文与运维经验，工具无法推导。

**引用关系四要素**（让 agent 顺藤摸瓜）：
1. 路径 + 行号（如 `src/auth/token.ts:42-89`）
2. 测试文件路径
3. ADR 链接
4. `Last verified` 时间戳 + git sha

### 5.5 Claude Code hooks：让 agent 自动遵守

Anthropic 提供 25+ 事件，docs-as-code 场景最值得配置的 8 个：

| 事件 | 是否值得配置 | 用途 |
|---|---|---|
| `SessionStart` | ✅ | 注入项目入口文档、最近 ADR，让 agent 开局即知情 |
| `UserPromptSubmit` | ✅ | 注入 staleness 警告与约束条件 |
| `PreToolUse` | ✅ | 阻止危险/不合规操作（如 `rm`、创建 `docs/notes.md` 等噪音文档） |
| `PostToolUse` | ✅ | 自动跑 vale/eslint，给反馈让 agent 自纠 |
| `Stop` | ✅ | 收尾时提醒"是否更新了文档/ADR/OpenAPI？" |
| `PreCompact` | ✅ | 关键决策落盘提醒，防止上下文压缩时丢失 |
| `InstructionsLoaded` | ✅ | 校验 `.claude/instructions.md` 版本与仓库是否匹配 |
| `PreToolUse`（二次） | ✅ | 对 `Write`/`Edit` 操作检查目标路径是否在 `docs/` 并触发 CODEOWNERS 提醒 |

**三个关键脚本用途**：
- `block-docs-write.sh`：阻止 agent "好心"创建 `docs/progress.md`、`docs/notes.md` 等噪音文档，强制写入规范路径。
- `remind-docs.sh`：改了 `src/auth/`、`src/db/`、`src/api/` 后，提醒检查架构文档 / ADR / OpenAPI 是否同步。
- `inject-stale-warning.sh`：`AGENTS.md` 的 `last_verified` 过 30 天，在 agent 读取时开头注入过期警告。

### 5.6 文档覆盖率与 review 文化

#### 三个自建指标

**指标 A：src 行变 / docs 行变 比**
```bash
RATIO=$(echo "scale=2; ${DOC_LINES:-0} / ${SRC_LINES:-1}" | bc)
```
健康值 **0.05–0.30**。低于 0.05 说明文档严重滞后；高于 0.30 说明可能在写小说。

**指标 B：staleness 度量**
- 过期率：`last_verified < now - 90d` 的文档比例。
- 漂移率：`verified_against` 的 git sha 之后，该文件夹有 N 次 commit 未验证。

**指标 C：agent 引用率**
在 hooks 里记录 agent `Read` 了哪些文档。0 引用的文档要么是僵尸（应删除），要么入口没正确链到（应修链接）。

#### 他山之石：GitLab Handbook 四角色

GitLab 的公开 SOP 是最详细的 docs-as-code 实践：
1. **Developer** 主笔——谁写代码谁写文档。
2. **PM** 定义 requirements——确保文档覆盖业务目标。
3. **Tech Writer** non-blocking review——可后补，但必须开 follow-up issue。
4. **Maintainer** 拥有合并权——对文档与代码的一致性负最终责任。

铁律：功能 MR 不带文档不能合并；AI 生成文档必须人工 review + 跑 Vale。

#### Stripe 与 Vercel 的打法

- **Stripe**：工程师写 first draft，专职 docs engineer 改写；API reference 100% 从 OpenAPI 自动生成。
- **Vercel**：强调"快速删除比慢速修复更优"——过期文档优先删除，不容忍"待修复"状态。

不同规模团队可按以下三档选择工具链：

## 第 6 章 场景五：让文档与规则不腐烂

### 【核心概念盒】

- [`JIT 检索`](#术语-jit-retrieval)（*Just-In-Time*，按需加载）：保留轻量标识符（路径、查询、链接），运行时再取数据，而非预加载全文。
- [`auto memory`](#术语-auto-memory)：Claude Code v2.1.59+ 的自动记忆机制，agent 自写、人后审，存储于 `~/.claude/projects/<project>/memory/`。
- [`compaction`](#术语-compaction)：长会话中 Claude Code 对上下文进行压缩，以释放 token 预算；压缩后部分规则需重新注入。
- [`context rot`](#术语-context-rot)：上下文过载导致的注意力稀释，表现为 agent 对单条规则的遵循度随 token 总量增加而下降。
- [`InstructionsLoaded`](#术语-instructionsloaded)：规则加载事件 hook，可审计哪些文件进入上下文，但不能审计 agent 是否遵守。
- [`PreToolUse`](#术语-pretooluse)：工具调用前 hook，可用于在 agent 执行动作前插入校验或阻断逻辑。

### 【一页结论】

1. JIT 检索 vs preload：保留路径或查询，运行时再取数据，避免把整份源码或规范塞进 CLAUDE.md。
2. CLAUDE.md ≤ 200 行；MEMORY.md 硬截断 200 行 / 25 KB，超出部分需 agent 主动读取。
3. auto memory 是"agent 自写、人后审"，不是 CLAUDE.md 的别名；两者在作者、内容、作用域、加载量、团队共享五维上完全不同。
4. InstructionsLoaded hook 只能审计加载，不能审计遵守；它告诉你"哪条规则进了上下文"，不告诉你"agent 是否照做"。
5. 失效信号三种：同一会话纠正 ≥2 次 / audit log 0 命中 / compaction 后重犯。
6. /memory 周审计 SOP 含 15 项 checklist，按"大小检查—矛盾清理—路径存活—强调降噪"四组执行。
7. 上下文压力根因：n² attention（每多一个 token 就多 n 个新关系）+ 训练分布偏差（长序列在训练数据里占比少）。
8. compaction 后项目根 CLAUDE.md 会自动重注入，但 nested CLAUDE.md 不会；深目录规则可能"突然消失"。
9. Skill 长会话被静默驱逐：全部 skills 共享 25000 token 预算，溢出时最旧的 skill 整条丢弃。
10. "YOU MUST" 用多了等于没用；每个 CLAUDE.md 至多保留 2–3 条全大写强调。

### 6.1 上下文工程的根问题：n² attention 与 context rot

Anthropic 在上下文工程文章中给出的核心判断是：preload 是反模式，agent 应当保留轻量标识符并在运行时动态取数。原文说，"agents keep lightweight identifiers (file paths, stored queries, web links, etc.) and fetch data dynamically at runtime via tools." 这与传统软件工程中"把依赖全打包进镜像"的思路正好相反——在 LLM 场景里，打包得越多，注意力越散。

所谓 n² attention，全称是每多一个 token 就多 n 个新的配对关系。Transformer 的自注意力机制需要计算序列中任意两个 token 之间的关联权重，因此上下文长度从 n 增加到 n+1 时，计算量并非线性增长，而是近似二次。更直观的后果是"context rot"：当 CLAUDE.md 或对话历史膨胀到数百行时，agent 对单条规则的敏感度会被稀释，就像人在嘈杂会议室里听不清任何一个人的声音。一个典型反例是把整个 `src/api/` 的接口实现全部塞进 CLAUDE.md，希望 agent"提前记住"所有 Handler；正确的做法是在 CLAUDE.md 里只写一句 `Grep(pattern="export.*Handler", path="src/api/")`，让 agent 在真正需要时才去检索。Claude Code 的混合策略正是如此：CLAUDE.md 作为轻量入口 upfront 加载，而具体文件内容通过 Grep、Glob、Read（带 offset/limit）等原语按需拉取。

### 6.2 auto memory 是什么、和 CLAUDE.md 怎么分工

这是用户最容易混淆的一对概念，必须拆清楚。

auto memory 的物理位置在 `~/.claude/projects/<project>/memory/`，其中 MEMORY.md 是索引文件，其余如 `debugging.md` 等为主题文件。写入触发分两种：显式触发来自用户说 "remember that X" 或 "always use pnpm not npm"，agent 会直接写进 auto memory；隐式触发来自 agent 自决，例如在同一次会话中学到 build/test 命令、调试方法论或风格偏好后，自动候选写入。无论哪种，人都应在后续周审计中审阅、剪枝或升级。

CLAUDE.md 与 auto memory 在五维上截然不同。第一，谁写：CLAUDE.md 是人写的规范与约定，auto memory 是 agent 写的学习记录。第二，内容：CLAUDE.md 放 instructions 和 rules，auto memory 放 learnings 和 patterns。第三，作用域：CLAUDE.md 是项目级或用户级，随 git 共享；auto memory 是 per working tree，仅存在本地机器，同事看不到。第四，加载量：CLAUDE.md 完整加载进上下文，MEMORY.md 则硬截断前 200 行或 25 KB，超出部分要靠 agent 主动用 file tool 读取。第五，团队共享：CLAUDE.md 通过版本控制同步，auto memory 不上传、不共享。关键差异可以概括为：auto memory 是"agent 的草稿本"，CLAUDE.md 是"团队的法典"；把规范下沉到 auto memory 会导致团队知识丢失，把临时调试历史上升进 CLAUDE.md 则会造成上下文噪音。

### 6.3 失效信号检测

目前 Claude Code 唯一的原生规则加载 hook 是 `InstructionsLoaded`，其事件载荷包含 `file_path`、`memory_type`（User|Project|Local|Managed）以及 `load_reason`（session_start|nested_traversal|path_glob_match|include|compact）。你可以用它构建最小可用的审计日志，例如通过 jq 把每次加载记录到 `~/.claude/instruction-audit.log`。但必须记住它的限制：hook 不阻塞执行，也不能修改加载内容；它只能告诉你"哪条规则进了上下文"，无法告诉你"agent 是否遵守了这条规则"。

因此，实际判断规则是否失效，需要依赖三个间接信号。第一，用户在同一会话内对同一行为纠正两次以上，说明规则要么没写、要么写得太弱或太长被忽略。第二，audit log 显示某 rule 文件近两周命中 0 次，意味着路径作用域写错或 glob 不匹配，规则成了"静默死规则"。第三，compaction 之后 agent 又开始犯之前纠正过的错，这通常是因为规则只在 conversation 里出现过，没持久化进 CLAUDE.md 或 auto memory，压缩后丢失。

### 6.4 周审计 SOP 与剪枝决策树

每周花 30 分钟跑一遍 15 项 checklist，可以显著延缓规则腐烂。这 15 项不必逐条念，而是按四组逻辑来走。第一组是"大小检查"：CLAUDE.md 是否超过 200 行，MEMORY.md 是否超过 200 行或 25 KB，skill description 是否超过 1536 字符。任何一项超标，都意味着该拆成 path-scoped rule、skill 或主题文件。第二组是"矛盾清理"：检查是否有相互矛盾的规则——如果有，留更具体的那条，删另一条；检查是否有"agent 没它也能做对"的规则——如果有，直接删除，遵循 "If Claude already does without it, delete" 原则；检查是否有多个规则讲同一事——合并到最具体的那一处。第三组是"路径存活"：audit log 里 0 次命中的 rule 文件要改 glob 或删除；CLAUDE.md 和 rules 引用的文件路径是否还存在，可以跑 `claude-rules-doctor` 或手动 grep；nested CLAUDE.md 是否在已废弃的目录里，如果是直接删。第四组是"强调降噪"：检查 "IMPORTANT/YOU MUST" 是否泛滥——超过 5 条等于没强调，应保留最关键 2–3 条；检查 auto memory 里是否有该升进 CLAUDE.md 的事实，或有过期的调试历史，分别执行升级或删除。

剪枝决策树的核心问题是：面对一条现有规则，该删、该留、该转 hook，还是该改写？如果 agent 没这条规则也能做对，答案是直接删。如果 agent 偶尔忘，再分两种情况：内容是事实（如命令、约定）就留在 CLAUDE.md 并加 "YOU MUST" 强调；内容是流程（多步骤、按需执行）就下沉为 skill，CLAUDE.md 只留一句"对 X 用 /skill"。如果 agent 经常违反，也分两种情况：可机检的（如 lint、test、路径限制）转 hook，利用 PreToolUse 或 PostToolUse 做强制校验；不可机检的则改写得更具体，带例子和反例。举个例子，一条 "use pnpm" 规则最初写在 CLAUDE.md 里，发现 agent 偶尔忘，就加了 "YOU MUST"；后来发现 agent 仍然经常违反，于是转成了 PreToolUse hook，在调用 Bash 前检查命令里是否混入了 npm；最终这条规则从"提示语"演变成了"强制闸"。

### 6.5 失败模式：13 种反模式

13 种反模式可以按"短期会话问题"、"长期会话问题"和"工具配置问题"三类来理解，每类内部按严重程度递进。

短期会话问题有五种。Kitchen sink session 指用户在同一会话里切换了两次以上话题，导致上下文混入无关信息；早期信号是 agent 开始引用与当前任务无关的旧代码，对策是不同任务必 `/clear`，一次性问答用 `/btw`。Correcting over and over 指同一缺陷被纠正两次以上，失败尝试在对话里堆积；早期信号是用户重复说"不对，应该是……"，对策是第二次纠错后立即 `/clear`，并重写一条包含"刚学到的事"的 prompt。Over-specified CLAUDE.md 指规则文件过长，重要规则被淹没；早期信号是用户重复 CLAUDE.md 里已写过的事，对策是周审计删冗余，可机检的转 hook。Trust-then-verify gap 指 agent 完成任务后没有自我验证，边界情况在 PR review 才暴露；早期信号是 PR 里频繁出现"漏了空值判断"，对策是强制 tests、screenshots、lint，让 agent 在提交前自我验证。Infinite exploration 指 agent 读了上百文件仍找不到方向；早期信号是 Read 调用数异常膨胀，对策是用 subagent 做调研，prompt 限定文件数和步骤数。

长期会话问题有四种。Compaction-induced amnesia 指压缩后 agent 又开始犯之前纠正过的错；根因是规则只在 conversation 里存在，没进持久化文件，对策是把核心规则放在项目根 CLAUDE.md，或用 `SessionStart(matcher:"compact")` hook 强制重注入。Memory leak 指 auto memory 膨胀，MEMORY.md 超过 200 行；早期信号是启动加载的 memory 截断后丢失关键信息，对策是执行周审计 SOP 第 6、7、8 项，定期拆分和清理。Skill 静默驱逐 指长会话中 skills 共享 25000 token 预算，溢出时最旧的 skill 整条消失；早期信号是 agent 突然不再调用某个之前熟练的 skill，对策是 compaction 后主动 `/skill-name` 刷新关键 skill。All-caps fatigue 指 "YOU MUST / IMPORTANT" 满篇还是不听；根因是强调过载导致 agent 脱敏，对策是每个 CLAUDE.md 至多保留 2–3 条全大写强调。

工具配置问题有四种。Silent dead rule 指 rule 文件还在 git 里，但 audit log 永不命中；根因是路径作用域或 glob 写错，对策是跑 `claude-rules-doctor` 或在 CI 里做命中率检查。Conflicting CLAUDE.md（monorepo）指跨子目录行为不一致；根因是多个嵌套 CLAUDE.md 相互覆盖，对策是用 `claudeMdExcludes` 排除别人的，或合并到 path-scoped rule。AGENTS.md / CLAUDE.md drift 指两个文件说法不一致；根因是维护双信源，对策是在 CLAUDE.md 第一行写 `@AGENTS.md` 做单一信源。Skill 触发不到 指 `/skill-name` 手动调用有效，但 agent 自己从不主动调用；根因是 description 里缺少触发短语，对策是在 description 前置 "Use when …" 等明确触发语。

### 6.6 决策树：新知识进哪一层？

当 agent 或人在会话中学到新知识，下一步不是"写进 CLAUDE.md"，而是先问五个问题。第一个问题：这件事机器可强制吗？如果是 lint、test 或路径限制，应进 hook（`.claude/settings.json`），而不是 prompt。第二个问题：是组织级合规或安全要求吗？如果是，应进 managed CLAUDE.md，确保全组织统一加载。第三个问题：每会话都需要、且全队该知道吗？如果是事实（命令、约定、架构），进项目根 `./CLAUDE.md`（保持 < 200 行）；如果是流程（多步骤、按需执行），进 `.claude/skills/<name>/SKILL.md`。第四个问题：仅在某些路径触发？如果是，写成 `.claude/rules/<name>.md` 并加 paths frontmatter。第五个问题：仅自己用、不入 git？如果是，写进 `./CLAUDE.local.md`（gitignore）或 `~/.claude/CLAUDE.md`。如果以上都不是，再判断是 agent 自己学到的（进 auto memory，让人后审）、长参考材料（留在 docs/，CLAUDE.md 只放 `@docs/...` 路径引用），还是一次性问答（不要沉淀，必要时用 `/btw` 让结果不进历史）。

反例同样重要。以下四类内容压根不该沉淀进任何持久化层：单次 bug 调试历史（应让 agent 用 Grep 现场查，或写进 auto memory 后两周删除）、文件级描述（agent 自己会读文件，不需要你在 CLAUDE.md 里复述函数签名）、标准语言或框架知识（agent 已具备，写进去只会增加噪音）、频繁变化的信息（如临时实验配置，等稳定后再考虑沉淀）。长篇大论的"为什么"也不该进 CLAUDE.md，除非写成 ADR 放在 docs/ 目录，CLAUDE.md 只给链接。

### 【实战速查】五条最反直觉的发现

1. Auto memory 是"agent 自写、人后审"——很多人把 `/memory` 当成 CLAUDE.md 的别名，结果两个文件被同步污染。正确分工：用户记结论、规范、约定（CLAUDE.md），agent 记构建命令、调试洞见、风格偏好（auto memory）。
2. InstructionsLoaded hook 只告诉你"加载"，不告诉你"遵守"——当前唯一的原生 telemetry，只能审计死规则，不能审计被忽略的规则。
3. "YOU MUST / IMPORTANT" 用多了等于没用——best-practices 把"过载强调"列为 bloat 信号；社区被表扬的 CLAUDE.md 特点是"thorough but not shouting in all-caps"。
4. Skills 在长会话里会被默默驱逐——compaction 后所有 skill 共享 25000 token 预算，超出时最旧的 skill 整条消失。关键 skill 要主动 `/skill-name` 重新注入。
5. Project-root CLAUDE.md 在 compact 时会自动重注入，但 nested CLAUDE.md 不会——深目录里的规则只在 agent 下次读那个目录时才回来，意味着 compaction 之后行为可能"突然变"。关键规则要么放项目根，要么用 `SessionStart(matcher:"compact")` hook 强制重注入。

> 至此你已经具备搭建一套 AI 友好文档体系的全部"零件"。但具体到自己的项目应该用 vanilla AGENTS.md、Spec-Kit 还是 BMAD？第 7 章给出选型与迁移路径。

## 第 7 章 方法论选型与迁移

### 【核心概念盒】

- **vanilla [`AGENTS.md`](#术语-agentsmd)**：约定层，单文件入口。一份 markdown 写规则，适合个人或小团队，30 分钟内上手。
- **[`Spec-Kit`](#术语-spec-kit)**：流程层（[`SDD`](#术语-sdd) 流水线）。提供 `specify` / `plan` / `tasks` / `implement` 四个 slash command，把增量开发拆成 spec → plan → tasks 的流水线，适合中大团队、跨 PR feature。
- **[`BMAD-METHOD`](#术语-bmad)**：组织 + 流程 + 角色层。把 PM / Architect / SM / Dev 等角色全部代理化，覆盖 Agile 全生命周期，适合企业、强治理场景。
- **[`OpenSpec`](#术语-openspec)**：以 spec deltas 为核心，强调"先写可验证规约再补实现"，brownfield 友好度高于 Spec-Kit 与 BMAD。
- **三类项目阶梯**：约定 → 流程 → 组织。跨阶梯升级是常见反模式。

### 【一页结论】

1. **vanilla / Aider / Spec-Kit / BMAD 是约定→流程→组织三阶梯**。不要跨阶梯升级。
2. **Spec-Kit 自身警示 over-engineering**；BMAD issue #2003 实测"小 MVP 慢 10–15×"。官方与活跃用户都承认的现实成本。
3. **brownfield 慎用 Spec-Kit / BMAD**——greenfield 优，brownfield 优先 OpenSpec（spec deltas）或自写 spec/plan/tasks。
4. **重型方法论的真实退化路径已经被走通**：BMAD 用作"规划工具"，实施阶段切回 vanilla CLAUDE.md。Spec-Kit 退化只需停用命令、归档 `.specify/`。
5. **多工具中立化首选 @-import + AGENTS.md**：单 source-of-truth，跨平台。
6. **长期看空重型 SDD**：模型推理能力提升时，spec-kit / BMAD 的边际价值会被压缩。把方法论选型当成"当下能力补丁"，不是"永久基础设施"。

### 7.1 三阶梯心智模型

AI 辅助研发的方法论可以按"重量"分成三层，每层解决不同规模的问题，升级时必须逐级来，不能跳。

**约定层**只有一份文件：把项目规则、构建命令、测试规范、禁止事项写进 [`AGENTS.md`](#术语-agentsmd) 或 [`CLAUDE.md`](#术语-claudemd)，放在仓库根目录。代理启动时自动读取，人类维护也只需要改一个地方。这个层级的全部心智负担就是"一份 markdown"，适合个人开发者、两人小团队、或者生命周期在六个月以内的原型项目。约定层的边界很清晰：当文件超过 200 行、规则开始互相覆盖、或者新成员需要反复问"这里该用哪个风格"时，说明约定层已经撑不住了。

**流程层**引入流水线概念：不再是一份静态规则，而是把增量开发拆成 spec → plan → tasks 的流动文档。[`Spec-Kit`](#术语-spec-kit) 是这一层的代表，它用 `specify` 命令生成 [`Constitution`](#术语-constitution) 约束下的 spec，再用 `plan` 和 `tasks` 把实现路径拆成可独立执行的任务。流程层适合 4–10 人团队、需要跨多个 PR 交付的 feature、或者 monorepo 里多个子域需要统一节奏的场景。它的成本也很明确：团队里至少要有一人熟悉 9 个有序 slash 命令的用法，且每次 feature 开头都要写 spec，对业务节奏极快的团队可能是负担。

**组织层**在流程之上叠加角色与治理：[`BMAD-METHOD`](#术语-bmad) 把 PM、Architect、Scrum Master、Dev 全部变成代理角色，每个角色有独立的 prompt 模板、workflow 和验收标准。组织层适合企业级项目、多 stakeholder、强合规审计、或者需要把 Agile 全流程代理化的场景。但组织层的重量也最大：安装和配置需要 1–3 天，且角色与 prompt 深度耦合，退化时很难无痛剥离。

跨阶梯升级是反模式。一个典型的失败模式是：3 人小团队看到 BMAD 的"角色驱动"概念很吸引人，直接跳过约定层和流程层，在仓库里装上 12+ agent persona 和 34+ workflow。结果每次改一个按钮颜色都要先跑一遍 PM → Architect → SM → Dev 的完整流程，开发效率不升反降。正确的做法是：先跑通约定层，当 AGENTS.md 超过 200 行且仍在膨胀时，再考虑拆出路径作用域规则；当 feature 开始跨 5+ PR 且多人冲突频繁时，再上流程层；只有当团队规模、治理强度、合规要求三项同时触发时，才值得承担组织层的重量。

### 7.2 四套方法论对照

在选型之前，先给每套方法论一句话定位，再展开维度对比。

**vanilla AGENTS.md** 的核心范式是"单文件人类规约"——用自然语言告诉代理"这里怎么做、那里不要碰"。**Aider CONVENTIONS.md** 与之类似，但风格更短、更 bullet，且原生绑定 Aider 的 `--read` 机制。**Spec-Kit** 的核心范式是 Spec-Driven Development（[`SDD`](#术语-sdd)）流水线，把"做什么"和"怎么做"分离成可审查的文档。**BMAD-METHOD** 的核心范式是角色驱动 Agile 框架，用代理角色覆盖从需求到交付的全生命周期。**OpenSpec** 则走另一条路：不写完整规约，只写 spec deltas（增量规约），特别适合已有大量存量代码的项目。

上手成本呈阶梯分布：vanilla 与 Aider 都在 30 分钟以内；Spec-Kit 需要 0.5–1 天熟悉命令流与模板；BMAD 需要 1–3 天安装角色包、配置 workflow、调通第一个 feature。brownfield 适配方面，vanilla 和 Aider 最优——它们不改动现有代码结构，只是加一份入口文件；OpenSpec 次之，它的 spec deltas 天然适合补写规约；Spec-Kit 和 BMAD 在 brownfield 中容易产出"表面修复"——规约写得很完整，但实现时为了兼容旧代码只能打补丁。prompt cache 友好度方面，vanilla 和 Aider 最优（单文件、短、静态），BMAD 最差（角色 prompt 长且动态拼接）。

退化路径是选型时必须预演的剧本：vanilla 和 Aider 没有退化问题——删掉文件即可；Spec-Kit 的退化路径中等，停用 slash 命令后把 constitution 留作 ADR 即可；BMAD 的退化路径最难，角色与 prompt 深度耦合，直接卸载会导致代理行为断裂，需要像 issue #2003 作者那样"把 BMAD 当规划工具、实施切回 vanilla"。

下面给出一张精简对照表，把核心差异浓缩到 4 个维度：

| 维度 | vanilla AGENTS.md | Spec-Kit | BMAD-METHOD | OpenSpec |
|---|---|---|---|---|
| **核心范式** | 单文件人类规约 | SDD 流水线（spec → plan → tasks） | 角色驱动 Agile 框架 | Spec deltas（增量规约） |
| **上手成本** | < 30 分钟 | 0.5–1 天 | 1–3 天 | < 1 天 |
| **brownfield 适配** | 优 | 中（greenfield 更强） | 中（v6 引入 brownfield workflow，但 issue 报告"表面修复"多） | 优 |
| **退化路径** | 无（删文件即可） | 中（停用命令，constitution 留作 ADR） | 难（需逐步剥离角色/prompt） | 中（停用 delta 生成，保留规约文档） |

这张表的使用方式是：先确定自己的项目是 greenfield 还是 brownfield，再量一下团队能承受的"流程僵化度"，最后看"万一要退，能不能无痛退"。如果三项中有两项落在右侧重型列，就需要认真评估是否值得承担这个重量。

### 7.3 选型决策树

选型不是"哪个最好"，而是"哪个最匹配当前项目的规模、协作模式和治理强度"。下面按五档规模给出推荐与升级触发点。

**个人 / 1 人 / 原型探索**：vanilla [`AGENTS.md`](#术语-agentsmd)（≤200 行）。不要装任何框架，一份文件写清楚规则就够了。升级触发点：文件超过 200 行、或者项目从原型进入长期维护。

**1–3 人 / 单仓库 / 6 个月内**：AGENTS.md + CONVENTIONS.md + 1–3 份 ADR。ADR 用来记录"为什么选这个技术栈"，避免口头约定丢失。升级触发点：CLAUDE.md 超 200 行、或者单仓库出现 ≥3 个子域且风格开始分歧。

**4–10 人 / 单仓库或浅层多包 / 长期**：在上一层基础上加 `.claude/rules/` 路径作用域规则与 `.claude/skills/` 技能工作流。路径作用域把不同子域的规则拆开，skills 把重复操作（如 fix-issue / create-pr）固化成可执行脚本。升级触发点：feature 跨 PR 数 ≥5、或者多人改同一处代码频繁冲突。

**跨团队 / monorepo / greenfield 0→1 重要**：[`Spec-Kit`](#术语-spec-kit)（constitution + spec + plan + tasks）。constitution 保证跨团队的原则一致，spec/plan/tasks 保证 feature 交付节奏可控。但这里有一个重要警告：brownfield 慎用 Spec-Kit，优先用 OpenSpec 的 spec-delta 试水，验证团队接受度后再决定是否上完整流水线。

**企业级 / 多 stakeholder / 强治理 / Agile 全流程**：[`BMAD-METHOD`](#术语-bmad)（PM + Architect + SM + Dev 角色驱动）。但上 BMAD 之前必须先评估"小 MVP 慢 10–15×"是否可接受——这不是社区谣言，是 issue #2003 的实测数据。如果团队当前的核心 KPI 是交付速度，BMAD 可能不是正确选择。

除了正向信号，还要关注反信号：项目即将 sunset（不要为临时代码投资方法论）、团队 ≤2 人（流程层和组织层的 overhead 会吃掉全部收益）、业务节奏比"流程僵化度"敏感（如果每天需求变三次，任何需要写 spec 的框架都是阻碍）。

### 7.4 升级路径与精简实战

**从轻到重的 5 个升级触发点**：

1. **入口文件 > 200 行且仍在加新规则** → 拆分到路径作用域：`.claude/rules/api.md`（paths: `src/api/**`），把通用规则留在 AGENTS.md，子域规则下沉到对应路径。
2. **Agent 频繁忽略某条规则 / 多个 CLAUDE.md 互相矛盾** → 引入 ADR + glossary，把"为什么"和"术语"从入口分离，减少入口文件的噪音。
3. **同一 feature 跨 5+ PR / 多人改一处易冲突** → 上 spec/plan/tasks 三件套。初期不必立刻装 Spec-Kit，先用 markdown 手写三份文档，验证团队习惯后再决定是否上命令流。
4. **新成员上手 > 1 周 / agent 出"看起来对实则错"的代码频次高** → 装 Spec-Kit（或 OpenSpec，brownfield 优先），强制 constitution + clarify + analyze 三步审查，把隐性知识显性化。
5. **跨团队 / 跨产品 / 合规审计要求** → 上 BMAD；先跑 1 个 feature 当 pilot，验证团队接受度再扩散。不要一次性全仓库铺开。

**精简信号**（什么时候该从重往轻退）：spec/PRD 数量 > 已实现 feature 数 ×2；团队抱怨"写 spec 比写代码慢"；agent 频繁绕过流程直接动代码；prompt cache miss 率高导致响应变慢。

**BMAD → vanilla 三步实战**（来自 issue #2003 作者的公开方案）：

1. **保留 BMAD 的 planning 阶段**：让 PM/Architect 角色跑出 PRD + Architecture 文档，这部分是 BMAD 价值最高的环节——把模糊需求拆成可审查的规约。
2. **实施阶段切到 vanilla**：把 PRD/Architecture 的产物抽要点注入 `CLAUDE.md`，再配一份轻量 `tasks.md` 作为任务列表。不再用 SM/Dev agent 的 prompt 编排，改用裸 Claude Code + 短任务列表驱动实现。
3. **抛弃完整 workflow**：删除从未触发的 agent persona，把跨 feature 重复的 architecture 抽到 `docs/architecture/` 一份，feature 文档只引路径。

实质是把 BMAD 当"重型规划工具"用，而不是"端到端框架"用。这个退化路径已经被社区走通，是重型方法论最现实的落地方式。

### 7.5 方法论混搭与多工具中立化

单一方法论往往不能覆盖全部场景，混搭是常态，但要遵守解耦原则。

**Spec-Kit + .claude/skills（可行，已是官方建议）**：Spec-Kit 维护者 mnriem 在 discussion #2268 明确说明："Constitution 是直接进 spec-kit 命令流的；AGENTS.md 角色较小；SKILLS 在 spec-kit 命令视野之外，仅 implement 命令例外。"这意味着三层可以安全共存：

- **Constitution** = 不可变原则（governance）。写明技术栈、安全底线、性能基线，改动需要 PR review。
- **AGENTS.md** = 跨工具入口（只读引用 constitution）。不同工具用同一行 `@AGENTS.md` 引入，避免重复。
- **`.claude/skills/`** = 可执行 procedure（fix-issue / create-pr 等具体 how-to）。由 agent 自更新，人类只审不手写。

**反模式**：同时跑 Spec-Kit 和 BMAD 完整流程。两套 PM/Architect/Dev 心智会让代理在上下文切换时崩溃——spec-kit 的 `specify` 命令刚生成 spec，BMAD 的 PM persona 又要求重新写 PRD，代理会陷入循环。另一个反模式是在 vanilla AGENTS.md 之外又叠一层 BMAD，小项目的体感就像"装了个交响乐团演四重奏"。

**多工具中立化三方案**：

| 方案 | 实现 | 优势 | 缺点 |
|---|---|---|---|
| **符号链接** | `ln -s AGENTS.md AGENT.md` | 零成本 | Windows 行为不一致；某些 agent 不解析 symlink |
| **@-import（推荐）** | `CLAUDE.md` 单行 `@AGENTS.md` | 跨平台稳；Claude Code 原生支持递归 import（5 层） | Aider 不支持，需 `--read` |
| **中央 git submodule** | 把 `docs/` 与 `AGENTS.md` 抽成独立仓库 | 多产品共享一份治理 | submodule 心智成本；agent 拉不到时静默失败 |

优先级建议：单仓单产品 → @-import；多产品同治理 → submodule；遗留兼容 → symlink。中立化的核心原则是：入口文件名用 `AGENTS.md`（最广兼容），其他工具用 1 行引用；路径作用域规则用工具原生格式，但内容只放工具特性相关部分，通用规约一律回归 AGENTS.md。

### 7.6 反方观点：为什么有人不用

任何方法论都有代价，重型方法的代价尤其高。以下是来自官方与社区的一手反方证据。

**Spec-Kit 反方**：官方 README 自承"Claude Code might be over-eager and add components you did not ask for"，明确标注"over-engineering risk"。社区扩展 TinySpec 的定位就是"skip the heavy multi-step SDD process"，直接回应了 Spec-Kit 的流程重量。Discussion #2315（IDP 团队评估）列出 7 个不够的地方：spec→contract test 缺失、依赖排序模型缺失、governance 不是 first-class 等。ThoughtWorks Tech Radar 的评价更直接："better suited to greenfield projects than brownfield ones"。

**BMAD 反方**：Issue #2003 的作者自称 BMAD fan，但实测结论是"a small MVP could take 10 to 15 times the time with BMAD compared to a normal traditional development process"，且截至调研时维护者无回应。Issue #1930 报告 `bmad-bmm-correct-course` workflow 会重写已完成的 story，导致已实现功能被回退。ThoughtWorks Tech Radar 对 BMAD 的评价是"enforce more rigid workflows"——在需要灵活性的场景里，刚性是缺陷。

**共同长期看空**：ThoughtWorks 在 OpenSpec 的 Tech Radar blip 末尾写道："Continue to monitor and revisit native capabilities and re-evaluate the need for SDD tooling as models grow more powerful."翻译过来就是：当模型推理能力进一步提升，重型 SDD 工具的边际价值会下降。这不是对某个具体工具的否定，而是对所有重型方法论的长期看空信号。选型时请记住：你今天投资的方法论基础设施，可能在 12–18 个月后因为模型能力提升而被压缩成一个内置 hook。把它当成"当下能力补丁"，不是"永久基础设施"。

### 【实战速查】Key Takeaways 清单

1. **vanilla / Aider / Spec-Kit / BMAD 是约定→流程→组织三阶梯**。不要跨阶梯升级。
2. **Spec-Kit 自身警示 over-engineering**；BMAD issue #2003 实测"小 MVP 慢 10–15×"。官方与活跃用户都承认的现实成本。
3. **brownfield 慎用 Spec-Kit / BMAD**——greenfield 优，brownfield 优先 OpenSpec（spec deltas）或自写 spec/plan/tasks。
4. **重型方法论的真实退化路径已经被走通**：BMAD 用作"规划工具"，实施阶段切回 vanilla CLAUDE.md。Spec-Kit 退化只需停用命令、归档 `.specify/`。
5. **多工具中立化首选 @-import + AGENTS.md**：单 source-of-truth，跨平台。
6. **混搭优先级**：constitution 不可变 governance + AGENTS.md 跨工具入口 + skills 可执行 procedure，三层解耦。
7. **长期看空重型 SDD**：模型推理能力提升时，spec-kit / BMAD 的边际价值会被压缩。把方法论选型当成"当下能力补丁"，不是"永久基础设施"。

## 第 8 章 综合建议与仓库骨架

### 8.1 信息密度排序：agent 30 分钟内最需要什么

AGENTS.md 或 CLAUDE.md 的篇幅永远有限，团队必须回答一个核心问题：在 200 行的预算里，应该先放什么？我们的经验是，把内容按 "agent 在最初 30 分钟内最需要" 的优先级排序，而不是按文档的完整度或历史顺序排列。

排在第一位的是 **Quickstart 命令**，应占约 30% 的篇幅。agent 拿到任务后的第一个动作就是运行测试、启动 dev server 或执行一次构建。如果它连项目都跑不起来，后续所有推理都是空中楼阁。因此，安装依赖、启动服务、运行单测的三条命令必须放在文件最上方，且附带环境变量或端口说明。

第二位是 **Repo layout + 不变量**，约占 25%。agent 需要快速建立空间直觉：源码在哪、测试在哪、配置文件遵循什么约定、哪些目录禁止直接修改。用 5-10 行描述目录结构，再用 3-5 条"永远/绝不"式不变量（例如"永远通过 service 层访问数据库，绝不直接在 handler 里写 SQL"）即可。

第三位是 **How to make a change**，约占 15%。这不是完整的 CONTRIBUTING.md，而是极简的 PR 流程：分支命名、测试必须绿、是否需要更新文档。agent 在提交代码前会自检，这几行规则能避免最常见的返工。

第四位是 **Where to look first**，约占 15%。提供一张"任务 → 路径"的速查映射：改 API 先看 `src/api/`，改前端组件先看 `packages/ui/`，排查性能问题先看 `docs/runbooks/performance.md`。agent 不需要搜索整个仓库，而是按图索骥。

第五位是 **Troubleshooting top 3**，约占 10%。列出新手（包括 agent）最可能踩的三个坑：端口冲突怎么解决、测试数据库如何重置、某个常见 lint 错误怎么修。每条一行命令加一行说明。

最后一位是 **指针到深度文档**，约占 5%。用 3-5 个链接指向 ARCHITECTURE.md、onboarding.md、decisions/ 等深度内容。agent 在需要时可以递归读取，但入口文件本身不应膨胀。

需要警惕的是反模式：背景故事、产品愿景、架构演进史虽然对人类读者有吸引力，但对 agent 来说是噪音。这些内容应移入 ARCHITECTURE.md 或独立的 `docs/vision.md`，而不是占据 AGENTS.md 的宝贵行数。

### 8.2 推荐仓库骨架：从一开始照搬即可

以下是一个综合本指南所有结论的中型项目仓库骨架（5-30 人团队、单 monorepo、Claude Code + Cursor + Copilot 三工具混用）。新项目可直接照搬，老项目可按需对号入座。

```
your-project/
├── AGENTS.md                  # 跨工具入口（≤200 行）
├── CLAUDE.md                  # @AGENTS.md + Claude 特有补充
├── .github/
│   ├── copilot-instructions.md
│   ├── instructions/
│   │   └── api.instructions.md   # applyTo: "src/api/**"
│   ├── CODEOWNERS
│   └── workflows/
│       ├── docs-lint.yml
│       ├── links.yml
│       └── docs-required.yml
├── .cursor/
│   └── rules/
│       └── frontend.mdc
├── .claude/
│   ├── rules/
│   │   ├── api.md            # paths: ["src/api/**/*.ts"]
│   │   ├── testing.md
│   │   └── security.md
│   ├── skills/
│   │   ├── fix-issue/SKILL.md
│   │   └── create-pr/SKILL.md
│   ├── hooks/
│   │   ├── block-docs-write.sh
│   │   ├── remind-docs.sh
│   │   └── inject-stale-warning.sh
│   └── settings.json
├── docs/
│   ├── onboarding.md         # 30 分钟动手骨架
│   ├── glossary.md           # 按子域分组
│   ├── architecture/
│   │   ├── workspace.dsl     # Structurizr / C4 DSL
│   │   └── context.svg       # 自动生成
│   ├── decisions/            # MADR ADR
│   │   ├── 0001-use-postgres.md
│   │   └── 0002-auth-strategy.md
│   ├── runbooks/             # 操作手册
│   └── howto/                # 任务级 how-to
├── ARCHITECTURE.md           # matklad 三段式
├── CONTRIBUTING.md           # PR 流程
├── README.md                 # 5 分钟看懂干什么
├── .vale.ini
├── .markdownlint.json
├── .lycheeignore
└── CLAUDE.local.md           # gitignored
```

这个骨架有几个关键决策值得解释。首先，**AGENTS.md 放在仓库根目录**，因为它是跨工具标准，Claude Code、Cursor、Copilot、Aider 等都能识别，放在根目录能确保任何代理进入项目时第一眼看到。其次，**CLAUDE.md 也放在根目录**，但它只做两件事：用 `@AGENTS.md` 引入通用规则，再追加 Claude 特有的补充（如 `.claude/rules/` 的用法、技能工作流的调用方式）。这样避免了双份维护。

第三，**规则放在 `.claude/rules/` 而不是 `.claude/CLAUDE.md/`**，是因为 Claude Code 的 harness 明确支持 `rules/` 目录下的作用域规则（通过 `paths` 字段自动匹配），而 `CLAUDE.md/` 并非官方约定，容易在未来版本产生歧义。第四，**保留 `CLAUDE.local.md` 并 gitignore**，是因为开发者个人常有些本地-only 的偏好（如特定的模型温度、私有 API endpoint），放入版本控制会污染团队共享配置，而放在本地又能被 Claude Code 自动加载。

第五，**docs/ 采用四级分层**：`onboarding.md` 负责 30 分钟动手；`architecture/` 放 C4 模型与自动生成的图；`decisions/` 用 MADR 格式记录架构决策；`runbooks/` 和 `howto/` 分别覆盖运维与开发任务。这种分层让 agent 和人类都能按需深入，而不是在一篇万字长文里迷路。最后，**CI 工作流包含 docs-lint、links 与 docs-required**，确保文档不会随着时间腐烂——这是骨架能持续生效的保险丝。

> 完整骨架已经放在你面前——现在该动手做一份属于你团队的 `AGENTS.md`、`docs/` 与 `.claude/`。需要的所有模板都在附录 B；权威源链接都在附录 C；遇到陌生术语随时跳附录 A。祝顺利。

### 术语-agentsmd

**全称 / 缩写解读**：Agent Markdown，AI 编码代理通用入口规范。2025-08-19 由 OpenAI 首次公开提交，现由 Linux Foundation 旗下 Agentic AI Foundation 接管，已被 60 000+ 项目采用，兼容 30+ 工具（Claude Code、Cursor、Aider、Copilot、OpenAI Codex 等）。
**一句话定义**：一份放在仓库根目录的 markdown 文件，让任意编码代理在启动时读取并理解项目约定、构建命令、测试规范与禁止事项。
**关键约束 / 边界**：规范本身没有版本号或 RFC 流程，仅以 markdown spec 加 FAQ 形式存在；不同工具的加载语义不同（AGENTS.md 是“最近者覆盖”，CLAUDE.md 是“全部追加合并”）；长度无硬性上限，但超过 200 行时代理遵循度会下降；monorepo 中子目录可放嵌套 AGENTS.md，但应避免复制父级内容。
**何处用到 / 何时不用**：任何需要让 AI 代理“开箱即懂”规则的新项目都应放置；个人一次性脚本、即将 sunset 的项目、或团队已统一使用 CONVENTIONS.md / Copilot-instructions 且无意迁移时不必额外引入。
**权威源**：[agents.md](https://agents.md/) · [agents.md GitHub](https://github.com/agentsmd/agents.md)

### 术语-claudemd

**全称 / 缩写解读**：Claude Markdown，Anthropic Claude Code 专属项目入口约定文件。
**一句话定义**：放在仓库根目录的 `CLAUDE.md`，启动时自动完整加载到上下文，功能上等价于 Claude Code 生态的 AGENTS.md，但支持 `@-import` 递归引入、`.claude/rules/` 路径作用域规则与 `.claude/skills/` 技能工作流。
**关键约束 / 边界**：建议 ≤200 行；超过不会硬截断，但会“consume more context and reduce adherence”；与 MEMORY.md 不同，CLAUDE.md 是团队共享的 git 文件，而 auto memory 是机器本地不上传；monorepo 中所有发现的 CLAUDE.md 会按 local > project > user > policy 优先级追加合并。
**何处用到 / 何时不用**：Claude Code 用户必用；若团队主要用 Cursor / Copilot / Aider，可用单行 `@AGENTS.md` 做跨工具兼容，不必在 CLAUDE.md 中重复写通用规则。
**权威源**：[Anthropic Memory & CLAUDE.md](https://code.claude.com/docs/en/memory)

### 术语-memorymd

**全称 / 缩写解读**：Memory Markdown，Claude Code 的记忆持久化索引文件。
**一句话定义**：`~/.claude/projects/<project>/memory/MEMORY.md` 是 auto memory 的入口索引，每会话自动加载前 200 行 / 25 KB（取小），超出部分需 agent 主动用 file tool 读取。
**关键约束 / 边界**：硬截断——超出 200 行或 25 KB 的内容启动时不进上下文；仅记录“稳定事实”（build/test 命令、风格偏好、调试方法论），不写临时调试历史；是 per working tree 的本地文件，不上 git，同事不可见。
**何处用到 / 何时不用**：Claude Code 自动维护，用户只需每周审计；不应把本应进 CLAUDE.md 的规范或约定下沉到 MEMORY.md，否则团队无法共享。
**权威源**：[Anthropic Memory & CLAUDE.md](https://code.claude.com/docs/en/memory)

### 术语-conventionsmd

**全称 / 缩写解读**：Conventions Markdown，Aider 编码代理的项目约定文件。
**一句话定义**：Aider 生态惯用的单文件入口，通常命名为 `CONVENTIONS.md`，启动时通过 `--read` 或配置数组加载，内容风格偏向 bullet 风、只读风格指南。
**关键约束 / 边界**：Aider 不原生支持 `@-import` 或 path frontmatter，需通过 `read:` 数组手动指定多文件；没有 200 行硬上限，但 prompt cache 友好度要求文件尽量精简；与 AGENTS.md / CLAUDE.md 内容可复用，但文件名不同。
**何处用到 / 何时不用**：Aider 用户首选；若项目同时用 Claude Code，建议把通用约定写进 AGENTS.md，再用 `@AGENTS.md` 一行引入，避免维护两份。
**权威源**：[Aider Conventions Guide](https://aider.chat/docs/usage/conventions.html)

### 术语-at-import

**全称 / 缩写解读**：at-import，Claude Code 与 Cursor 在 markdown 文件里用 `@path` 语法递归引入其他文件。
**一句话定义**：`@filename.md` 或 `@docs/adr/0001.md` 让代理在加载主文件时自动把被引文件内容追加到上下文；Claude Code 支持最多 5 跳递归，超出静默截断。
**关键约束 / 边界**：5 跳上限是硬限制；Claude Code 的 `@` 语法与 Cursor 的 `@filename.ts`（把代码文件引入上下文）语义不同，不要混用；不支持 symlink 解析（某些 agent 会静默失败）；最佳实践是把 CLAUDE.md 写成“一行 `@AGENTS.md`”的路由型入口，避免物理冗余。
**何处用到 / 何时不用**：monorepo 或多文件规则拆分必用；单文件 ≤200 行的小项目无需拆分；若需兼容 Aider / Copilot（二者不支持 `@-import`），应改用 symlink 或 CI 同步方案。
**权威源**：[Anthropic Best Practices](https://code.claude.com/docs/en/best-practices)

### 术语-path-frontmatter

**全称 / 缩写解读**：path frontmatter，在 markdown 文件顶部用 YAML frontmatter 声明该文件的作用路径。
**一句话定义**：三大代理（Claude Code `paths:`、Cursor `globs:`、Copilot `applyTo:`）通用的作用域机制，让规则文件只对匹配路径的文件生效，避免全局规则污染无关上下文。
**关键约束 / 边界**：Claude Code 的 `paths:` 是 YAML 数组，只在“读到匹配文件时”加载；Cursor 的 `globs:` 支持标量或数组，且与 `alwaysApply: true` 互斥；Copilot 的 `applyTo:` 是逗号分隔字符串，在 GitHub.com 仅 cloud-agent + code-review 生效，IDE 端 Copilot Chat 完全不读。
**何处用到 / 何时不用**：monorepo 多子域、或规则超过 200 行需要拆分时必用；单域小项目、或规则通用到所有文件时不必加 frontmatter。
**权威源**：[Anthropic Memory & CLAUDE.md](https://code.claude.com/docs/en/memory) · [Cursor Rules](https://cursor.com/docs/context/rules) · [Copilot Custom Instructions](https://docs.github.com/en/copilot/customizing-copilot/adding-custom-instructions-for-github-copilot)

### 术语-paths-field

**全称 / 缩写解读**：paths field（Claude Code），规则文件 frontmatter 中的路径作用域字段。
**一句话定义**：Claude Code `.claude/rules/*.md` 文件顶部 YAML 里的 `paths: ["src/api/**/*.ts"]` 数组，限定该规则只在 agent 读取匹配文件时加载到上下文。
**关键约束 / 边界**：YAML 数组格式；触发时机是“读到匹配文件时”，用户聊天还没 Read 文件时不会进上下文；优先级 local > project > user > policy，后加载的覆盖先加载的。
**何处用到 / 何时不用**：需要按目录拆分规则时必用；全局规则（如代码风格）应放在根 CLAUDE.md，不要为每个目录复制一份。
**权威源**：[Anthropic Memory & CLAUDE.md](https://code.claude.com/docs/en/memory)

### 术语-globs-field

**全称 / 缩写解读**：globs field（Cursor），规则文件 frontmatter 中的路径作用域字段。
**一句话定义**：Cursor `.cursor/rules/*.mdc` 文件顶部 YAML 里的 `globs: "src/api/**/*.ts"` 或数组，作用类似 Copilot `applyTo` 与 Claude Code `paths`，按 glob 限定规则生效范围。
**关键约束 / 边界**：支持标量或数组；与 `alwaysApply: true` 互斥；`Apply Intelligently` 必须填 `description:` 字段；优先级 Team Rules → Project Rules → User Rules，earlier sources take precedence。
**何处用到 / 何时不用**：Cursor 用户按目录拆分规则时必用；若规则通用到所有文件，用 `alwaysApply: true` 跳过 globs。
**权威源**：[Cursor Rules](https://cursor.com/docs/context/rules)

### 术语-applyto-field

**全称 / 缩写解读**：applyTo field（GitHub Copilot），自定义指令文件 frontmatter 中的路径作用域字段。
**一句话定义**：Copilot `.github/instructions/*.instructions.md` 文件顶部 YAML 里的 `applyTo: "src/api/**"` 逗号分隔字符串，限定该规则只对匹配 glob 的文件生效。
**关键约束 / 边界**：字符串类型（非数组）；在 GitHub.com 仅 cloud-agent + code-review 生效，IDE 端 Copilot Chat 完全不读；支持 `excludeAgent` 旁路开关；优先级 Personal > Repository > Organization。
**何处用到 / 何时不用**：Copilot cloud-agent 场景下按目录拆分规则时可用；IDE 内编码助手场景不要依赖 applyTo，应改用全局 copilot-instructions.md。
**权威源**：[Copilot Custom Instructions](https://docs.github.com/en/copilot/customizing-copilot/adding-custom-instructions-for-github-copilot)

### A.2 架构与决策（11 条）

### 术语-c4-model

**全称 / 缩写解读**：Context, Container, Component, Code model，Simon Brown 提出的四级架构图模型。
**一句话定义**：从系统上下文（Context）到容器（Container）、组件（Component）、代码（Code）逐级放大的架构可视化方法，是目前最流行的架构描述标准之一。
**关键约束 / 边界**：四级抽象不是 UML 类图，而是“框+线+标签”的简化图；需要配合 Structurizr DSL 或 Mermaid 才能文本化；4+1 view 更完整但维护成本高，C4 更适合 agent 解析。
**何处用到 / 何时不用**：中小型系统、微服务、需要让 AI agent 读懂架构时首选；重度 UML 团队、或已有完整 arc42 手册的企业可不必额外画 C4。
**权威源**：[c4model.com](https://c4model.com/)

### 术语-arc42

**全称 / 缩写解读**：arc42 architecture template，开源的 12 节架构文档模板。
**一句话定义**：覆盖目标、约束、上下文、构建块、运行时、部署、决策等 12 个章节的架构手册模板，常用于中重型项目的合规与审计场景。
**关键约束 / 边界**：12 节全部填满可能过于冗长；建议把 C4 图嵌入第 5、6、7 章，而不是重复写文字描述；自由文本为主，agent 可解析性低于 C4 DSL。
**何处用到 / 何时不用**：大型企业、需要审计追踪、或团队已有 arc42 文化时适用；轻型项目、或 agent 是主要读者时，优先用 C4 + Code Map 组合。
**权威源**：[arc42.org](https://arc42.org/)

### 术语-four-plus-one

**全称 / 缩写解读**：Four Plus One Architectural View Model，Philippe Kruchten 1995 年提出的架构视图模型。
**一句话定义**：从逻辑视图（Logical）、开发视图（Development）、过程视图（Process）、物理视图（Physical）4 个视图加 1 个场景视图（Scenarios）描述系统，是 UML 时代的经典框架。
**关键约束 / 边界**：5 视图同步维护成本高；UML 图不利于 LLM 直接阅读；现代实践中已被 C4 model 大量替代，仅在重度 UML 团队或学术场景中保留。
**何处用到 / 何时不用**：已有 UML 工具链和建模文化的团队可继续用；新项目、或需要 agent 直接解析架构时，建议迁移到 C4 + Structurizr DSL。
**权威源**：见 [report.md](./report.md) §2.1

### 术语-structurizr-dsl

**全称 / 缩写解读**：Structurizr Domain-Specific Language，Simon Brown 发布的 C4 模型领域专用语言。
**一句话定义**：把 C4 模型写成代码（DSL），再渲染成多种图形格式（Mermaid、PlantUML、SVG），支持版本化、diff 与程序化读取，已有 Structurizr MCP server。
**关键约束 / 边界**：DSL 是文本，但渲染需要 Structurizr 工具链；复杂布局仍需人工微调；与自由 Mermaid 相比学习曲线稍陡。
**何处用到 / 何时不用**：需要版本化架构图、或 agent 需要程序化读取架构时必用；一次性原型、或团队只接受可视化拖拽工具时不必强推。
**权威源**：[Structurizr](https://structurizr.com/)

### 术语-adr

**全称 / 缩写解读**：Architecture Decision Record，架构决策记录。
**一句话定义**：一份小文档，记录“在某个时间因为某些理由做了某个决定”，用于追溯架构演化、防止新人/agent 重复推翻已决策事项。
**关键约束 / 边界**：ADR 不可改、只能追加新 ADR 取代；Status 严格枚举（proposed / accepted / deprecated / superseded by 0042）；文件名建议编号化（`0001-…`）；每条 ADR ≤ 2 页。
**何处用到 / 何时不用**：任何需要记录“为什么选 A 不选 B”的架构决策都应写； trivial 的代码风格选择（如缩进 2 空格）不必写 ADR，放 AGENTS.md 即可。
**权威源**：[adr.github.io](https://adr.github.io/)

### 术语-madr

**全称 / 缩写解读**：Markdown Architecture Decision Records，基于 markdown 的 ADR 模板。
**一句话定义**：在 Nygard 原版五段式基础上增加 YAML frontmatter、Decision Drivers、Considered Options、Pros/Cons 等字段，是目前最流行的 ADR 实现，特别适合 AI agent 程序化检索。
**一句话定义**：MADR 把“考虑过的选项”显式列出，让 agent 和人类都能快速理解决策背景；YAML frontmatter 支持程序化过滤（如“列出所有 superseded 的 ADR”）；长度 1–2 页，编号文件名，Status 严格枚举。
**关键约束 / 边界**：比 Nygard 模板长，小团队可能觉得过度结构化；frontmatter 字段越多，维护成本越高；不适合高管决策或咨询场景（那时用 Y-statement 更合适）。
**何处用到 / 何时不用**：中大型团队、需要 traceability、或 agent 主导维护 ADR 时首选；个人项目、或决策简单到半页能写完时，用 Nygard 模板更轻。
**权威源**：[MADR 4.0](https://adr.github.io/madr/)

### 术语-nygard

**全称 / 缩写解读**：Nygard ADR Template，Michael Nygard 2011 年提出的 ADR 原始模板。
**一句话定义**：五段式固定结构：Title / Status / Context / Decision / Consequences，散文风，半页到 1 页即可。
**关键约束 / 边界**：没有显式“Considered Options”字段，决策背景需要读者从 Context 中推断；无 frontmatter，不利于 agent 程序化检索；Status 只有简单枚举。
**何处用到 / 何时不用**：个人/小团队、或决策背景简单明了时适用；需要选项对比、合规审计、或 agent 自动检索时，应升级到 MADR。
**权威源**：[adr.github.io](https://adr.github.io/)

### 术语-y-statement

**全称 / 缩写解读**：Y-statement ADR，一行式 ADR 写法。
**一句话定义**：模板为“In the context of X, facing Y, we decided for Z, and against W, to achieve V, accepting D”，把决策六要素压缩成一句话，适合幻灯片或高管汇报。
**关键约束 / 边界**：信息密度极高但细节不足，不能替代完整 ADR；没有 Status 追踪；不适合需要长期维护的技术决策。
**何处用到 / 何时不用**：高管决策、咨询/教学、或需要快速传达决策结论时可用；技术团队日常架构决策、或需要 agent 检索时，应写 MADR。
**权威源**：见 [report.md](./report.md) §2.2

### 术语-code-map

**全称 / 缩写解读**：Code Map，代码地图。
**一句话定义**：受 matklad（rust-analyzer 作者）启发的三段式文档：Bird's-eye view（项目解决什么问题）→ Code map（主要目录/模块，每段 2–5 句，回答“X 在哪里？”）→ Cross-cutting concerns（横切关注点如性能、错误处理、可观测性）。
**一句话定义**：Code Map 的核心原则是“命名重要文件/模块/类型，但不直接链接（链接会腐烂）”，并显式指出架构不变量与层间边界。rust-analyzer 的 architecture.md 是模范范本：约 18 个 crate 的两三句描述，每个都说明“是 API boundary 还是 internal”。
**关键约束 / 边界**：不要放链接（会腐烂）；不要写文件级描述（让 agent grep）；应聚焦“在哪里改”而非“怎么改”；Cross-cutting concerns 是反遗漏核心。
**何处用到 / 何时不用**：任何需要让新人/agent 在 30 分钟内定位代码的存量项目都应写；全新项目代码量 < 1000 行时可延后，但应在第一次重大重构前补齐。
**权威源**：[matklad ARCHITECTURE.md](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html) · [rust-analyzer architecture.md](https://github.com/rust-lang/rust-analyzer/blob/master/docs/book/src/contributing/architecture.md)

### 术语-bounded-context

**全称 / 缩写解读**：Bounded Context，DDD（领域驱动设计）中的限界上下文。
**一句话定义**：把大领域切成多个有清晰边界的子领域，每个子域内部术语自洽，子域之间通过显式上下文映射（Context Map）交互。
**关键约束 / 边界**：不是物理模块边界，而是语义边界；一个 bounded context 可跨多个服务，一个服务也可含多个 context；Glossary 应按 bounded context 分组，而不是全局字母序。
**何处用到 / 何时不用**：中大型项目、多团队协作、或术语同名异义频繁时必须引入；个人小项目、或领域概念 < 10 个时不必过度设计。
**权威源**：[Martin Fowler — Bounded Context](https://martinfowler.com/bliki/BoundedContext.html)

### 术语-glossary

**全称 / 缩写解读**：Glossary，术语表 / 通用语言的物化形式。
**一句话定义**：把项目核心名词的定义集中维护，避免代码与文档同名异义；DDD 中即“通用语言”（Ubiquitous Language）的落地文件。
**关键约束 / 边界**：小项目按字母序；中大型项目先按 bounded context 分组、子域内字母序；每条应含“Don't confuse with”反漂移字段；也是 docs-as-code，PR 修改要 review。
**何处用到 / 何时不用**：任何存在业务术语（Order、Invoice、Cart 等）的项目都应维护；纯技术工具库、或术语 < 5 个的项目可延后。
**权威源**：[Martin Fowler — Ubiquitous Language](https://martinfowler.com/bliki/UbiquitousLanguage.html)

### A.3 增量开发（8 条）

### 术语-sdd

**全称 / 缩写解读**：Spec-Driven Development，规约驱动开发。
**一句话定义**：先写可执行或可验证的规约（spec），再写实现代码；AI 时代由 Spec-Kit、OpenSpec 等工具复兴，强调“spec → test → code”顺序铁律。
**关键约束 / 边界**：不是传统瀑布文档，spec 必须可验证；模型能力提升会压缩重型 SDD 工具的边际价值；小项目可能“写 spec 比写代码慢”。
**何处用到 / 何时不用**：跨模块新功能、多人协作、或需要追溯“做什么 vs 怎么做”时适用；改 typo / 修小 bug / 一句话能描述 diff 的任务应跳过 plan 直接做。
**权威源**：见 [report.md](./report.md) §3.1

### 术语-spec-kit

**全称 / 缩写解读**：GitHub Spec-Kit，GitHub 官方推出的 SDD 工具集。
**一句话定义**：提供 `specify` / `plan` / `tasks` / `implement` 四个 slash command 与配套模板（constitution.md + spec.md + plan.md + tasks.md），强调“INDEPENDENTLY TESTABLE”硬约束与 Constitution 不可违背原则。
**一句话定义**：Spec-Kit 的核心产物是四件套：Constitution（项目宪章，不可违背）→ spec（做什么）→ plan（怎么做）→ tasks（拆成可独立执行的任务）。官方自承“over-engineering risk”，社区扩展 `spec-kit-verify` 补 spec→test 验证回路。自身 90.8k★，136 release，136 个第三方扩展。
**关键约束 / 边界**：流程僵化度高（9 个有序 slash 命令）；brownfield 适配中等，greenfield 更强；ThoughtWorks Tech Radar 评价“better suited to greenfield projects than brownfield ones”；退化路径：停用 slash 命令，constitution 留作 ADR。
**何处用到 / 何时不用**：跨团队 monorepo、greenfield 0→1、或需要强治理时适用；个人/小团队、brownfield  legacy 现代化、或业务节奏比流程僵化度敏感时慎用。
**权威源**：[GitHub Spec-Kit](https://github.com/github/spec-kit) · [ThoughtWorks Tech Radar Vol 34](https://www.thoughtworks.com/radar/tools)

### 术语-bmad

**全称 / 缩写解读**：Breakthrough Method for Agile AI-Driven Development，面向 AI 驱动敏捷开发的重型方法论。
**一句话定义**：把 PM / Architect / Scrum Master / Dev 等角色全部代理化，提供 34+ workflow 与 12+ agent persona，覆盖 Agile 全生命周期。
**一句话定义**：BMAD 的核心创新是角色驱动：每个 agent persona 有明确职责边界与输入输出格式。真实采用 33 仓库 + 16 package；最受关注下游 `BMAD-AT-CLAUDE`（229★）专门把 BMAD ported to Claude Code，说明 vanilla BMAD 在 Claude Code 上 not turn-key。Issue #2003 实测“小 MVP 慢 10–15×”。
**关键约束 / 边界**：流程僵化度极高；上手成本 1–3 天；brownfield 适配中等（v6 引入 brownfield workflow，但 issue 报告“表面修复”多）；退化难（角色/workflow 与 prompt 深度耦合）；prompt cache 友好度差。
**何处用到 / 何时不用**：企业级、多 stakeholder、强治理、Agile 全流程必须标准化时适用；个人/小团队、需要快速迭代、或项目即将 sunset 时绝对不用。
**权威源**：[GitHub BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD) · [BMAD-AT-CLAUDE](https://github.com/24601/BMAD-AT-CLAUDE)

### 术语-openspec

**全称 / 缩写解读**：OpenSpec，Tessl 公司推出的 spec 工作流工具。
**一句话定义**：强调规约先行、可机读，特别聚焦“spec deltas”（增量规约）而非一次性完整规约，是 Spec-Kit 的同代竞争者。
**关键约束 / 边界**：ThoughtWorks Tech Radar Vol 34 评为“Assess”；brownfield 场景比 Spec-Kit 更友好（spec-delta 模式）；但生态规模小于 Spec-Kit。
**何处用到 / 何时不用**：brownfield 现代化、或需要“先写 delta spec 试水”时优先于 Spec-Kit；greenfield 0→1 且团队已熟悉 Spec-Kit 时不必切换。
**权威源**：[ThoughtWorks Technology Radar Vol 34](https://www.thoughtworks.com/radar/tools)

### 术语-constitution

**全称 / 缩写解读**：Spec-Kit Constitution，项目宪章文件。
**一句话定义**：Spec-Kit 流程里的最高约束文件，写明项目不可违背的原则（如技术栈、安全底线、性能基线），所有 spec 与 plan 必须与宪章一致，plan-template.md 中有显式的“Constitution Check”门禁。
**关键约束 / 边界**：不是业务需求文档，而是“不可协商的约束”；改动需要 PR review；与 AGENTS.md 解耦：constitution 管 governance，AGENTS.md 管跨工具入口。
**何处用到 / 何时不用**：使用 Spec-Kit 时必用；vanilla AGENTS.md 或 Aider 项目无需单独写 constitution，可把核心约束放进 AGENTS.md 的“Do Not”章节。
**权威源**：[GitHub Spec-Kit](https://github.com/github/spec-kit)

### 术语-spec-plan-tasks

**全称 / 缩写解读**：Spec / Plan / Tasks trio，增量开发的三份标准文档。
**一句话定义**：spec.md 描述“做什么”（需求、场景、验收标准）；plan.md 描述“怎么做”（技术路线、依赖、风险）；tasks.md 拆成可独立执行的任务清单，带 `[P]` 并行标记与 AC 覆盖标注。
**关键约束 / 边界**：不是瀑布三阶段，而是“diff 一句话 → 直接做；多文件或不熟悉 → plan；新功能或重构 → 全套”的决策树产物；tasks.md 里 test 编号必须 < 实现编号。
**何处用到 / 何时不用**：跨文件改动（3+ 文件）、新功能、重构时适用；改 typo / 单文件修 bug 时跳过，用 inline TODO 或口头 plan 即可。
**权威源**：见 [report.md](./report.md) §3.3

### 术语-independently-testable

**全称 / 缩写解读**：Independently Testable user story，Spec-Kit 对用户故事的硬约束。
**一句话定义**：每个用户故事必须能单独验证，不能依赖其他故事完成才能测；是 Spec-Kit spec-template.md 的 mandatory 约束。
**关键约束 / 边界**：不是“不能依赖其他模块”，而是“测试时可独立执行”；若故事 A 的测试必须等故事 B 的接口就绪，说明拆分过细或依赖关系未澄清。
**何处用到 / 何时不用**：写 Spec-Kit spec 时必用；非 Spec-Kit 项目也可作为用户故事拆分质量自检标准。
**权威源**：[GitHub Spec-Kit](https://github.com/github/spec-kit)

### 术语-gherkin-ac

**全称 / 缩写解读**：Gherkin Acceptance Criteria，用 Given/When/Then 三段式写的验收标准。
**一句话定义**：源自 Cucumber / BDD，把验收标准写成“Given 前置条件 / When 动作 / Then 期望结果”，AI 容易解析也方便人类阅读。
**关键约束 / 边界**：每个 story 3–7 条 AC；超 7 条说明 story 太大，应拆分；不是测试代码，而是“人写、机读、测试实现”的三方契约。
**何处用到 / 何时不用**：BMAD、Spec-Kit 或任何需要明确验收标准的增量开发场景适用；探索性原型、或需求极度不确定时不必强行写 AC。
**权威源**：见 [report.md](./report.md) §3.2

### A.4 Docs-as-code（5 条）

### 术语-vale

**全称 / 缩写解读**：Vale linter，开源自然语言 lint 工具。
**一句话定义**：按可配置的样式规则检查 markdown 与文档，支持拼写、大小写、术语替换、禁用词、可读性、句法序列；社区有 Google / Microsoft / RedHat / write-good / proselint 现成包，CI 中守住“AI 友好文档风格”。
**一句话定义**：Vale 是 90% 项目的文档风格检查首选：Go 实现速度快；YAML 规则文件易维护；通过 `Packages = write-good, proselint` 一行即可接管多套风格；与 markdownlint-cli2 互补（Vale 管语义风格，markdownlint 管结构格式）。
**关键约束 / 边界**：不是 markdown 结构检查器（标题层级、列表样式由 markdownlint 负责）；中文/日文场景下 textlint 更强；规则包需要本地 StylesPath 配置。
**何处用到 / 何时不用**：任何需要统一文档风格、术语一致性、或 CI 门禁的项目都应引入；纯英文技术文档、或团队已有成熟 style guide 且无需自动化时，可只跑 markdownlint。
**权威源**：[Vale 官方文档](https://vale.sh/docs/install)

### 术语-markdownlint

**全称 / 缩写解读**：markdownlint-cli2，Node.js 实现的 markdown 规则校验工具。
**一句话定义**：强制标题层级、行长、列表风格、代码围栏语言等格式约束，CI 中用来保证 markdown 结构一致性，与 Vale 形成“结构 + 语义”双轨检查。
**关键约束 / 边界**：只检查结构，不检查语义或风格；规则成熟但插件生态不如 textlint 丰富；与 markdownlint-cli（v1）配置格式不同，迁移需注意。
**何处用到 / 何时不用**：所有写 markdown 的项目都应引入；纯文本或非 markdown 文档项目无需。
**权威源**：[markdownlint-cli2](https://github.com/DavidAnson/markdownlint-cli2)

### 术语-lychee

**全称 / 缩写解读**：lychee link checker，Rust 写的死链检测器。
**一句话定义**：异步并发扫描文档里失效的内外部链接，大仓速度比 Node.js 替代品快 5–30×，支持 `--cache --max-cache-age 1d` 缓存，常用于 CI 中双层策略（增量 PR 守门 + 全量定期巡检）。
**关键约束 / 边界**：不检查锚点是否存在（只检查 URL 可访问性）；外部链接受网络波动影响，建议设重试；GitHub Action 用官方 `lycheeverse/lychee-action`。
**何处用到 / 何时不用**：任何含外部链接的文档仓库都应引入；纯内部文档、或链接全部相对路径且由 monorepo 保证存在时，可降低优先级。
**权威源**：[lycheeverse/lychee](https://github.com/lycheeverse/lychee)

### 术语-codeowners

**全称 / 缩写解读**：Code Owners file，GitHub 的所有者文件。
**一句话定义**：按路径声明谁负责审阅哪些代码，常被 AI 工具复用做“按目录加载不同规则”或“文档变更必须特定角色 review”。
**关键约束 / 边界**：区分大小写；`/docs/` 包含全部子目录；需在 Branch Protection 启用 “Require review from Code Owners”；不是权限控制文件，只是 review 路由。
**何处用到 / 何时不用**：多人协作、需要按模块分配 review 责任、或文档变更需 tech writer 把关时必用；个人项目、或团队 < 3 人时可延后。
**权威源**：[GitHub CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)

### 术语-paths-filter

**全称 / 缩写解读**：dorny/paths-filter，流行的 GitHub Action 路径过滤器。
**一句话定义**：根据 PR 改动路径输出布尔变量，用于条件触发后续步骤；典型场景是“src 改了但 docs 没改”时失败，强制代码与文档同步。
**关键约束 / 边界**：只检测路径变化，不检测内容变化；需配合 `skip-docs` 或 `chore` label 做旁路；与 CODEOWNERS 互补（paths-filter 做门禁，CODEOWNERS 做 review 路由）。
**何处用到 / 何时不用**：需要“代码改必须带文档改”的 PR 门禁时必用；个人项目、或文档与代码不同仓库时无需。
**权威源**：[dorny/paths-filter](https://github.com/dorny/paths-filter)

### A.5 Claude Code 机制（10 条）

### 术语-claude-code

**全称 / 缩写解读**：Claude Code CLI，Anthropic 官方编码代理 CLI。
**一句话定义**：支持 CLAUDE.md / hooks / skills / @-import / auto memory / JIT 检索等机制，是本指南最常引用的代理实现，与 Cursor / Copilot / Aider 并列为四大主流工具。
**关键约束 / 边界**：上下文窗口有硬上限；compaction 后 nested CLAUDE.md 不会自动重注入；skills 共享 25000 token 预算，溢出时最旧的 skill 整条丢弃；不是 IDE 插件，而是独立 CLI。
**何处用到 / 何时不用**：Anthropic 模型用户、或需要 hooks/skills 高级机制时首选；已深度绑定 Cursor IDE 工作流、或团队强制 Copilot 时，可用 AGENTS.md 做跨工具兼容。
**权威源**：[Anthropic Best Practices](https://code.claude.com/docs/en/best-practices)

### 术语-auto-memory

**全称 / 缩写解读**：auto memory，Claude Code 自动记忆机制。
**一句话定义**：会话中观察到的稳定事实（build/test 命令、调试方法论、风格偏好）自动持久化到 `~/.claude/projects/<project>/memory/MEMORY.md`，下次会话自动加载前 200 行 / 25 KB。
**一句话定义**：Auto memory 的核心分工是“agent 自写、人后审”：用户记结论、规范、约定（CLAUDE.md），agent 记构建命令、调试洞见、风格偏好（auto memory）。写入触发分显式（用户说 "remember X"）与隐式（agent 自决）；与 CLAUDE.md 的关键差异：CLAUDE.md 完整加载、团队共享、人写；MEMORY.md 截断加载、机器本地、agent 写。
**关键约束 / 边界**：硬截断 200 行 / 25 KB；是 per working tree 的本地文件，不上 git，同事不可见；不应把“规范/约定”下沉到 auto memory（团队无法共享）；周审计 SOP 要求每月把“该上升 team”的 auto memory 升进 CLAUDE.md。
**何处用到 / 何时不用**：Claude Code 自动维护，用户只需每周审计；不应手动把本应进 CLAUDE.md 的内容写进 MEMORY.md；其他工具（Cursor / Copilot / Aider）无此机制，不可用。
**权威源**：[Anthropic Memory & CLAUDE.md](https://code.claude.com/docs/en/memory)

### 术语-skills

**全称 / 缩写解读**：Claude Code skills，技能机制。
**一句话定义**：把可复用的工作流封装成一个目录（`.claude/skills/<name>/`）加 SKILL.md，按需加载到上下文；SKILL.md 含 description、when_to_use、steps 等字段，agent 根据描述自动判断何时调用。
**一句话定义**：Skills 是“流程层”的最佳实践：多步、按需、可复用。description 总预算占 context window 的 1%（fallback 8000 字符），单条 description+when_to_use 1536 字符封顶；全部 skills 共享 25000 token compaction 预算，溢出时最旧的 skill 整条丢弃。关键 skill 在长会话后应主动 `/skill-name` 重新注入。
**关键约束 / 边界**：不是全局规则（全局放 CLAUDE.md），而是“特定场景下的操作手册”；description 必须前置 “Use when …” 触发短语，否则 agent 可能从不自动调用；compaction 后 skill 可能失活。
**何处用到 / 何时不用**：复杂操作（fix-issue、create-pr、release-bump）需要多步且可复用时必用；一次性任务、或步骤 < 3 步的简单操作不必封装成 skill。
**权威源**：[Anthropic Skills](https://code.claude.com/docs/en/skills)

### 术语-hooks

**全称 / 缩写解读**：Claude Code hooks，工具调用钩子。
**一句话定义**：可在 PreToolUse / PostToolUse / InstructionsLoaded / SessionStart / UserPromptSubmit / Stop / PreCompact 等事件点插入脚本，实现自动化守卫与上下文注入。
**一句话定义**：Hooks 是“机器可强制”规则的落地层：PreToolUse 阻止危险操作（rm、create docs/notes.md）；PostToolUse 自动跑 vale/eslint 让 agent 自纠；SessionStart 注入项目入口与最近 ADR；Stop 提醒更新文档；PreCompact 提醒关键决策落盘。Anthropic 有 25+ 事件，docs-as-code 场景最有用的 8 个已在上文列出。
**关键约束 / 边界**：hook 不阻塞、不能改变加载内容（InstructionsLoaded 只审计）；脚本需自行处理错误码；过度配置 hook 会导致每次操作延迟增加。
**何处用到 / 何时不用**：需要自动化守卫（阻止 agent 创建噪音文档）、或需要在特定事件点注入上下文时必用；简单项目、或团队不熟悉 shell 脚本时可延后。
**权威源**：[Anthropic Hooks](https://code.claude.com/docs/en/hooks)

### 术语-instructionsloaded

**全称 / 缩写解读**：InstructionsLoaded hook event，Claude Code 在加载完所有规则与 memory 之后触发的 hook 事件。
**一句话定义**：事件载荷含 `file_path`、`memory_type`（User|Project|Local|Managed）、`load_reason`（session_start|nested_traversal|path_glob_match|include|compact），常用于注入运行时上下文或写审计日志。
**关键约束 / 边界**：hook 不阻塞、不能改变加载内容；只用于审计；它告诉你“哪条规则进了上下文”，不告诉你“agent 是否照做”；是当前唯一的原生 telemetry。
**何处用到 / 何时不用**：需要追踪“哪些规则被加载、哪些规则是死规则”时必用；不需要审计、或已通过其他方式（如用户反馈）追踪规则有效性时不必配置。
**权威源**：[Anthropic Hooks](https://code.claude.com/docs/en/hooks)

### 术语-pretooluse

**全称 / 缩写解读**：PreToolUse hook，Claude Code 在执行工具调用前触发的 hook 事件。
**一句话定义**：常用于权限校验、命令拦截（如阻止 `rm -rf`、阻止创建 `docs/progress.md` 等噪音文档）、注入额外指令。
**关键约束 / 边界**：不阻塞——即使脚本返回非零，工具调用仍会继续（除非显式实现拦截逻辑）；拦截逻辑需自行设计（如改命令参数或写警告）。
**何处用到 / 何时不用**：需要守卫 agent 不执行危险操作、或需要强制前置检查时必用；完全信任 agent、或环境已有沙箱保护时可省略。
**权威源**：[Anthropic Hooks](https://code.claude.com/docs/en/hooks)

### 术语-compaction

**全称 / 缩写解读**：context compaction，Claude Code 上下文压缩机制。
**一句话定义**：长会话超过窗口阈值时自动摘要旧消息，把历史对话压缩成更短的摘要，是控制 context rot 的内置手段；compaction 后项目根 CLAUDE.md 会自动重注入，但 nested CLAUDE.md 不会。
**一句话定义**：Compaction 的预算分配：skill description 总预算占 context window 的 1%（fallback 8000 字符）；单条 skill 重新注入首 5000 token；全部 skills 共享 25000 token；溢出时最旧的 skill 整条丢弃。这意味着长会话中关键 skill 可能“被忘”，需要主动 `/skill-name` 刷新。同时，compaction 后若 agent 又开始犯之前纠正过的错，说明规则只在 conversation 里出现过，没进 CLAUDE.md。
**关键约束 / 边界**：不是无损压缩，旧消息细节会丢失；nested CLAUDE.md 不会自动重注入；skill 可能失活；PreCompact hook 可用来提醒关键决策落盘。
**何处用到 / 何时不用**：Claude Code 自动触发，用户无需手动干预；但应在 PreCompact hook 中提醒 agent 把关键决策写入 ADR 或 CLAUDE.md；其他工具无此机制。
**权威源**：[Anthropic Best Practices](https://code.claude.com/docs/en/best-practices) · [Anthropic Skills](https://code.claude.com/docs/en/skills)

### 术语-jit-retrieval

**全称 / 缩写解读**：Just-In-Time retrieval，按需加载策略。
**一句话定义**：只在真正需要时把文档片段注入上下文，避免一次性塞满窗口；Claude Code 使用“CLAUDE.md 预加载 + glob/grep 按需检索”的混合模式，是对抗 context rot 的核心手段。
**一句话定义**：Anthropic 上下文工程原话：“Rather than preloading data, agents keep lightweight identifiers (file paths, stored queries, web links, etc.) and fetch data dynamically at runtime via tools.” JIT 的最小命令集合：Grep → 找符号；Glob → 找文件路径；Read → 路径确定后调用（尽量 offset/limit）；Bash → head/tail/wc/git log 取元信息。反模式是把整个 `src/api/` 塞进 CLAUDE.md，或 `cat dump.sql` 进上下文。
**关键约束 / 边界**：需要 agent 具备工具调用能力（Grep/Glob/Read/Bash）；preload 在“已知小范围”场景下更快；JIT 的延迟取决于文件系统检索速度。
**何处用到 / 何时不用**：大仓、长文档、或多文件改造时必用；小项目（< 10 文件）、或 agent 已缓存全部内容时，适度 preload 可接受。
**权威源**：[Anthropic Effective Context Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### 术语-context-rot

**全称 / 缩写解读**：context rot，上下文腐烂。
**一句话定义**：长会话或长文档累积无关信息后，模型注意力被稀释、答案质量下降的现象；根因是 n² attention（n token 形成 n² 配对关系）与长序列训练分布稀疏。
**关键约束 / 边界**：不是内存泄漏，而是注意力分配问题；不能通过“加更多上下文”解决，必须通过 JIT 检索、定期剪枝、compaction 等手段主动减少无关信息。
**何处用到 / 何时不用**：任何长会话（> 20 轮）或长文档（> 200 行）场景都会出现；预防手段包括：不同任务必 `/clear`、用 `/btw` 处理一次性问答、周审计删冗余规则、把长参考材料留在 docs/ 只放路径引用。
**权威源**：[Anthropic Effective Context Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### 术语-prompt-cache

**全称 / 缩写解读**：Anthropic prompt cache，API 的提示缓存机制。
**一句话定义**：把稳定前缀（如 system prompt、CLAUDE.md 内容）缓存 5 分钟内复用，显著降低长上下文成本与延迟；Aider 也利用此机制实现 prompt caching。
**关键约束 / 边界**：5 分钟 TTL；仅缓存前缀（不能缓存中间片段）；缓存 miss 时成本与延迟回归正常；重型 SDD 工具（如 BMAD）因频繁更换上下文导致 cache miss 率高。
**何处用到 / 何时不用**：Claude API 用户自动受益；设计 prompt 时应把稳定内容放前缀、动态内容放后缀；频繁切换 system prompt 或大量 skills 会压缩缓存收益。
**权威源**：[Anthropic Best Practices](https://code.claude.com/docs/en/best-practices) · [Aider Conventions Guide](https://aider.chat/docs/usage/conventions.html)

### B.4 ARCHITECTURE.md (matklad 三段式) 模板

来源：matklad（rust-analyzer 作者）的 ARCHITECTURE.md 范式。关键约束：只命名重要文件/模块/类型，**不直接放链接**（链接会过期）。

```markdown
# ARCHITECTURE

## Bird's-eye view
<项目解决什么问题，一段话。核心用户是谁，核心价值是什么。>

## Code map

### `src/auth/`
认证与授权。入口是 `src/auth/index.ts`，对外暴露 `authenticate()` 与 `authorize()` 两个函数。内部按策略拆分：JWT、Session、OAuth。

### `src/db/`
数据访问层。使用 Drizzle ORM，所有 migration 放在 `src/db/migrations/`。关键实体：User、Order、EmailToken。

### `src/routes/`
HTTP 路由层。每个 domain 一个文件（`auth.ts`、`orders.ts`），统一挂载到 `src/routes/index.ts`。路由只负责解析请求/调用 service/序列化响应，不含业务逻辑。

## Cross-cutting concerns

### Error handling
全栈统一错误码，由 `src/lib/errors.ts` 定义。HTTP 层只转换，不创造新错误语义。

### Observability
所有 service 入口自动注入 trace_id；日志格式为 JSON，字段统一。

### Testing
Contract test 覆盖所有外部接口；Integration test 覆盖跨模块流程；Unit test 仅用于纯函数。
```

```yaml
    steps:
```

```yaml
              - '*.md'
              - '!CHANGELOG.md'
            skip:
              - '.github/skip-docs-check'

  enforce:
    needs: detect
    runs-on: ubuntu-latest
    steps:
      - name: Allow docs-skip label
        id: label
        uses: actions/github-script@v7
        with:
          script: |
            const labels = context.payload.pull_request.labels.map(l => l.name);
            return labels.includes('skip-docs') || labels.includes('chore');
          result-encoding: string

      - name: Require docs change
        if: |
          needs.detect.outputs.code == 'true' &&
          needs.detect.outputs.docs != 'true' &&
          steps.label.outputs.result != 'true'
        run: |
          echo "::error title=Docs missing::代码改动需要同步更新 docs/ 或 *.md。"
          echo "若确属内部重构，可加 PR label 'skip-docs' 或 'chore' 跳过。"
          exit 1

      - name: Pass
```

#### B.8.2 `block-docs-write.sh`

```bash
#!/usr/bin/env bash
# 防止 agent "好心"地创建 docs/progress.md / docs/notes.md 等噪音文档
FP=$(jq -r '.tool_input.file_path')

# 仅拦截"创建 docs/ 下新文件"，编辑已有文件放行
if [[ "$FP" == *"/docs/"* ]] && [[ ! -f "$FP" ]]; then
  case "$FP" in
    */progress*|*/notes*|*/todo*|*/summary*|*/plan*)
      jq -n --arg fp "$FP" '{
        hookSpecificOutput: {
          hookEventName: "PreToolUse",
          permissionDecision: "deny",
          permissionDecisionReason: "禁止 agent 新建过程性 docs（progress/notes/todo/summary/plan）。请走 PR description 或 issue。"
        }
      }'
      exit 0
      ;;
  esac
fi
exit 0
```

#### B.8.4 `inject-stale-warning.sh`

```bash
#!/usr/bin/env bash
AGENTS_MD="$CLAUDE_PROJECT_DIR/AGENTS.md"
[[ -f "$AGENTS_MD" ]] || exit 0

LV=$(grep -m1 'last_verified:' "$AGENTS_MD" | sed 's/.*: *//' | tr -d '"')
[[ -z "$LV" ]] && exit 0

if [[ $(uname) == "Darwin" ]]; then
  AGE_DAYS=$(( ( $(date +%s) - $(date -j -f '%Y-%m-%d' "$LV" +%s) ) / 86400 ))
else
  AGE_DAYS=$(( ( $(date +%s) - $(date -d "$LV" +%s) ) / 86400 ))
fi

if (( AGE_DAYS > 30 )); then
  jq -n --arg d "$AGE_DAYS" '{
    hookSpecificOutput: {
      hookEventName: "UserPromptSubmit",
      additionalContext: ("AGENTS.md 上次校验已 " + $d + " 天，可能存在文档与实现不一致。本轮如发现矛盾以代码为准并提示用户更新文档。")
    }
  }'
fi
exit 0
```

### C.4 架构与决策

- [**matklad — ARCHITECTURE.md (2021)**](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html) — Code Map 范式的开山文章，提出"命名重要文件/模块/类型但不放链接"的核心原则与 Bird's-eye / Code Map / Cross-cutting Concerns 三段式结构。引用于：第 3 章、附录 A 术语-code-map。
- [**rust-analyzer architecture.md**](https://github.com/rust-lang/rust-analyzer/blob/master/docs/book/src/contributing/architecture.md) — Code Map 的模范范本，约 18 个 crate 的描述、API boundary 标注与完整的 Cross-cutting Concerns 覆盖。引用于：第 3 章、附录 A 术语-code-map。
- [**C4 model**](https://c4model.com/) — Simon Brown 提出的 Context / Container / Component / Code 四级架构抽象模型。引用于：第 3 章、附录 A 术语-c4-model。
- [**arc42 Architecture Template**](https://arc42.org/overview) — 12 章节完整架构手册模板，覆盖目标、约束、上下文、构建块、运行时、部署、决策等，常用于合规与审计场景。引用于：第 3 章、附录 A 术语-arc42。
- [**Structurizr**](https://structurizr.com/) — C4 DSL 工具链，支持文本描述架构、多格式渲染（Mermaid / PlantUML / SVG）、版本化与 diff；含 MCP server 可让 agent 程序化查询架构关系。引用于：第 3 章、附录 A 术语-structurizr-dsl。
- [**adr.github.io — Architecture Decision Records**](https://adr.github.io/) — Nygard 五段式、Y-statement 一行式、MADR 三种 ADR 模板的权威托管站。引用于：第 3 章、附录 A 术语-adr / 术语-nygard / 术语-y-statement。
- [**MADR 4.0 — Markdown Architecture Decision Records**](https://adr.github.io/madr/) — 在 Nygard 原版基础上增加 YAML frontmatter、Decision Drivers、Considered Options、Pros/Cons 等字段的最流行 ADR 模板。引用于：第 3 章、附录 A 术语-madr。
- [**Martin Fowler — Ubiquitous Language**](https://martinfowler.com/bliki/UbiquitousLanguage.html) — DDD "通用语言"概念的经典阐述，术语表（Glossary）的理论基础。引用于：附录 A 术语-glossary。
- [**Martin Fowler — Bounded Context**](https://martinfowler.com/bliki/BoundedContext.html) — DDD 限界上下文的原典，大型项目按子域组织术语表与文档的依据。引用于：附录 A 术语-bounded-context。
- [**dependency-cruiser**](https://github.com/sverweij/dependency-cruiser) — JS/TS 项目依赖关系图生成器，支持将"core 不能 import ui"等架构规则写成 CI 强制检查。引用于：第 3 章、附录 B.9。

### C.6 Docs-as-Code 工具

- [**Vale — Prose Linter**](https://vale.sh/docs/install) — Go 实现的自然语言风格检查器，YAML 规则驱动，通过 `Packages = write-good, proselint` 一行接管多套风格；是 90% 项目的文档风格检查首选。引用于：第 5 章、附录 A 术语-vale、附录 B.6。
- [**lychee — Link Checker**](https://github.com/lycheeverse/lychee) — Rust 实现的死链检测器，支持内外部链接、超时重试、排除模式，是 CI 死链接扫描的事实标准。引用于：第 5 章、附录 A 术语-lychee、附录 B.6。
- [**markdownlint-cli2**](https://github.com/DavidAnson/markdownlint-cli2) — Node.js 实现的 Markdown 结构校验工具，管标题层级、列表样式、代码围栏语言标签、行长限制，与 Vale 互补。引用于：第 5 章、附录 A 术语-markdownlint、附录 B.6。
- [**dorny/paths-filter**](https://github.com/dorny/paths-filter) — GitHub Action 路径过滤器，根据 PR 改动路径输出布尔变量用于条件触发后续步骤，是 CI 中实现"只改 docs/ 不跑全套测试"的关键组件。引用于：第 5 章、附录 A 术语-paths-filter、附录 B.6。
- [**GitLab Documentation Workflow**](https://docs.gitlab.com/development/documentation/workflow/) — 公开的四角色 SOP，写（Author）、审（Reviewer）、维（Maintainer）、读（User）各角色的文档职责与工作流，是 docs-as-code 的最详细公开实践。引用于：第 5 章。
- [**Write The Docs — Docs as Code**](https://www.writethedocs.org/guide/docs-as-code/) — PR 门禁、共享所有权、自动化测试的经典入门指南，是"把文档当作一等工程资产"概念的早期推广者。引用于：第 5 章。
