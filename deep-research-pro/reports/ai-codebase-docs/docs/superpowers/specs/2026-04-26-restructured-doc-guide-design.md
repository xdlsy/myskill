## 1. 背景与目标

### 1.1 现状问题

当前 `report.md` 由六个主题的子研究合并而成，作为研究产物完整、考据充分，但作为可读指南存在三类问题：

1. **术语未解释**：`AGENTS.md`、`SDD`、`MADR`、`ADR`、`JIT`、`auto memory` 等高频概念在第一次出现时没有定义，缩写也未给全称
2. **段落感弱**：连续抛出对照表/列表，相关概念散落在多处，缺乏过渡叙述
3. **核心原则一句带过**：很多原则性结论（如"Patches take 2× / locating 10×"、"diff 一句话就直接做"）只有一句引用，没有解释和例子

### 1.2 设计目标

输出一份《结构化文档指南.md》，使其满足以下原则（用户原话）：

- **(P1) 术语首次出现处必解释**：含全称、一句话定义、来源链接
- **(P2) 核心概念用段落体展开**：先一句总结、再一段解释、给一两个具体例子
- **(P3) 段落感强、概念聚合**：相关概念放在一起讲，对照表前必有引子
- **(P4) 重点概念可跳转引用**：内部锚点 + 外部权威源链接，便于读者随用随查

### 1.3 不做什么

- 不做信息删减：原报告所有"实战可落地的结论、对照表、决策树、骨架范本"全部保留
- 不改变事实：所有数字、时间线、引用关系与原报告一致
- 不改变 `report.md` 本身（保留为信源）

## 2. 整体架构

### 2.1 章节大纲

```
《结构化文档指南.md》
├── 引言                            为什么 / 给谁看 / 怎么用
├── 第 1 章 全景与术语速查           整体心智模型 + 一页术语索引
├── 第 2 章 场景一：搭建 AI 友好的项目入口     ← 原 Topic 1
├── 第 3 章 场景二：让 AI 看懂存量代码         ← 原 Topic 2
├── 第 4 章 场景三：用 AI 做增量开发           ← 原 Topic 3
├── 第 5 章 场景四：把文档维护成代码           ← 原 Topic 4
├── 第 6 章 场景五：让文档与规则不腐烂         ← 原 Topic 5
├── 第 7 章 方法论选型与迁移                  ← 原 Topic 6
├── 第 8 章 综合建议与仓库骨架                ← 原 综合建议
├── 附录 A 术语表                  ~30 条概念的权威定义，章内首次出现处链回此处
├── 附录 B 模板与脚本              spec/plan/tasks 模板、hook 脚本、配置文件
└── 附录 C 参考资源                全部外链，按主题分组
```

### 2.2 每章统一布局

每个场景章（第 2–6 章，第 7 章近似）必有以下四段：

| 段名 | 用途 | 长度 |
|---|---|---|
| **【核心概念盒】** | 3–6 行术语+一句话定义；每条链接到附录 A | 占首屏 |
| **【一页结论】** | 5–10 条本章最关键的结论；适合赶时间的读者 | 一段或一短表 |
| **【正文】** | 按 2–4 个小节展开；重叙述、轻列表；相关概念聚合 | 主体 |
| **【实战速查】** | 决策树 / 检查清单 / 对照表，至少一项；供未来翻阅 | 章末 |

第 1 章和第 8 章稍特殊：第 1 章是全文导航 + 术语索引；第 8 章是骨架与信息密度建议。

### 2.3 术语三跳引用机制

满足原则 P4 的关键设计——任一重点概念形成「正文 → 站内术语条 → 外部权威源」三跳：

```
第 2 章正文                       附录 A 术语表                外部权威源
   AGENTS.md  ────────►  ## AGENTS.md  ────────►  https://agents.md
   (一句话定义+锚点链接)         (完整定义、字段、约束)        (规范原文)
```

后续同名术语再次出现时不重复跳转，直接使用即可。

## 3. 格式规范

### 3.1 术语首次出现的处理

每个术语第一次出现必带三件套：**全称**（缩写时）+ **一句话定义** + **附录锚点链接**。

> 例：`AGENTS.md`（[*Agent Markdown*](#术语-agentsmd)，AI 编码代理通用入口规范，2025-08-19 由 OpenAI 提交，现由 Linux Foundation 旗下 Agentic AI Foundation 维护）已被 60 000+ 项目采用……

缩写示例：
- `SDD`（*Spec-Driven Development*，规约驱动开发）
- `ADR`（*Architecture Decision Record*，架构决策记录）
- `MADR`（*Markdown Architecture Decision Records*，基于 Markdown 的 ADR 规范）
- `JIT`（*Just-In-Time*，按需加载）

### 3.2 核心概念的段落体改写

凡原报告里**单句抛出的原则**，必须改成"一句话总结 → 一段话解释 → 一两个例子"的三层结构。

举例：原报告 §2 开头那句 matklad 引用，改写后约 250 字（详见设计文档前面与用户交流的样本）。

### 3.3 段落聚合与过渡

- **不堆砌名词**：相关概念集中到同一段落，用过渡句串联
- **对照表前必有引子**：先一段话说"本节我们关注的是 X、Y、Z 三类工具，分别解决…"
- **对照表后必有解读**：再补一段"对一般 5–30 人团队来说，最值的组合是 …"

### 3.4 表格的克制

| 列数 | 处理方式 |
|---|---|
| ≤ 4 | 保留 |
| 5–7 | 保留，配按列展开的两段叙述 |
| ≥ 8 | 拆为多张小表，或转结构化列表 |

### 3.5 代码 / 脚本的处理

- 主体只引用 5–10 行**骨架结构**，配一段"为什么长这样"
- 完整 vale.ini / hook 脚本 / Spec-Kit 模板 / 仓库骨架等→ **整段挪到附录 B**
- 主体引用附录格式：`完整脚本见 [附录 B.3](#b3-claude-code-hooks-实战脚本)`

## 4. 术语表（附录 A）收录范围

### 4.1 收录标准（满足任一即收录）

- 在原报告里出现 ≥ 3 次的概念
- 缩写或专有名词
- 是某章核心机制（如 `auto memory`、`@-import`）
- 容易混淆的概念（`MEMORY.md` vs `CLAUDE.md`、Spec-Kit `plan` vs Claude Code `plan mode`）

### 4.2 初步术语清单（约 30 条）

| 类别 | 术语 |

| 入口体系 | `AGENTS.md` / `CLAUDE.md` / `MEMORY.md` / `CONVENTIONS.md` / `@-import` / `path frontmatter` / `paths` / `globs` / `applyTo` |
| 架构与决策 | `C4 model` / `arc42` / `4+1 view` / `Structurizr DSL` / `ADR` / `MADR` / `Nygard 模板` / `Y-statement` / `Code Map` / `Bounded Context` / `Glossary` |

```markdown
**权威源**：[链接]
```

## 5. 内容覆盖原则

### 5.1 保留

- 6 大主题所有实战可落地结论、对照表、决策树、骨架范本
- 所有数字、时间线、引用关系（与原报告一致）
- "失败模式 / 反模式"、"信息密度排序"、"仓库骨架"等关键提炼

### 5.2 改写

- 所有"段落感弱 / 堆砌名词 / 术语未解释"的部分按 §3 规范重写
- *Executive Summary* 改成"引言"，重写为有动机叙事的段落（不再是 bullet list）
- 各章结尾增加"下一步"指针（指向另一章或附录模板）

### 5.3 剔除

- 仅服务原报告考据目的的元信息（如"通过 GitHub Commits API 抓取"等）→ 移附录或删除
- 原报告 *Methodology* 章节（不属于指南内容）→ 删除
- 重复出现 ≥ 2 次的同一组小数字 / 表格 → 合并到一处

### 5.4 主动补充

- **每章开头的"为什么"**：锚定动机，让读者知道这章为什么值得读
- **章节之间的连接句**：6 个场景串成一条故事线，不是 6 个独立片段
- **每章末尾的"下一步"指针**：要么指向下一章，要么指向附录

## 7. 验收标准

写完后会逐项自检：

1. 任一术语首次出现处都有定义+附录链接
2. 任一缩写都有全称
3. 没有连续两个对照表之间无引子叙述
4. 每章都有"概念盒 / 一页结论 / 正文 / 实战速查"四段
5. 全文 markdown lint 通过（标题层级、链接格式）
6. 每章结尾都有跳转到下一章或附录的指针
7. 附录 A 全部术语条目齐全
8. 附录 C 每条参考资源至少被正文引用一次

## 8. 写作流程（实施阶段）

按下列顺序完成：

1. 写引言 + 第 1 章（全景与术语速查）
2. 写附录 A 术语表（先把术语全写出来，章内可直接链接）
3. 依次写第 2–7 章；每章完成后跑一次自检 §7
4. 写第 8 章
5. 写附录 B（模板与脚本，从 report.md 抽取）
6. 写附录 C（参考资源，整理外链）
7. 全文通读 + markdown lint 检查
8. 输出到 `结构化文档指南.md`
